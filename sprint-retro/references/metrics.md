# 숫자의 출처

회고 4절과 5절에 쓰는 값은 전부 `pack/retro-pack.json` 에서 나온다. 손으로 세거나 대시보드 화면을 눈으로 읽어 옮기지 않는다.

## 팩 만드는 법

```bash
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --list                    # 스프린트 목록 (id 포함)
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --sprint "26_3_#4" --out ./pack
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --sprint 2080 --out ./pack  # 이름이 겹칠 때 id 로
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --current --out ./pack    # 진행 중
```

`--sprint` 는 Jira 에서 다시 수집한다. 폴러의 `results.json` 은 **활성 스프린트만** 담고 있어 지난 스프린트 회고에는 못 쓴다. 스크립트가 `collect.py` 의 스프린트 질의만 갈아끼워 같은 계산기(`compute.py`)를 태우므로, 대시보드와 같은 규칙으로 계산된 값이 나온다.

산출물:

| 파일 | 내용 |
|------|------|
| `pack/input.json` | 수집 원본 (티켓 + 상태 이력 + 워크로그) |
| `pack/results.json` | `compute.py` 계산 결과 — 대시보드가 읽는 것과 같은 형식 |
| `pack/retro-pack.json` | 회고용 요약. 아래 표의 값들이 여기 있다 |

## 값 대응표

| 회고 본문 | 팩 경로 | 비고 |
|-----------|---------|------|
| 기간 | `기간` | 스크립트가 이미 보정해 둔 문자열이다. `sprint.end` 를 직접 잘라 쓰지 않는다 |
| 설계 문서 N건 | `티켓.문서_티켓_후보` | 제목 접두사(`[WIKI]`·`[발표]`·`[설계]`)로 고른 **후보**다. 접두사 없이 쓴 문서는 안 잡히므로 사람이 확인해 센다 |
| Jira 티켓 N건 | `티켓.전체` | 그 스프린트에 배정됐던 내 티켓 |
| QA 결함 처리 | `티켓.QA_결함` · `티켓.QA_결함_시간` | HOM 원본이 링크된 티켓 |
| 머지된 PR | `PR.머지` · `PR.저장소별` | 저장소별로 나뉜다. 본문에 어느 범위를 썼는지 밝힌다 |
| 실가동 / 캐파 | `부하.실가동h` / `부하.캐파h` → `부하.가동률%` | 실가동은 겹침을 **중복 제거**한 값 |
| 평균 동시 진행 | `부하.평균_동시_진행` | `티켓별_합h ÷ 경과 업무시간` |
| 계획 SP 합 | `계획.계획_SP_합` · `계획.SP_환산h` | 환산은 1SP = 8h |
| 챌린지 실적 | `챌린지_후보[].실적h` | 스프린트 구간과 겹치는 몫만 |
| 챌린지 PR 규모 | `챌린지_후보[].pr` | `+추가/-삭제 N파일` |
| 부록 표 | `부록_티켓별_실적` | 실적 내림차순 |

`PR.저장소별` 은 저장소마다 따로 센다. `머지된 PR 50건` 처럼 한 숫자로 적을 거면 **어느 저장소 기준인지** 본문이나 각주에 남긴다.

## 믿으면 안 되는 값

| 팩의 값 | 왜 |
|---------|-----|
| `기록_구멍.장기_열림_의심` 에 걸린 티켓의 `실적h` | `개발중` 에 하루 넘게 방치된 체류가 통째로 작업시간이 됐다. 5일 방치면 38시간으로 잡힌다. 챌린지 표의 `실적` 칸에 넣기 전에 실제 소요를 사람에게 확인한다 |
| `기록_구멍.작업시간_0` 티켓 | 상태를 안 거쳤을 뿐 작업은 있었을 수 있다. **5절의 재료지 4절의 재료가 아니다** |
| `출처` 가 `worklog` 인 행 | 상태 이력 대신 **Jira 업무 로그**를 표시값으로 쓴 행이다. `compute.py` 의 조건이 `기획 티켓이거나 로그가 1초라도 있으면`(`use_logged`)이라 **로그가 붙은 티켓은 전부 여기 해당한다.** 폴러가 실적을 자동 기입하므로 대부분의 완료 티켓이 결국 `worklog` 가 된다 — 실측 26_3_#5: 46건 중 44건. 그러니 이 비율이 높은 것 자체는 이상 신호가 아니고, **`사람이 손으로 적었다`거나 `상태 측정이 실패했다`는 뜻도 아니다.** 회고 5절에 그렇게 쓰지 마라 |
| `PR.스프린트_티켓에_없는_PR` | 릴리스 PR(`develop => qa`)과 지난 스프린트 티켓의 PR 이 섞인다. 세어서 쓰지 말고 **한 건씩 보고** 티켓 밖 작업만 고른다 |
| `챌린지_후보[].실적h` 중 `장기열림: true` | 위와 같은 이유. 목록이 시간 내림차순이라 **맨 위에 올 수 있다** |
| `부하.평균_동시_진행` | 겹침 등분 설정(`results.json` 의 `overlap_split`)이 바뀌면 값이 달라진다. 지난 대시보드에서 본 숫자와 다를 수 있다 |
| `results.json` 의 `analysis` | 모델이 쓴 산문이고 **갱신되지 않고 이월된다.** 실측 2026-09-13: 활성 스프린트 결과에 8월 중순 문장이 그대로 남아 있었다. 회고에 인용하지 않는다 |

## 함정 — 언제 재는가에 따라 숫자가 바뀐다 ★

같은 스프린트라도 **스냅샷을 뜬 시점**에 따라 티켓별 작업시간이 통째로 달라진다. `compute.py` 가 로그가 1초라도 있으면 로그를 쓰고(`use_logged`), 없으면 상태 체류로 계산하기 때문이다. 폴러가 실적을 나중에 기입하므로 **기준이 체류에서 로그로 넘어가는 시점**이 존재한다.

실측 — 26_3_#4 를 두 시점에 잰 결과다.

| | 스프린트 종료 직후 스냅샷 (2026-09-02) | 11일 뒤 재수집 (2026-09-13) |
|---|---|---|
| 업무 로그가 있는 티켓 | **0건** / 85 | **78건** / 85 |
| `work_source` | changelog 83건 | worklog 78건 |
| 티켓별 합 (`work_biz_seconds`) | 257.2h | 163.3h (**1.58배 차이**) |
| 평균 동시 진행 (`wip_avg`) | 3.9 | 2.47 |
| 실가동 · 캐파 · 티켓 수 | 57.3h · 66h · 85건 | **같음** |

읽는 법:

- **실가동·가동률·캐파·티켓 수는 기준과 무관하다.** 스프린트 간 비교에 안전한 값이다.
- **티켓별 실적과 평균 동시 진행은 기준에 묶인다.** 지난 회고의 숫자와 나란히 놓기 전에 그 회고가 어느 시점 스냅샷을 썼는지 확인한다. 다르면 비교하지 말고 기준이 다르다는 사실을 각주로 남긴다.
- 지난 회고의 스냅샷은 `docs/` 에 있으면 그것을 열어 `work_source` 분포를 세어 확인한다.
- **체류 기반 값을 SP 산정 근거로 쓰지 마라.** 전역 지침이 업무 로그를 정본으로 못 박은 이유가 이것이다.

## 함정 — 저장소 이름

설정(`~/.config/homedot-worktime/config.env` 의 `WORKTIME_GITHUB_REPO`)에 옛 저장소 이름이 남아 있다. 옛 이름으로 `gh pr list` 를 부르면 **에러 없이 빈 목록**이 돌아와 `그 기간에 머지가 없었다` 로 보인다. 실측 2026-09-13:

```
rabyss/homedot-hub-react  → dev-rsquare/hd-cloud-client
rabyss/homedot-hub-admin  → dev-rsquare/hd-cloud-admin
rabyss/design-system      → dev-rsquare/hd-ds
```

스크립트가 `gh repo view` 로 리다이렉트를 따라가 현재 이름으로 조회하고, 해석한 이름을 `PR.조회_실패` 에 기록한다. 머지 0건인 저장소도 같은 칸에 남으므로 **팩을 읽을 때 이 칸을 먼저 본다.** 실제로 그 기간에 작업이 없었던 저장소일 수도 있고, 조회가 틀린 것일 수도 있다.

## 대조 (2026-08-18 ~ 2026-08-30, `26_3_#4`)

사용자가 손으로 쓴 회고와 스크립트 출력이 일치하는지 확인한 기록이다. 스크립트를 고친 뒤 값이 흔들리면 여기로 돌아와 비교한다.

| 항목 | 손으로 쓴 회고 | 스크립트 |
|------|---------------|----------|
| 기간 | 2026-08-18 ~ 2026-08-30 | 2026-08-18 ~ 2026-08-30 |
| Jira 티켓 | 85건 | 85건 |
| 설계 문서 | 2건 | 2건 (`문서_티켓_후보`) |
| 실가동 / 캐파 | 57.3h / 66h → 87% | 57.3h / 66.0h → 87% |
| 계획 SP 합 | 30.71 (환산 245시간) | 30.71 (245.7h) |
| 머지된 PR | 50건 | 50건 (hd-cloud-client) · 11건 (hd-ds) |
| QA 결함 | 57건 | 56건 |
| 평균 동시 진행 | 3.9건 | 2.47건 |

PR 은 **머지일 경계를 맞춘 뒤에야** 손으로 쓴 값과 같아졌다. 보정 전에는 51건이었고, 늘어난 한 건은 08-31 05:45Z 에 머지된 #2211 이다 — 그 PR 은 다음 스프린트(26_3_#5, 08-31 시작)에도 잡혀 **경계일이 양쪽에 이중으로 들어갔다.** `display_end()` 가 이 보정을 한다.

평균 동시 진행만 크게 갈리는데, 이것은 오차가 아니라 **위 `언제 재는가` 함정**이다. 손으로 쓴 회고는 2026-09-02 스냅샷(체류 기준)을 썼고 스크립트는 로그가 붙은 뒤의 값을 낸다.

QA 결함 1건 차이는 세는 범위의 차이로 보인다. 회고를 쓸 때 어느 범위로 셌는지 본문에 밝히면 다음 스프린트와 비교할 수 있다.
