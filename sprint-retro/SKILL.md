# 스프린트 회고

## 이 스킬이 하는 일

지난 스프린트의 **정량 지표**(티켓 수·실가동·가동률·PR)는 스크립트로 뽑고, **정성 서술**(왜 어려웠고 무엇을 판단했는지)은 PR 본문·티켓·커밋에서 근거를 찾아 쓴다. 최종 산출물은 `references/template.md` 구조를 따르는 마크다운 한 편이다.

핵심 원칙 하나: **숫자는 팩에서만, 서술은 근거 자료에서만 가져온다.** 둘 다 없으면 쓰지 않고 `근거 부족`으로 남긴다. 이 문서는 성과를 설명하는 자료라 한 줄이라도 지어내면 전부가 의심받는다.

## 0. 이 스킬은 읽기만 한다

- `refresh.py`를 부르지 않는다. 그쪽은 담당자·상태를 동기화하고 실적을 기입한다. 회고는 **끝난 스프린트를 관찰**하는 작업이라 Jira를 만질 이유가 없다.
- Jira 티켓을 만들거나 상태를 바꾸지 않는다.
- 데이터 팩은 `--out` 폴더에만 쓴다. 폴러의 `~/.config/homedot-worktime/state`는 건드리지 않는다.

## 1. 대상 스프린트 확정

```bash
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --list
```

- 사용자가 이름이나 기간을 지정했으면 그 값을 쓴다.
- 지정이 없으면 **가장 최근에 닫힌 스프린트**를 기본값으로 제시하고 AskUserQuestion으로 확인한다. 같은 이름의 스프린트가 둘일 수 있으므로(실측: `26_3_#3` → id 2077·2078) 기간까지 보여 주고 고르게 한 뒤, 겹치면 이름 대신 **id로** 넘긴다.
- 진행 중인 스프린트를 회고하려는 것이면 그렇게 확인받는다. 그때는 2단계에서 `--current`를 쓴다.

## 2. 데이터 팩 생성

```bash
cd <스크래치패드>
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --sprint "26_3_#4" --out ./pack
# 진행 중인 스프린트면
python3 ~/.claude/skills/sprint-retro/scripts/sprint_pack.py --current --out ./pack
```

- 지난 스프린트는 Jira에서 재수집하므로 티켓 수에 따라 2~5분 걸린다. 한 번만 돌리고 `pack/retro-pack.json`을 재사용한다.
- 결과가 크므로 컨텍스트로 통째로 읽지 말고 `python3 -c` 나 `jq`로 필요한 키만 꺼낸다.
- 각 숫자가 어느 필드에서 나오는지와 믿으면 안 되는 값은 `references/metrics.md`를 본다. **팩에 없는 숫자를 본문에 쓰지 않는다.**

## 3. 챌린지 후보 선별

팩의 `챌린지_후보`는 실적 시간 상위 15건이다. 시간만으로는 회고감이 못 되므로 아래를 더 본다.

| 신호 | 왜 회고감인가 |
|------|---------------|
| 실적 시간 상위 | 그만큼 판단이 많이 들어간 일 |
| PR 변경 규모(파일 수·증감) | 구조를 건드린 일 |
| `reopen` 1회 이상 | 한 번에 못 맞춘 일 → 5절 재료 |
| `스프린트_티켓에_없는_PR` | 티켓 밖에서 한 일 → 5절 재료 |
| 티켓은 있는데 PR이 없는 건 | 설계·조사 작업일 가능성 |
| 같은 도메인 QA 결함이 여러 건 | 묶어서 한 챌린지로 |

**후보 목록을 사용자에게 먼저 보여 주고 고르게 한다.** 무엇이 어려웠는지는 데이터에 없다. 사용자가 "알아서 골라"라고 하면 위 신호로 정하되, 고른 이유를 한 줄씩 밝힌다.

챌린지는 **3~6건**이다. 근거가 있는 만큼만 쓰고 수를 맞추려고 채우지 않는다. 챌린지가 못 된 건은 3절 표로 내린다.

## 4. 서술 근거 수집

챌린지 한 건마다 아래 순서로 읽는다. 앞에서 나온 것이 우선이다.

1. **PR 본문** — `gh pr view <번호> --repo <저장소> --json title,body,additions,deletions,changedFiles`. 이 팀 PR 본문에는 `Purpose`·`Decision / Trade-offs`가 있어 **판단 근거가 그대로 들어 있다.** 챌린지의 `판단` 블록은 대부분 여기서 나온다.
2. **Jira 티켓** — 설명과 댓글. 결정 사항, 배제한 대안, 기획과 주고받은 내용.
3. **커밋 본문** — `git log --format='%H%n%s%n%b' <범위>`. 제목이 아니라 본문을 읽는다.
4. **리뷰 코멘트** — 지적받아 방향을 바꾼 지점이 `어려웠던 지점`의 재료다.
5. **설계 문서** — 티켓에 링크된 위키·Notion.

읽고도 `왜 어려웠는가`를 못 찾으면 **그 건은 챌린지가 아니다.** 3절 표로 내리거나 사용자에게 한 가지만 묻는다. 추측으로 채우지 않는다.

## 5. 작성

`references/template.md`의 구조와 순서를 그대로 따른다. 작성 규칙도 그 파일에 있다. 특히:

- 챌린지 본문은 **상황 / 어려웠던 지점 / 판단 / 남은 것** 4블록 고정이다.
- 5절 `잘 안 된 지점`을 비우지 않는다. 팩의 `기록_구멍`·`reopen_있음`·`계획`이 그대로 재료다. 이 절이 없으면 회고가 아니라 실적 보고서가 된다.
- 부록의 티켓별 실적 표를 반드시 남긴다. 사람이 회고를 읽을 때 서술과 숫자를 대조하는 자리다.
- **이 표를 SP 산정의 근거로 쓰라고 쓰지 마라.** SP 산정의 정본은 Jira 업무 로그이고 `estimate_sp.py` 가 그것을 직접 읽는다. 회고는 파생 사본이라 여기서 다시 근거를 대면 출처가 둘로 갈린다.

## 6. 저장

- 정본 위치는 이 스킬 옆의 `~/chucoding/skills/sprint-retro/docs/` 다. 바로 여기에 쓴다.
- 그 폴더의 `.gitignore` 는 **회고 본문(`.md`)만 막고 스냅샷(`.json`)은 추적한다.** 본문은 업무 내용이라 올리지 않고, 스냅샷은 숫자의 기준을 확인하는 근거라 남긴다.
- 파일을 쓴 뒤 `git status` 로 회고 파일이 미추적으로도 안 잡히는지 확인한다. 잡히면 `.gitignore` 가 깨진 것이므로 커밋하지 말고 알린다.
- `~/Documents/스프린트회고/` 는 예전 정본 위치였다. 지금은 JSON 보관용이고 macOS 개인정보 보호(TCC)가 막아 `ls` 도 `Read` 도 `EPERM` 으로 실패하므로(실측 2026-09-13) 여기에 쓰려고 시도하지 않는다.
- 스크래치패드에 두지 않는다 — 세션이 끝나면 사라진다.
- 파일명은 `<스프린트 이름> <시작>~<종료>` 형태로 통일한다. 스프린트마다 **회고 `.md` 와 스냅샷 `.json` 한 쌍**이 같은 이름으로 놓인다.
  예: `26_3_#4 2026-08-18~2026-08-30.md` 와 `26_3_#4 2026-08-18~2026-08-30.json`
- 회고를 쓴 뒤 팩의 `results.json` 을 그 이름의 `.json` 으로 `docs/` 에 복사한다. `.gitignore` 가 `.md` 만 막고 `.json` 은 추적하므로, **나중에 어느 기준으로 계산된 숫자인지 확인할 근거가 저장소에 남는다.** 이게 없으면 지난 회고 숫자와 재수집 값이 어긋날 때 원인을 다시 찾아야 한다.
- 부록 표 위에 그 스냅샷 파일명과 `work_source` 분포를 한 줄로 밝힌다. `metrics.md` 의 `언제 재는가` 함정 참고.
- Notion에도 올릴지 사용자에게 묻는다. 올린다면 전역 `Notion 지침`을 따른다.

## 7. 마무리

- 본문에 쓴 숫자를 팩과 한 번 대조한다. 특히 `references/metrics.md`의 `믿으면 안 되는 값` 표에 걸린 티켓이 본문에 들어갔는지 본다.
- 확인하지 못한 것을 따로 밝힌다. 예: 특정 저장소 PR 조회 실패, 근거 자료를 못 찾아 3절로 내린 건.
- 회고 문서는 저장소 밖 파일이라 vitest·E2E·커밋 제안 대상이 아니다. 저장소의 문서를 함께 고쳤다면 그때만 커밋을 묻는다.
