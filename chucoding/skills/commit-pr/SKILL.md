파일 수정을 마쳐 커밋 초안을 제시할 때, 사용자가 커밋이나 PR 작성을 요청할 때, 푸시를 마치고 PR 생성 여부를 판단할 때 이 스킬을 적용한다. 아래 `커밋 메시지 및 PR 작성 공통 원칙`은 커밋 메시지와 PR 양쪽에 모두 적용되는 상위 원칙이고, 이어지는 `커밋 메시지 작성 지침`과 `PR 작성 지침`은 그 위에서 각 산출물에 더해지는 세부 규칙이다.

## 커밋 메시지 및 PR 작성 공통 원칙

- [커밋 메시지와 PR은 변경 파일이나 구현 세부를 나열하는 데 그치지 않고 변경의 목적과 의사결정 근거를 보존한다.](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
- [제목은 검색 가능한 간결한 What으로 작성하고, 본문은 Why를 우선하되 변경된 What을 완전히 생략하지 않는다.](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
- 작성 전 `최초 요청과 수용 기준 → 이슈·티켓 → 승인된 계획·스펙·ADR → 명시적으로 합의된 결정 → diff·커밋·실제 테스트 결과` 순서로 확인한다.
- [소스 코드는 무엇을 하는지는 보여도 왜 존재하는지는 드러내지 않을 수 있으므로](https://google.github.io/eng-practices/review/developer/cl-descriptions.html), 코드와 diff는 What과 How를 확인하는 근거로 사용한다. 사용자·운영·사업상의 동기와 접근 선택 이유는 의도 자료에 명시된 내용만 사용한다.
- [Why에는 변경 전의 문제, 변경하지 않을 경우 남는 영향, 기대 결과, 접근 선택 이유, 관련 제약과 트레이드오프 중 확인된 내용만 포함한다.](https://git-scm.com/docs/SubmittingPatches)
- `유지보수성을 높이기 위해`, `사용자 경험을 개선하기 위해`, `성능을 개선하기 위해`처럼 근거 없는 일반론을 작성하지 않는다.
- What을 `~하기 위해` 형태로 바꾼 문장은 Why로 간주하지 않는다. Why는 `이 변경이 없으면 무엇이 남는가`와 `왜 이 접근을 선택했는가`에 답해야 한다.
- 커밋 메시지나 PR을 작성하기 전에 현재 컨텍스트에 기존 문제, 기대 결과, 제약·비목표, 선택 이유, 배제한 대안, 수용 기준과 근거가 있는지 확인한다.
- 의도 정보가 부족하면 연결된 이슈·티켓·계획·ADR과 이전 에이전트의 작업 결과를 먼저 확인한다. 그래도 확인할 수 없으면 추측하지 않고 `의도 근거 부족`을 표시한 뒤 최소 질문 하나를 제시한다.
- [AI가 생성한 PR 요약은 그대로 확정하지 않고 검토하여 작성자만 아는 목적과 맥락을 보완한다.](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)
- 오탈자, 포맷, 자동 생성 파일 갱신처럼 기계적인 변경은 Why 본문을 생략할 수 있다.
- 최종 작성 전에 Why가 What의 재진술인지, 각 주장에 의도 자료나 검증 결과가 연결되는지, 미실행 테스트나 확인되지 않은 효과를 주장하지 않았는지 점검한다.

## 커밋 메시지 작성 지침

- 저장소에 커밋 메시지 규칙이나 템플릿이 있으면 해당 규칙과 구조를 우선한다.
- 제목은 파일명이나 함수명보다 변경으로 달라지는 동작이나 결과를 중심으로 간결하게 작성한다.
- [비자명한 변경의 본문은 `기존 문제와 영향 → 변경 목적 → 이 접근을 선택한 이유` 순서로 작성하고, 필요한 경우 제약·트레이드오프·배제한 대안을 덧붙인다.](https://git-scm.com/docs/SubmittingPatches)
- diff에서 바로 확인할 수 있는 파일별 변경이나 구현 세부를 본문에 나열하지 않는다.
- 관련 이슈·티켓·ADR을 참조하되, 링크를 열지 않아도 이해할 수 있도록 핵심 맥락을 본문에 요약한다.
- 테스트 결과와 성능·보안 효과는 확인된 근거가 있을 때만 작성한다.

### 제목 접두사

- 초안을 만들기 전에 `git log`로 최근 커밋 제목을 확인해 접두사 규칙이 있는지 먼저 본다. 기억에 의존하지 않고 매번 실제 로그에서 확인한다.
- 접두사 규칙이 있으면 초안 단계부터 접두사를 붙여 제시한다. 초안에서 빼고 커밋 시점에 채우는 방식은 쓰지 않는다.
- 접두사 표기는 대괄호 위치, 구분 기호, 공백까지 최근 커밋에서 가장 많이 쓰인 형태를 그대로 따른다.
- 접두사에 로그만으로 알 수 없는 값이 들어가면 임의로 채우지 말고 사용자에게 되묻는다.
- `git commit` 실행 직전에 제목이 접두사로 시작하는지 다시 확인한다. 빠졌으면 커밋하지 않고 제목을 고친 뒤 실행한다.

### 본문 길이

- 본문은 3문장 이내를 기본으로 하고, 꼭 필요한 경우에만 5문장까지 늘린다.
- 세 문장은 `기존 문제 → 변경 목적 → 접근 선택 이유` 순서로 접속 표현을 써서 자연스럽게 이어 쓴다.
- 제목에서 이미 드러난 내용을 본문에서 다시 설명하지 않는다.
- 제약, 트레이드오프, 배제한 대안은 실제로 판단을 바꾼 것만 한 문장으로 남기고 없으면 생략한다.
- 기계적인 변경은 제목만으로 끝낸다.
- 길이를 줄이려고 Why를 빼지 않는다. 줄일 대상은 반복된 서술과 diff에서 확인되는 설명이다.

### 본문 예시

[Google eng-practices의 좋은 CL 설명 예시](https://google.github.io/eng-practices/review/developer/cl-descriptions.html#good), [git SubmittingPatches의 서술 규칙](https://git-scm.com/docs/SubmittingPatches#describe-changes), [Linux submitting-patches의 본문 규칙](https://www.kernel.org/doc/html/latest/process/submitting-patches.html#describe-your-changes) 모두 본문을 불릿 목록이 아닌 문장형 단락으로 작성한다. 아래 예시도 같은 형식을 따른다.

변경 전 문제를 현재 시제로 서술하고, 변경 목적과 접근 선택 이유를 이어서 설명한다. 제목 접두사 규칙은 저장소마다 다르므로 예시에서는 생략한다.

```
목록 재조회 시 선택한 필터가 초기화되던 동작 수정

목록을 재조회하면 필터 상태가 초기값으로 돌아가, 사용자가 조건을 매번 다시 선택해야 한다.
그래서 재조회 후에도 선택한 조건이 유지되도록 바꿨다.
초기화 시점을 조정하는 대신 조회 조건을 URL 쿼리로 옮겼는데, 뒤로 가기와 새로고침에서도 조건이 유지되고 조건이 담긴 링크를 그대로 공유할 수 있기 때문이다.
```

### 커밋 제안 시점

- 파일을 생성하거나 수정하는 작업을 마치면 사용자가 요청하지 않아도 커밋 메시지 초안을 제시하고 커밋 여부를 묻는다.
- 초안은 위 작성 지침에 따라 제목과 본문을 모두 갖춘 형태로 제시한다.
- 커밋 여부는 자유 입력을 기다리지 않고 선택지 UI로 묻는다. 선택지는 `커밋`, `커밋 & 푸시`, `커밋대기` 세 개를 제시하고, 그 밖의 요청은 사용자가 직접 입력하는 항목으로 받는다.
- 선택지 UI를 띄우는 도구가 없는 환경에서는 같은 선택지를 번호 목록으로 출력한다.
- `커밋 & 푸시`를 선택하면 커밋 후 현재 브랜치의 upstream까지 푸시한다. upstream이 없으면 푸시 대상을 먼저 확인한다.
- `커밋대기`를 선택하면 커밋하지 않고 그 턴을 끝낸다. 무엇을 할지 되묻지 않고, 초안을 그대로 둔 채 사용자의 다음 입력을 기다린다. 커밋 외의 요청을 직접 입력 항목으로 받으면 그 입력이 질문에 대한 답으로 기록되어 나중에 대화 내역에서 사용자가 무엇을 요청했는지 찾기 어렵다. `커밋대기`는 그 입력을 일반 사용자 입력으로 되돌리기 위한 항목이므로, 선택 뒤에 선택지를 다시 띄우지 않는다.
- 실제 `git commit`은 사용자가 승인한 뒤에만 실행한다. 초안 제시만으로 커밋하지 않는다.
- 변경이 서로 다른 목적의 단위로 나뉘면 단위별 초안을 제시하고 분리 커밋 여부를 함께 묻는다.
- 아래 경우에는 묻지 않는다.
  - 작업이 아직 중간 단계이고 다음 수정이 이어질 때
  - 스크래치패드나 임시 파일만 변경했을 때
  - 사용자가 커밋하지 않겠다고 밝혔거나 커밋 시점을 직접 지정했을 때

## PR 작성 지침

사용자가 PR 작성을 요청하거나 제안 시점 규칙에 따라 PR 생성 여부를 물을 때, 아래 규칙을 우선 적용하여 PR 제목과 본문을 한국어로 간결하게 작성한다.

### 1. PR 제안 시점

- 푸시를 마치면 아래 순서로 판정하고, 위에서 걸리면 아래는 보지 않는다.
  1. `gh`가 원격을 GitHub 저장소로 인식하지 못하면 묻지 않는다.
  2. 현재 브랜치가 통합 브랜치 자체이면 묻지 않는다.
  3. 이미 열린 PR이 있으면 새로 만들지 않고 푸시로 갱신되었다는 사실만 알린다.
  4. 통합 브랜치에서 분기된 작업 브랜치이면 PR 제목과 본문 초안을 제시하고 선택지로 생성 여부를 묻는다.
  5. base를 확정할 수 없으면 임의로 정하지 않고 base를 되묻는다.
- 통합 브랜치 후보는 이름을 하드코딩하지 않고 `origin/HEAD`가 가리키는 브랜치와 원격에 실제로 존재하는 `develop`, `master`에서 찾는다.
- 후보 중 `git merge-base --is-ancestor <후보> HEAD`를 만족하는 것을 base로 삼고, 여럿이면 merge-base가 가장 최근인 것을 고른다. `develop`과 `main`이 모두 조상이면 `develop`을 고른다.
- 작업 브랜치에서 다시 분기된 브랜치는 base 판정을 사람에게 맡긴다. 상위 작업 브랜치와 통합 브랜치 중 무엇을 대상으로 할지 추정하지 않는다.
- 열린 PR 여부는 생성 직전에 `gh pr list --head <브랜치>`로 다시 확인한다. 훅이 주입하는 PR 상태는 PR이 없는 경우와 조회에 실패한 경우를 구분하지 않아, 그 값만 믿으면 중복 PR이 생길 수 있다.
- base보다 앞선 커밋이 없으면 묻지 않는다.
- PR 제목과 본문은 아래 규칙에 따라 작성한 초안을 그대로 제시한 뒤 생성한다. 사용자가 승인하지 않으면 생성하지 않는다.

### 2. 작업 내역 확인

- 현재 브랜치와 원격 저장소의 기본 브랜치를 확인한다.
- 원격 저장소의 기본 브랜치를 확인할 수 없으면 임의로 추정하지 않고 사용자에게 확인한다.
- 기본 브랜치와 현재 브랜치의 병합 기준점부터 `HEAD`까지 커밋과 변경 내용을 분석한다.
- 공통 원칙에 따른 의도 자료와 실제 변경 내용을 함께 기준으로 작성한다.
- 추측하거나 확인되지 않은 변경 사항을 작성하지 않는다.

### 3. PR 제목

- 현재 브랜치명에서 이슈 번호를 추출한다.
- 이슈 번호를 찾을 수 없으면 `NO-ISSUE`를 사용한다.
- 실제 변경 내용을 분석하여 가장 적합한 유형 하나를 선택한다.
- 유형은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`, `ci`, `style`, `revert` 중 하나만 사용한다.
- 제목은 `유형(이슈 번호): 제목` 형식으로 작성한다.

### 4. PR 본문

- 저장소에 PR 템플릿이 있으면 해당 구조와 섹션 순서를 유지한다.
- [PR 템플릿이 없으면 GitHub의 공식 PR 설명 예시처럼 What, Why, Testing을 구분하여](https://docs.github.com/en/copilot/tutorials/customization-library/custom-instructions/pull-request-assistant) `Purpose`, `Decision / Trade-offs`, `Description`, `How to test`, `Review Requirement`, `Risks / Rollback`, `Additional Info` 순서로 섹션을 사용한다.
- [Purpose에는 변경 전 문제, 변경이 필요한 이유, 기대 결과를 한두 문장으로 작성하고](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes) 구현 내용을 목적형 문장으로 반복하지 않는다.
- Decision / Trade-offs에는 접근 선택 이유, 관련 제약, 배제한 대안을 작성한다. 별도 의사결정이 없으면 `- 해당 없음: 별도 의사결정이 없는 변경`으로 작성한다.
- Description에는 리뷰에 필요한 수준으로 주요 변경을 작성하고, diff에서 확인되는 파일별 변경 목록을 그대로 재서술하지 않는다.
- How to test에는 사용자 요청 또는 현재 대화에서 실제 실행이 확인된 테스트와 결과만 작성한다.
- PR 작성을 위해 테스트를 자동으로 실행하지 않는다.
- 확인된 테스트 실행 기록이 없으면 `- 미실행`과 사유를 작성한다.
- Review Requirement에는 리뷰어가 중점적으로 확인할 사항을 작성한다.
- Risks / Rollback에는 확인된 위험, 호환성 영향, 롤백 방법을 작성한다. 해당 내용이 없으면 `- 해당 없음: 확인된 위험 또는 별도 롤백 절차 없음`으로 작성한다.
- Additional Info에는 확인된 관련 링크를 포함한다. 예: Notion, Figma
- 확인된 관련 링크가 없으면 템플릿 포함 여부와 관계없이 Additional Info 섹션을 생략한다.

### 5. Assignee와 라벨

- PR을 생성할 때 Assignee와 라벨을 함께 지정한다. 본문만 만들고 비워 두지 않는다.
- Assignee 기본값은 현재 `gh` 인증 계정이다. `gh pr create --assignee @me`로 지정하고, 사용자가 다른 담당자를 지정하면 그 값을 따른다.
- 리뷰어는 Assignee와 별개다. 사용자가 리뷰어를 지정하지 않으면 `--reviewer`를 임의로 채우지 않는다.
- 라벨은 `gh label list`로 저장소에 실제 존재하는 목록을 먼저 조회한 뒤 그중에서 고른다. 존재하지 않는 라벨을 새로 만들지 않는다.
- 조회한 목록에서 PR 제목의 유형(`feat`, `fix`, `refactor` 등)과 뜻이 맞는 라벨이 있으면 그것을 고른다. 라벨 체계가 유형과 다르게 잡혀 있으면 저장소 체계를 따른다.
- 맞는 라벨이 없으면 비슷한 것을 억지로 붙이지 않고 라벨 없이 생성한 뒤 그 사실을 알린다.
- Assignee와 라벨 후보는 제목과 본문 초안과 함께 제시해 같은 승인으로 처리한다. 생성 여부를 승인받은 뒤 따로 다시 묻지 않는다.
- 생성 직후 `gh pr view --json assignees,labels`로 실제 반영을 확인한다. 도구 성공 메시지로 대신하지 않는다.
- 지정에 실패하면 PR 링크와 함께 어느 항목이 비었는지 알리고 수동 지정이 필요하다는 점을 밝힌다.
- 이미 열린 PR이 푸시로 갱신되기만 한 경우에는 Assignee와 라벨을 바꾸지 않는다.

### 6. 출력 형식

- 존댓말보다는 제목을 작성하듯이 본문도 간결하게 요지만 작성한다.
- 마크다운으로 출력하여 사용자가 GitHub PR 본문에 붙여넣기 쉽게 한다.
- 승인을 받아 `gh`로 직접 생성하는 경우에는 붙여넣기용 출력 대신 생성된 PR 링크를 알린다.
- PR 제목 예시를 반드시 제시하며, 위 규칙에 따라 선택한 유형과 현재 브랜치에서 추출한 이슈 번호를 포함한다. 이슈 번호가 없으면 `NO-ISSUE`를 사용한다.
- 본문은 마크다운 코드 블록(```markdown ... ```)으로 감싸서 복사하기 편하게 한다. 만약 본문에 코드블럭이 필요한 경우에는 (```)문법 대신 (`)문법을 사용한다.

### 7. PR 생성 후 티켓 상태 전환

- PR 생성이 성공하면 연결된 Jira 티켓 상태를 `리뷰중`으로 전환한다.
- 이 전환은 PR 생성 승인에 포함된 후속 동작으로 본다. 상태 전환 여부를 다시 묻지 않는다.
- 대상 티켓 키는 현재 브랜치명에서, 없으면 PR 제목의 이슈 번호에서 찾는다. 티켓 키를 찾을 수 없거나 `NO-ISSUE`이면 전환하지 않고 그 사실만 알린다.
- 전환 전에 해당 티켓에서 사용 가능한 전환 목록을 조회한다. `리뷰중`에 해당하는 전환이 없으면 비슷한 상태로 임의 전환하지 않고 사용자에게 알린 뒤 지시를 기다린다.
- 티켓이 이미 `리뷰중`이거나 그보다 진행된 상태면 다시 전환하지 않는다.
- HOM 티켓처럼 링크된 클론 티켓이 있으면 같은 상태로 함께 전환한다.
- 아래 경우에는 전환하지 않는다.
  - PR 초안만 제시하고 실제 생성은 하지 않았을 때
  - PR 생성이 실패했을 때
  - 이미 열린 PR이 푸시로 갱신되기만 했을 때
  - 사용자가 상태를 직접 관리하겠다고 밝혔을 때
- 전환을 마치면 티켓 키와 바뀐 상태를 PR 링크와 함께 알린다. 전환에 실패하면 실패 사유와 함께 수동 전환이 필요하다는 점을 알린다.
