파일 수정을 마쳐 커밋 초안을 제시할 때, 사용자가 커밋이나 PR 작성을 요청할 때, 푸시를 마치고 PR 생성 여부를 판단할 때 이 스킬을 적용한다. 아래 `커밋 메시지 및 PR 작성 공통 원칙`은 커밋 메시지와 PR 양쪽에 모두 적용되는 상위 원칙이고, 이어지는 `커밋 메시지 작성 지침`과 `PR 작성 지침`은 그 위에서 각 산출물에 더해지는 세부 규칙이다.

## 커밋 메시지 및 PR 작성 공통 원칙

- [커밋 메시지와 PR은 변경 파일이나 구현 세부를 나열하는 데 그치지 않고 변경의 목적과 의사결정 근거를 보존한다.](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
- [제목은 검색 가능한 간결한 What으로 작성하고, 본문은 Why를 우선하되 변경된 What을 완전히 생략하지 않는다.](https://google.github.io/eng-practices/review/developer/cl-descriptions.html)
- 작성 전 `최초 요청과 수용 기준 → 이슈·티켓 → 승인된 계획·스펙·ADR → 명시적으로 합의된 결정 → diff·커밋·실제 테스트 결과` 순서로 확인한다.
- [소스 코드는 무엇을 하는지는 보여도 왜 존재하는지는 드러내지 않을 수 있으므로](https://google.github.io/eng-practices/review/developer/cl-descriptions.html), 코드와 diff는 What과 How를 확인하는 근거로 사용한다. 사용자·운영·사업상의 동기와 접근 선택 이유는 의도 자료에 명시된 내용만 사용한다.
- [Why에는 변경 전의 문제, 변경하지 않을 경우 남는 영향, 기대 결과, 접근 선택 이유, 관련 제약과 트레이드오프 중 확인된 내용만 포함한다.](https://git-scm.com/docs/SubmittingPatches)
- `유지보수성을 높이기 위해`, `사용자 경험을 개선하기 위해`, `성능을 개선하기 위해`처럼 근거 없는 일반론을 작성하지 않는다.
- What을 `~하기 위해` 형태로 바꾼 문장은 Why로 간주하지 않는다. Why는 `이 변경이 없으면 무엇이 남는가`와 `왜 이 접근을 선택했는가`에 답해야 한다.
- 커밋 메시지나 PR을 작성하기 전에 현재 컨텍스트에 기존 문제, 기대 결과, 제약·비목표, 선택 이유, 배제한 대안, 수용 기준과 근거가 있는지 확인한다.
- 의도 정보가 부족하면 연결된 이슈·티켓·계획·ADR과 이전 에이전트의 작업 결과를 먼저 확인한다. 그래도 확인할 수 없으면 추측하지 않고 `의도 근거 부족`을 표시한 뒤 최소 질문 하나를 제시한다.
- [AI가 생성한 PR 요약은 그대로 확정하지 않고 검토하여 작성자만 아는 목적과 맥락을 보완한다.](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)
- 오탈자, 포맷, 자동 생성 파일 갱신처럼 기계적인 변경은 Why 본문을 생략할 수 있다.
- 최종 작성 전에 Why가 What의 재진술인지, 각 주장에 의도 자료나 검증 결과가 연결되는지, 미실행 테스트나 확인되지 않은 효과를 주장하지 않았는지 점검한다.

## 커밋 메시지 작성 지침

- 저장소에 커밋 메시지 규칙이나 템플릿이 있으면 해당 규칙과 구조를 우선한다.
- 제목은 파일명이나 함수명보다 변경으로 달라지는 동작이나 결과를 중심으로 간결하게 작성한다.
- [비자명한 변경의 본문은 `기존 문제와 영향 → 변경 목적 → 이 접근을 선택한 이유` 순서로 작성하고, 필요한 경우 제약·트레이드오프·배제한 대안을 덧붙인다.](https://git-scm.com/docs/SubmittingPatches)
- diff에서 바로 확인할 수 있는 파일별 변경이나 구현 세부를 본문에 나열하지 않는다.
- 관련 이슈·티켓·ADR을 참조하되, 링크를 열지 않아도 이해할 수 있도록 핵심 맥락을 본문에 요약한다.
- 테스트 결과와 성능·보안 효과는 확인된 근거가 있을 때만 작성한다.

### commitlint 규칙

CI가 commitlint로 커밋 메시지를 검사하는 저장소에서는 규칙을 어긴 커밋이 푸시 뒤에야 CI에서 걸린다. 그래서 초안을 쓰기 전에 그 저장소의 설정을 읽어 초안에 적용하고, 제시하기 전에 검증한다. 규칙 값은 저장소마다 다르므로 기억하는 값을 쓰지 않고 매번 설정에서 읽는다.

- 초안을 쓰기 전에 아래 위치에서 commitlint 설정을 찾는다.
  - `commitlint.config.{js,cjs,mjs,ts,cts,mts}`
  - `.commitlintrc`, `.commitlintrc.{json,yaml,yml,js,cjs,mjs,ts,cts,mts}`
  - `package.json`의 `commitlint` 키
- 로컬 워크트리에 없으면 base 브랜치 원격에서도 찾는다. `git fetch origin <base>` 뒤 `git ls-tree --name-only origin/<base>`로 위 파일이 있는지 보고, 있으면 `git show origin/<base>:<파일>`로 읽는다. base는 `### 1. PR 제안 시점`의 통합 브랜치 판정 규칙으로 정한다. 이 절의 `<base>`는 `origin/`을 뗀 브랜치 이름(예: `main`)이다. base가 `origin/main`처럼 원격 접두사가 붙은 값으로 정해졌으면 접두사를 떼고 쓴다.
  - 원격까지 보는 이유는 워크트리가 설정이 들어오기 전 커밋에서 갈라졌을 수 있어서다. 이때 로컬에는 설정도 `.husky/commit-msg` 훅도 없어 규칙이 없는 것처럼 보이지만, CI는 base에 들어온 설정으로 검사한다.
  - fetch가 실패하면 기존 `origin/<base>`로 찾되, 원격 최신 상태를 확인하지 못했다는 사실을 검증 결과에 함께 적는다.
  - base를 확정하지 못했거나 `origin/<base>`가 없으면 원격 탐색을 건너뛰고, 검증 결과에 `원격 설정 미확인`을 적는다. 커밋 초안 단계에서는 base를 되묻지 않는다.
  - `package.json`은 파일이 있다는 것만으로는 설정이 아니므로 `git show`로 읽어 `commitlint` 키가 있을 때만 설정으로 본다.
- 설정을 찾으면 아래 규칙을 읽어 초안에 적용한다.
  - `extends`로 상속한 공유 설정의 규칙도 포함한다. 상속 규칙은 설치된 패키지(`node_modules/<패키지>`)에서 읽는다. 참고로 `@commitlint/config-conventional`은 type 목록(`type-enum`)을 제한하고 제목(`header-max-length`)과 본문(`body-max-line-length`), footer(`footer-max-line-length`)를 줄당 100자로 제한한다. 이 값은 대조용 참고값이고, 설치된 패키지나 commitlint 실행 결과가 다르면 그쪽을 따른다.
  - 상속한 패키지가 설치되어 있지 않아 규칙을 읽지 못하면 값을 추정하지 않는다. 예외로 `@commitlint/config-conventional`이면 위 참고값 중 줄 길이 제한(100자)만 대조하고, type 목록을 비롯한 나머지 상속 규칙은 검증 결과에 `상속 규칙 미확인`으로 적는다. 그 밖의 공유 설정이면 상속 규칙 전체를 `상속 규칙 미확인`으로 적는다.
  - 설정 파일에서 직접 정의한 규칙은 상속한 값보다 우선한다. 특히 `header-max-length`, `body-max-line-length`, `footer-max-line-length`, `type-enum`, `scope-empty`, `scope-enum`, `subject-full-stop`을 확인한다. 수준이 `0`인 규칙은 꺼진 것이므로 적용하지 않는다. 수준이 `1`인 규칙은 경고라 CI를 막지 않지만 초안에서는 지킨다.
  - `plugins`로 정의한 사용자 규칙(예: scope를 티켓 ID 형식으로 강제하는 규칙)은 규칙 함수의 정규식이나 조건까지 읽고 적용한다.
  - scope처럼 설정만으로 값을 정할 수 없는 항목은 브랜치명에서 찾고, 없으면 임의로 채우지 않고 되묻는다.
- commitlint 설정이 있으면 `### 제목 접두사`에서 최근 커밋 로그로 정한 형식보다 설정을 우선한다. 로그에 규칙 도입 전 커밋이 섞여 있을 수 있기 때문이다.
- 초안을 제시하기 전에 검증한다.
  - commitlint가 설치되어 있으면 초안을 스크래치패드 파일에 쓰고 `npx --no commitlint --config <설정 경로> < <초안 파일>`로 돌린다. 원격에서만 찾은 설정은 스크래치패드에 저장해 그 경로를 넘긴다. `package.json`에서 찾은 설정은 `commitlint` 키의 값만 꺼내 `.commitlintrc.json`으로 저장한다.
  - 설정 로드 오류(패키지 미설치, `extends`나 `plugins` 해석 실패, 복사한 설정의 상대 import 실패)는 규칙 위반과 구분한다. 규칙 위반은 commitlint가 규칙 이름과 함께 보고한 경우뿐이고, 로드 오류면 아래 수동 확인으로 넘어간다.
  - 수동 확인은 줄마다 문자 수를 잰다. commitlint와 같은 기준(문자열 길이, 한글 1자 = 1)으로 재기 위해 `node -e 'require("fs").readFileSync(0,"utf8").split("\n").forEach((l,i)=>console.log(i+1,l.length))' < <초안 파일>`을 쓴다. 제목과 본문, footer 각 줄을 해당 제한과 비교하고 type과 scope도 규칙과 대조한다. `plugins`로 정의한 사용자 규칙은 설정 소스의 규칙 함수를 읽어 직접 대조한다.
- commitlint 통과와 별개로 본문 각 줄이 `### 본문 길이`의 줄 폭 제한(72자, `body-max-line-length`가 더 작으면 그 값) 안인지도 잰다. commitlint 설정이 없는 저장소에서도 이 확인은 한다.
- 검증 결과를 초안과 함께 한 줄로 밝힌다. 예: `commitlint 통과(origin/develop의 commitlint.config.mjs), 본문 최장 66자/72자`, `commitlint 미설치, 수동 확인: 제목 42자/100자, 본문 최장 66자/72자`, `commitlint 설정 없음, 본문 최장 66자/72자`, `commitlint 설정 없음, 본문 최장 66자/72자(URL 1줄 89자 예외)`.
- 검증에 실패하면 초안을 고친 뒤 다시 검증하고, 통과한 초안만 제시한다.

### 제목 접두사

- 초안을 만들기 전에 `git log`로 최근 커밋 제목을 확인해 접두사 규칙이 있는지 먼저 본다. 기억에 의존하지 않고 매번 실제 로그에서 확인한다.
- 접두사 규칙이 있으면 초안 단계부터 접두사를 붙여 제시한다. 초안에서 빼고 커밋 시점에 채우는 방식은 쓰지 않는다.
- 접두사 표기는 대괄호 위치, 구분 기호, 공백까지 최근 커밋에서 가장 많이 쓰인 형태를 그대로 따른다. 단 commitlint 설정이 있으면 `### commitlint 규칙`을 우선한다.
- 접두사에 로그만으로 알 수 없는 값이 들어가면 임의로 채우지 말고 사용자에게 되묻는다.
- `git commit` 실행 직전에 두 가지를 다시 확인한다. 하나라도 어긋나면 커밋하지 않고 메시지를 고친 뒤 실행한다.
  - 제목이 접두사로 시작하는지
  - 제목과 footer의 각 줄이 `### commitlint 규칙`에서 확인한 길이 제한 안에 있고, 본문 각 줄이 `### 본문 길이`의 줄 폭 제한 안에 있는지. commitlint 설정이 없어도 본문 줄 폭은 확인한다. 나눌 수 없는 어절이라 예외로 밝힌 줄은 줄 폭 확인에서 빼되, commitlint 길이 제한은 그 줄에도 적용한다. 초안 제시 뒤 사용자 요청으로 메시지를 고쳤다면 다시 잰다.

### 본문 길이

- 본문은 3문장 이내를 기본으로 하고, 꼭 필요한 경우에만 5문장까지 늘린다.
- 세 문장은 `기존 문제 → 변경 목적 → 접근 선택 이유` 순서로 접속 표현을 써서 자연스럽게 이어 쓴다.
- 문장을 이어 쓰면 한 문장이 길어지므로 줄 길이는 따로 지킨다. 본문 한 줄은 줄 폭 제한을 넘기지 않는다. 줄 폭 제한은 72자이고, commitlint 설정의 `body-max-line-length`가 72보다 작으면 그 값이다. 72자는 git의 관례적인 줄 폭이고, `@commitlint/config-conventional`의 100자 제한에도 여유를 남긴다.
- 줄 폭 제한을 넘는 문장은 어절 사이에서 줄을 나눈다. 줄바꿈은 문장 수에 들어가지 않으며, 나눈 줄을 불릿 목록으로 바꾸지 않는다.
- URL처럼 한 어절이 줄 폭 제한을 넘어 나눌 수 없으면 그 어절만 한 줄에 두고 검증 결과에 예외로 밝힌다. 그 줄이 commitlint 제한까지 넘으면 티켓 키나 `#<이슈 번호>`처럼 커밋 시점에 이미 정해진 짧은 표기로 바꾼다. footer에도 줄 길이 제한이 있으므로 footer로 옮기는 것은 해결이 아니다. Notion이나 Figma 링크처럼 짧은 표기가 없으면 본문에는 링크 없이 무엇을 참조했는지만 적고, 링크는 PR 본문의 `관련 티켓`에 남긴다.
- 제목에서 이미 드러난 내용을 본문에서 다시 설명하지 않는다.
- 제약, 트레이드오프, 배제한 대안은 실제로 판단을 바꾼 것만 한 문장으로 남기고 없으면 생략한다.
- 기계적인 변경은 제목만으로 끝낸다.
- 길이를 줄이려고 Why를 빼지 않는다. 줄일 대상은 반복된 서술과 diff에서 확인되는 설명이다.

### 커밋 제안 시점

- 파일을 생성하거나 수정하는 작업을 마치면 사용자가 요청하지 않아도 커밋 메시지 초안을 제시하고 커밋 여부를 묻는다.
- 초안은 위 작성 지침에 따라 제목과 본문을 모두 갖춘 형태로 제시한다.
- 커밋 여부는 자유 입력을 기다리지 않고 선택지 UI로 묻는다. 선택지는 `커밋`, `커밋 & 푸시`, `main으로 바로 커밋 & 푸시` 세 개를 제시하고, 그 밖의 요청은 선택지 UI가 자동으로 붙이는 직접 입력 항목으로 받는다.
- 푸시가 들어가는 두 선택지의 설명에는 푸시 직전에 `it-plugin:self-review-fix-loop`가 돌아 Critical과 Warning을 직접 고치고 그 수정분을 별도 커밋으로 남긴다는 사실을 한 줄로 알린다. `### 푸시 전 self-review-fix-loop`의 `루프 수정분 커밋`이 이 선택의 승인을 그 커밋의 승인으로 보기 때문이다.
- `main으로 바로 커밋 & 푸시`는 아래 두 조건을 모두 만족할 때만 제시한다. 하나라도 확인하지 못하면 빼고 `커밋`과 `커밋 & 푸시` 두 개만 제시한다.
  - `git remote get-url origin`의 저장소 경로 첫 부분(소유자)이 `chucoding`인 개인 저장소다. SSH 주소는 호스트 별칭을 쓸 수 있으므로(`git@github-chucoding:chucoding/skills.git`) 소유자는 호스트명이 아니라 `:` 또는 호스트 뒤 `/` 다음의 첫 경로로 판정한다. 호스트는 `github.com`이거나 `github-`로 시작하는 SSH 별칭이어야 하며, 다른 호스트에 같은 소유자명이 있어도 개인 저장소로 보지 않는다. 그 밖의 저장소는 PR 리뷰를 거쳐 병합하는 업무 저장소로 본다.
  - `git rev-parse --verify origin/main`이 성공한다. 통합 브랜치가 `master`나 `develop`인 저장소에서는 이 선택지가 맞지 않는다.
- 선택지 UI를 띄우는 도구가 없는 환경에서는 같은 선택지를 번호 목록으로 출력한다.
- `커밋 & 푸시`를 선택하면 커밋 후 아래 `푸시 전 self-review-fix-loop`를 거쳐 현재 브랜치의 upstream까지 푸시한다. upstream이 없으면 푸시 대상을 먼저 확인한다.
- `커밋`을 선택하면 푸시하지 않으므로 self-review-fix-loop도 돌리지 않는다.
- `main으로 바로 커밋 & 푸시`를 선택하면 현재 브랜치에 커밋한 뒤 PR 없이 원격 `main`까지 올린다. 순서는 다음과 같다.
  1. 현재 브랜치에 커밋한다. 워크트리에서는 `main`을 체크아웃할 수 없으므로 브랜치를 바꾸지 않는다.
  2. `git fetch origin main`으로 원격 `main`을 갱신한다. 실패하면 예전 `origin/main`을 기준으로 진행하지 않는다. 실패 메시지를 그대로 보여주고, 만든 커밋은 그대로 둔 채 `커밋 & 푸시`의 푸시 경로로 전환할지 묻는다. 현재 브랜치가 `main`이면 전환해도 같은 곳으로 푸시하게 되므로 묻지 않고 멈춘다.
  3. `git merge-base --is-ancestor origin/main HEAD`로 fast-forward 가능 여부를 확인한다. 불가하면 4단계와 5단계를 건너뛰고 바로 6단계로 간다.
  4. `git log --oneline origin/main..HEAD`로 함께 올라갈 커밋을 확인한다. 방금 만든 커밋 외에 이 브랜치에 앞서 쌓인 커밋이 있으면 목록을 보여주고 모두 PR 없이 `main`에 들어간다는 사실을 알린 뒤, 선택지로 `모두 푸시`와 `푸시 중단`을 묻는다. 방금 만든 커밋뿐이면 묻지 않는다. 방금 만든 커밋은 이번 푸시 절차에서 만든 커밋 전부를 뜻하며 개수와 관계없다. 분리 커밋으로 여러 개를 만든 경우, 루프 수정분을 커밋한 경우, 남은 지적을 반영해 재커밋하거나 rebase해 다시 들어온 경우가 여기에 해당한다. 같은 절차에서 이미 `모두 푸시`를 승인한 커밋도 rebase 뒤에 다시 묻지 않는다.
  5. 아래 `푸시 전 self-review-fix-loop`를 거친 뒤 `git push origin HEAD:main`으로 푸시한다. 첫 리뷰의 base는 `origin/main`이고, 지적을 반영한 뒤에는 그 절의 `재리뷰`를 따른다. 현재 브랜치가 `main`이어도 리뷰를 건너뛰지 않는다.
  6. 원격 `main`과 어긋났으면 푸시하지 않고 멈춘다. 3단계에서 확인한 경우와, fetch 뒤 다른 푸시가 먼저 들어가 5단계의 푸시가 non-fast-forward로 거부된 경우가 모두 여기에 해당한다. 어긋난 커밋 목록을 보여주고 선택지로 `origin/main 위로 rebase 후 푸시`와 `푸시 중단`을 묻는다. 자동으로 rebase하거나 강제 푸시하지 않는다. rebase하면 커밋이 바뀌므로 2단계부터 다시 수행한다.
  7. 푸시가 non-fast-forward 외의 이유, 예를 들어 보호 브랜치 규칙으로 거부되면 우회하지 않고 거부 메시지를 그대로 보여준다. 그다음 이미 만든 커밋은 그대로 두고 `커밋 & 푸시`의 푸시 경로(현재 브랜치 upstream으로 푸시)로 전환할지 묻는다. 다시 커밋하지 않는다. 현재 브랜치가 `main`이면 전환해도 같은 거부를 받으므로 묻지 않고 거부 메시지만 보여준 뒤 멈춘다.
- `main`으로 푸시한 뒤에는 PR 생성 여부를 묻지 않는다. 변경이 이미 통합 브랜치에 들어갔기 때문이다. 이 예외는 `### 1. PR 제안 시점`의 판정 순서에도 들어 있다.
- 직접 입력으로 커밋 외의 요청을 받으면 커밋하지 않고 그 요청을 수행한다. 다만 그 입력은 질문에 대한 답으로 기록되어 나중에 대화 내역에서 사용자가 무엇을 요청했는지 찾기 어렵다. 그래서 응답 첫 줄에 받은 요청을 인용해 남긴 뒤 수행한다. 요청을 수행하느라 파일이 다시 바뀌면 그 작업을 마친 시점에 초안과 선택지를 새로 제시한다.
- 실제 `git commit`은 사용자가 승인한 뒤에만 실행한다. 초안 제시만으로 커밋하지 않는다.
- 변경이 서로 다른 목적의 단위로 나뉘면 단위별 초안을 제시하고 분리 커밋 여부를 함께 묻는다.
- 아래 경우에는 묻지 않는다.
  - 작업이 아직 중간 단계이고 다음 수정이 이어질 때
  - 스크래치패드나 임시 파일만 변경했을 때
  - 사용자가 커밋하지 않겠다고 밝혔거나 커밋 시점을 직접 지정했을 때

### 로컬 통합 브랜치 동기화

main 푸시나 PR 머지 뒤 로컬 `main`은 이 스킬에서 당기지 않는다. Orca 워크스페이스를 닫을 때 archive 훅의 `~/.orca/integration-branch-sync.sh`가 메인 체크아웃 저장소의 `main`을 fast-forward로 맞춘다. 워크스페이스를 닫기 전까지는 메인 체크아웃이 뒤처져 있으므로, `~/.claude/skills/chucoding`처럼 메인 체크아웃을 링크로 쓰는 설치본은 그동안 이전 내용을 읽는다.

- 훅은 저장소마다 Orca Settings → Repository의 archive 스크립트에 등록되어 있어야 돈다. 훅이 등록되지 않은 저장소이거나 워크스페이스를 닫지 않으면 동기화되지 않는다. 푸시나 머지를 어디서 했는지는 상관없다.
- 대상은 원격에 있는 `main` 하나다. 머지했는지 main에 직접 푸시했는지와 관계없이 워크스페이스를 닫을 때마다 `main`을 맞춘다. 이 훅은 `main`만 대상으로 하므로 원격 HEAD가 다른 브랜치를 가리키거나 `develop`, `master`가 남아 있어도 맞추지 않는다. 이 대상은 `### 1. PR 제안 시점`의 base 판정 후보와 다르다. 아직 `develop`을 통합 브랜치로 쓰는 저장소가 있으면 그 저장소의 로컬 `develop`은 훅이 맞추지 않는다.
- 로컬 브랜치가 없거나, 닫는 워크스페이스 자신에 체크아웃되어 있거나, 체크아웃된 워크트리에 변경이 남았거나, fast-forward가 안 되거나, fetch가 실패하면 건너뛰고 훅 로그에만 남긴다.
- 위 어느 경우에도 에이전트가 대신 당기지 않는다. 사용자가 직접 요청할 때만 당긴다.

### 푸시 전 self-review-fix-loop

- `커밋 & 푸시`와 `main으로 바로 커밋 & 푸시`에서 커밋을 마친 뒤, 푸시하기 직전에 `Skill` 도구로 `it-plugin:self-review-fix-loop`를 `--scope branch <base>` 인자로 호출한다. 이 루프는 리뷰를 라운드마다 `it-plugin:self-review`에 맡기고 Critical과 Warning을 working tree에서 직접 고친 뒤 재리뷰를 반복한다. 루프는 커밋하지 않으므로 고친 변경은 아래 `루프 수정분 커밋`에서 이 스킬이 커밋한다. `--max-rounds` 같은 다른 옵션은 지정하지 않고 루프 기본값을 쓴다.
- 푸시 뒤가 아니라 직전에 돌리는 이유는 두 가지다. 푸시 뒤에 지적을 반영하면 커밋과 푸시를 한 번 더 해야 하고, it-review-bot도 그 커밋을 다시 리뷰한다.
- 커밋을 마친 시점에는 working tree가 깨끗하므로 기본 범위인 `working-tree`로는 리뷰할 diff가 없다. 반드시 `--scope branch`로 base를 지정한다. 루프가 2라운드부터 `working-tree`로 재리뷰하는 것은 1라운드에서 고친 변경을 보기 위한 루프 내부 동작이므로 여기서 지정하지 않는다.
- 첫 리뷰의 base는 `### 1. PR 제안 시점`의 통합 브랜치 판정 규칙으로 정한다. 루프와 self-review의 자체 base 감지에 맡기지 않는다. `main으로 바로 커밋 & 푸시`에서는 판정 없이 `origin/main`을 base로 쓴다. 지적을 반영한 뒤의 재리뷰는 base가 다르므로 아래 `재리뷰`를 따른다.
- 루프를 호출하기 직전에 `git rev-parse HEAD`로 리뷰할 HEAD를 기록해 둔다. 재리뷰 범위의 기준이 되며, 결과 파일에서 거꾸로 찾지 않는다. 루프 수정분을 커밋하면 기록을 그 커밋으로 바꾼다.
- 루프를 호출하기 전에 `git status --porcelain --untracked-files=no`가 비어 있는지 확인한다. 커밋하지 않은 변경이 남아 있으면 루프가 2라운드부터 그 변경까지 리뷰하고 고칠 수 있고, 끝난 뒤 루프가 고친 변경과 원래 있던 변경을 가를 수 없다. 이때는 루프를 돌리지 않고 남은 변경과 이유를 밝힌 뒤 리뷰 없이 푸시할지 선택지로 묻는다. 추적되지 않는 파일을 빼고 보는 이유는 아래 결과 파일처럼 `.gitignore`에 없는 파일이 섞일 수 있기 때문이다.
- 아래 경우에는 리뷰를 건너뛰고 바로 푸시한다. 건너뛴 사실과 이유는 한 줄로 밝힌다.
  - origin이 hd-cloud-wiki이고, 이 브랜치에 열린 PR이 없어 푸시 뒤 `### 1. PR 제안 시점`에서 PR을 새로 만들 때. 판정은 `### 8. PR 생성 후 리뷰 봇 루프 (hd-cloud-wiki 한정)`의 origin 판정을 그대로 쓰고, 열린 PR 여부는 `gh pr list --head <브랜치>`로 확인한다. 이때는 PR 생성 전에 위키 저장소 `create-pr`의 사전 게이트(코드는 `code-review-harness`, 문서는 `wiki-review-harness`)를 거치고 PR 뒤에는 리뷰 봇 루프가 돌아, 이 루프까지 돌리면 같은 변경을 세 번 리뷰하게 된다. 그 게이트는 `gh pr create` 직전에만 돌므로, 이미 열린 PR에 푸시할 때나 PR 조회에 실패했을 때는 건너뛰지 않고 루프를 돌린다. 건너뛰고 푸시했는데 사용자가 PR 생성을 거절하면 게이트도 돌지 않으므로, 이번 푸시는 로컬 리뷰 없이 올라갔다는 사실을 한 줄로 알린다.
  - 현재 브랜치가 통합 브랜치 자체일 때. 단 `main으로 바로 커밋 & 푸시`는 base가 `origin/main`이므로 이 조건을 적용하지 않는다.
  - base보다 앞선 커밋이 없을 때
  - base를 확정할 수 없을 때. 작업 브랜치에서 다시 분기된 브랜치도 여기에 해당한다. `main으로 바로 커밋 & 푸시`는 base가 정해져 있으므로 이 조건을 적용하지 않는다.
  - `it-plugin`이 설치되지 않아 `it-plugin:self-review-fix-loop`를 호출할 수 없을 때. 단 `main으로 바로 커밋 & 푸시`는 PR 리뷰도 거치지 않으므로 바로 푸시하지 않고, 리뷰 없이 푸시할지 선택지로 묻는다.
- 결과는 루프 최종 출력의 종료 사유와 `잔존 블로킹 이슈`, `수정 불가 이슈` 두 섹션으로 판정한다. 루프 출력은 종료 사유를 코드명이 아니라 문구로 적으므로, 아래 코드명은 `it-plugin:self-review-fix-loop`의 최종 출력 절(Step 3-1)에 있는 코드와 문구의 대응표로 읽는다. 이 스킬에 그 표를 옮겨 적지 않는다. Critical과 Warning 건수를 세지 않는다. 루프가 수정 불가로 넘긴 이슈는 건수에서 빠지므로 `모든 Critical/Warning 해결`로 끝나도 남은 이슈가 있을 수 있기 때문이다.
  - 종료 사유가 `all-blocking-resolved`, `no-progress-twice`, `max-rounds`, `only-unfixable-left` 중 하나면 먼저 아래 `루프 수정분 커밋`을 거친다.
  - 그 뒤 두 섹션이 모두 없으면 그대로 푸시한다. 단 `main으로 바로 커밋 & 푸시`에서 루프 수정분을 커밋했으면 `루프 수정분 커밋`의 예외대로 푸시 전에 먼저 묻는다.
  - 어느 한 섹션이라도 있으면 그 목록을 보여주고 선택지로 `수정 후 재커밋`과 `그대로 푸시`를 묻는다. 자동으로 푸시하지 않는다. 루프가 못 고친 이슈를 이 스킬이 묻지 않고 대신 고치지도 않는다. `main으로 바로 커밋 & 푸시`에서 루프 수정분을 커밋했으면 이 질문이 `루프 수정분 커밋`의 `푸시` 확인을 겸하므로, 수정분 diff를 목록과 함께 보여주고 `푸시`를 따로 다시 묻지 않는다. 한 푸시 절차에서 확인은 한 번이다.
  - `수정 후 재커밋`을 고르면 수정한 뒤 이 스킬의 커밋 절차로 돌아간다. 이때 다시 `커밋 & 푸시`나 `main으로 바로 커밋 & 푸시`를 고르면 같은 푸시 절차가 이어지는 것으로 보고, 루프를 처음부터 다시 돌리지 않고 아래 `재리뷰`를 따른다. 후자는 fetch와 fast-forward 확인부터 다시 수행한다.
  - 종료 사유가 `self-review-failed`, `build-failed`, `trust-boundary-test-failed`, `instrument-regression`, `result-unreadable`, `coverage-dropped` 중 하나면 비정상 종료다. 루프 출력의 종료 사유 줄을 그대로 보여주고, 리뷰 없이 푸시할지 선택지로 묻는다. 루프 수정분은 커밋하지 않는다. 빌드나 테스트를 깨뜨렸거나 재리뷰를 받지 못한 수정이기 때문이다. 그래서 푸시해도 이미 만든 커밋만 올라가고 루프가 고친 변경은 working tree에 그대로 남는다는 사실을 `git status --short`와 함께 밝힌다.
  - `no-changes`는 건너뛰는 조건의 `base보다 앞선 커밋이 없을 때`에서 걸러지므로 나오지 않아야 한다. 나오면 base가 잘못됐을 수 있으므로 비정상 종료와 같이 처리한다.
- 루프 수정분 커밋은 루프가 working tree에 남긴 변경을 푸시 전에 커밋하는 단계다.
  - 루프가 끝난 뒤 `git status --porcelain --untracked-files=no`가 비어 있으면 고친 변경이 없는 것이므로 이 단계를 건너뛴다.
  - 변경이 있으면 `git status --short`와 `git diff`로 수정분을 보여주고, `커밋 메시지 작성 지침`대로 초안을 제시한 뒤 커밋한다. 본문에는 루프가 어떤 지적을 반영했는지 쓴다.
  - 커밋 여부는 다시 묻지 않는다. 앞서 받은 `커밋 & 푸시`나 `main으로 바로 커밋 & 푸시` 승인을 이 커밋의 승인으로 간주하며, `### 커밋 제안 시점`의 승인 후 커밋 규칙의 예외다. 그 선택지 설명이 루프가 직접 고쳐 별도 커밋으로 남긴다고 미리 알리므로, `### 8. PR 생성 후 리뷰 봇 루프 (hd-cloud-wiki 한정)`가 예고와 함께 받은 PR 생성 승인을 루프 실행 승인으로 보는 것과 같은 근거다.
  - 단 `main으로 바로 커밋 & 푸시`는 PR 리뷰도 거치지 않아 루프가 고친 내용을 아무도 보지 않은 채 `main`에 들어간다. 그래서 커밋은 위대로 하되 푸시 전에 수정분 diff를 보여주고 선택지로 `푸시`와 `푸시 중단`을 묻는다. `푸시 중단`은 `재리뷰`의 한 푸시 절차가 끝나는 경우와 같다. 같은 푸시 절차에서 이미 `푸시`를 승인했으면 6단계 rebase 뒤 2단계부터 다시 수행할 때나 7단계에서 `커밋 & 푸시` 경로로 바꿀 때 다시 묻지 않는다. 4단계의 `모두 푸시` 승인을 rebase 뒤에 다시 묻지 않는 것과 같다. 충돌을 해소했거나 재리뷰 루프가 새 수정분을 커밋해 승인한 내용과 달라졌을 때만 다시 묻는다.
  - 직전 커밋에 amend하지 않고 별도 커밋으로 쌓는다. amend하면 기록한 리뷰 HEAD가 현재 HEAD의 조상이 아니게 되어 아래 `재리뷰`가 반영 커밋만 골라낼 수 없고 첫 리뷰의 base로 다시 리뷰해야 하기 때문이다. `main으로 바로 커밋 & 푸시`에서도 같다. 4단계가 이번 푸시 절차에서 만든 커밋을 모두 방금 만든 커밋으로 보므로 커밋이 늘어도 다시 묻지 않는다.
  - 커밋한 뒤 기록한 리뷰 HEAD를 이 커밋으로 바꾼다. 그래야 아래 `재리뷰`가 루프 수정분을 다시 보지 않고 그 뒤의 반영 커밋만 본다. `no-progress-twice`나 `max-rounds`로 끝났으면 마지막 라운드의 수정분은 재리뷰를 받지 못했지만, 그 경우 `잔존 블로킹 이슈`가 남아 사용자가 목록과 diff를 보고 판단하므로 따로 리뷰하지 않는다.
- 재리뷰는 한 푸시 절차에서 1회까지다. 루프 안의 라운드는 세지 않고 루프 호출 1번을 1회로 센다. 예전에는 재커밋할 때마다 브랜치 전체를 처음부터 다시 리뷰해 `r2`, `r3` 라운드가 쌓였고, 지적을 반영한 몇 줄을 보려고 이미 본 변경까지 매번 다시 읽었다.
  - 범위는 지적을 반영한 커밋뿐이다. 직전에 기록한 리뷰 HEAD를 base로 루프에 `--scope branch <리뷰한 HEAD SHA>`를 넘긴다. 재리뷰 루프가 고친 변경도 위 `루프 수정분 커밋`대로 커밋한다.
  - rebase나 amend로 직전 리뷰 HEAD가 현재 HEAD의 조상이 아니게 되면(`git merge-base --is-ancestor <리뷰한 HEAD> HEAD` 실패) 반영 커밋만 골라낼 수 없으므로 첫 리뷰의 base로 다시 리뷰한다. 이 경우도 재리뷰 1회로 센다.
  - 반영 커밋에 새 파일이 있으면(`git diff --diff-filter=A --name-only <리뷰한 HEAD> HEAD` 결과가 있으면) 첫 리뷰의 base로 다시 리뷰한다. 새 파일은 첫 리뷰에서 본 적이 없어 지적에 대한 응답으로만 볼 수 없고, 반영분만 보면 기존 변경과 어떻게 맞물리는지가 diff에 드러나지 않기 때문이다. 이 경우도 재리뷰 1회로 센다.
  - `git diff <리뷰한 HEAD> HEAD`가 로직을 바꾸지 않으면 재리뷰를 건너뛰고 그 사실을 한 줄로 밝힌다. 주석, 의미가 같은 문구 다듬기, 포맷, 참조까지 함께 바꾼 이름 변경이 여기에 해당한다. 조건, 분기, 수치, 호출 관계나 규칙 문장의 의미를 바꿨으면 로직 변경으로 본다. 애매하면 로직 변경으로 본다.
  - 한 푸시 절차는 첫 루프를 부른 때부터 푸시를 마치거나, `푸시 중단`을 고르거나, 재커밋 때 `커밋`만 고를 때까지다. 선택지 없이 멈추는 경로(`main으로 바로 커밋 & 푸시`의 2단계와 7단계에서 묻지 않고 멈출 때, 루프 비정상 종료 뒤 리뷰 없는 푸시를 거절했을 때)처럼 푸시하지 않고 끝나는 경우도 같다. 이 중 하나가 일어나면 기록한 리뷰 HEAD와 재리뷰 횟수를 버리고, 다음 푸시는 첫 리뷰부터 다시 시작한다.
  - 재커밋 때 푸시 경로를 바꾸면(`커밋 & 푸시`와 `main으로 바로 커밋 & 푸시` 사이) 위 항목들의 "첫 리뷰의 base"는 새로 고른 경로의 base로 본다. 리뷰를 마친 뒤 7단계에서 `커밋 & 푸시` 경로로 바꿀 때는 커밋이 그대로이므로 리뷰를 다시 돌리지 않는다.
  - `main으로 바로 커밋 & 푸시`의 6단계 rebase는 지적 반영이 아니므로 재리뷰로 세지 않는다. 첫 리뷰 전에 rebase했으면 rebase한 HEAD로 첫 리뷰를 돈다. 리뷰를 마친 뒤 rebase했으면, 충돌 없이 끝났을 때는 내 커밋의 변경이 그대로이므로 리뷰한 부분을 다시 보지 않는다. 기록한 리뷰 HEAD는 rebase한 HEAD가 아니라 직전에 리뷰한 커밋이 rebase된 뒤의 대응 커밋으로 바꾼다(리뷰한 HEAD 뒤에 반영 커밋이 n개 있었으면 `HEAD~n`). rebase한 HEAD로 바꾸면 그 사이에 쌓인 반영 커밋이 재리뷰 범위에서 빠지기 때문이다. 반영 커밋이 있으면 그 커밋만 위 규칙대로 재리뷰한다. 충돌을 해소했으면 해소한 내용을 아무도 보지 않았으므로 첫 리뷰의 base로 다시 리뷰하고 재리뷰 1회로 센다. 재리뷰를 이미 1회 쓴 뒤라면 다시 돌리지 않고 아래 항목처럼 리뷰 없이 푸시할지 선택지로 묻는다.
  - 재리뷰를 이미 1회 돌린 뒤 다시 `수정 후 재커밋`으로 돌아오면 리뷰 없이 푸시하고, 마지막 반영분은 리뷰하지 않았다는 사실을 한 줄로 밝힌다. 단 `main으로 바로 커밋 & 푸시`는 PR 리뷰도 거치지 않으므로 바로 푸시하지 않고, 리뷰 없이 푸시할지 선택지로 묻는다.
- 루프와 self-review는 결과 파일(`r*.result.json`, `instrument.json`, `applied-fixes.json`, `r*.diff` 등)을 `.claude/tmp/self-review/` 아래에 쓴다. 저장소 `.gitignore`에 `.claude/tmp`가 없을 수 있으므로 이 파일들은 스테이징하지 않는다. `루프 수정분 커밋`에서도 같다.

## PR 작성 지침

사용자가 PR 작성을 요청하거나 제안 시점 규칙에 따라 PR 생성 여부를 물을 때, 아래 규칙을 우선 적용하여 PR 제목과 본문을 한국어로 간결하게 작성한다.

### 1. PR 제안 시점

- 푸시를 마치면 아래 순서로 판정하고, 위에서 걸리면 아래는 보지 않는다.
  1. `main으로 바로 커밋 & 푸시`로 원격 `main`에 올렸으면 묻지 않는다.
  2. `gh`가 원격을 GitHub 저장소로 인식하지 못하면 묻지 않는다.
  3. 현재 브랜치가 통합 브랜치 자체이면 묻지 않는다.
  4. 이미 열린 PR이 있으면 새로 만들지 않고 푸시로 갱신되었다는 사실만 알린다.
  5. 통합 브랜치에서 분기된 작업 브랜치이면 PR 제목과 본문 초안을 제시하고 선택지로 생성 여부를 묻는다. 화면이 바뀌는 변경이면 아래 `AS-IS와 TO-BE 증빙`대로 PR을 만들지 먼저 묻고, 만든다고 하면 증빙을 남긴 뒤 초안을 제시한다. hd-cloud-wiki PR이면 `### 8. PR 생성 후 리뷰 봇 루프 (hd-cloud-wiki 한정)`의 예고를 초안과 함께 제시하고, `gh pr create` 전에 위키 저장소 `create-pr` 스킬의 §6.1 코드 변경 PR 사전 게이트와 §6.1.2 문서 변경 PR 사전 게이트를 거친다. `### 푸시 전 self-review-fix-loop`가 이 저장소를 건너뛰는 근거가 이 게이트이므로 생략하지 않는다.
     - 게이트의 리뷰는 `Skill` 도구로 직접 부른다. `.md`가 아닌 파일을 바꿨으면 `code-review-harness`를, `.md`를 바꿨으면 `wiki-review-harness`를 부르고, 둘 다 바꿨으면 둘 다 부른다. 면제 판정(간단 작업, 간단 문서 변경), 검증 명령 실행, §6.1 ③ 사용자 동작 테스트, 기록 파일(`pr-verify-ok`, `pr-docs-review-ok`) 작성은 위키 `create-pr`의 해당 절대로 한다. 하네스에 넘기는 base는 이 절의 통합 브랜치 판정으로 정한 PR base다(위키 `create-pr`의 `BASE_OVERRIDE`에 해당). `gh pr create` 직전에는 위키 `create-pr` §6.2 최종 검증 스크립트를 실행해 기록 파일이 현재 HEAD와 맞는지 대조하고, 실패하면 PR을 만들지 않는다.
     - 위키 `create-pr` 스킬 자체는 호출하지 않는다. 그 스킬은 브랜치 검증부터 `gh pr create`까지 PR 생성 전체를 실행해 이 스킬의 PR 생성과 겹친다. PR 생성은 이 스킬이 맡고, 게이트 결과는 본문 `테스트 방법` 끝에 적는다.
  6. base를 확정할 수 없으면 임의로 정하지 않고 base를 되묻는다.
- 통합 브랜치 후보는 이름을 하드코딩하지 않고 `origin/HEAD`가 가리키는 브랜치와 원격에 실제로 존재하는 `develop`, `master`에서 찾는다.
- 후보 중 `git merge-base --is-ancestor <후보> HEAD`를 만족하는 것을 base로 삼고, 여럿이면 merge-base가 가장 최근인 것을 고른다. `develop`과 `main`이 모두 조상이면 `develop`을 고른다.
- 작업 브랜치에서 다시 분기된 브랜치는 base 판정을 사람에게 맡긴다. 상위 작업 브랜치와 통합 브랜치 중 무엇을 대상으로 할지 추정하지 않는다.
- 열린 PR 여부는 생성 직전에 `gh pr list --head <브랜치>`로 다시 확인한다. 훅이 주입하는 PR 상태는 PR이 없는 경우와 조회에 실패한 경우를 구분하지 않아, 그 값만 믿으면 중복 PR이 생길 수 있다.
- base보다 앞선 커밋이 없으면 묻지 않는다.
- PR 제목과 본문은 아래 규칙에 따라 작성한 초안을 그대로 제시한 뒤 생성한다. 사용자가 승인하지 않으면 생성하지 않는다.

#### AS-IS와 TO-BE 증빙

- 화면이 바뀌는 변경이면 녹화를 시작하기 전에 PR을 만들지 선택지로 먼저 묻는다. 선택지는 `증빙 남기고 PR 초안 작성`, `증빙 없이 PR 초안 작성`, `PR 만들지 않음`이다. 녹화는 코드를 base로 잠시 되돌리고 ego 창을 앞으로 가져오므로, PR을 만들지 않을 때 이런 부수효과가 생기지 않게 하려는 것이다. 이 답은 녹화 시작 승인이고, 초안 승인은 기존대로 따로 받는다.
- `증빙 남기고 PR 초안 작성`을 고르면 PR 초안을 만들기 전에 `Skill` 도구로 `chucoding:screen-evidence`를 호출해 증빙을 남긴다. 동작이 필요하면 GIF, 화면만 보면 되면 이미지로 하고, AS-IS는 작업 종류(기존 기능 수정, 신규 기능, 레거시 이관, 벤치마킹)에 따라 출처를 정하거나 생략한다. 판단 기준과 보관, PR 첨부 방법은 그 스킬을 따른다.
- 증빙은 PR을 만들 때 함께 넣는다. 리뷰어가 첫 리뷰부터 변경 전후를 보게 하려는 것이므로, PR을 먼저 만들고 나중에 붙이지 않는다. 초안 본문의 테스트 섹션에 증빙 블록을 넣고, 승인을 받으면 `gh pr create --attach`로 생성한다. `gh pr edit --attach`는 리뷰 반영으로 화면이 바뀌어 TO-BE를 다시 남겼을 때와, 사용자가 이미 열린 PR에 증빙을 넣어 달라고 직접 요청했을 때만 쓴다. 후자는 `chucoding:screen-evidence`의 예외 절차를 따른다.
- 테스트 섹션의 증빙 블록과 사전 게이트 결과 밖 항목에는 실제로 실행한 테스트만 쓴다.
- 화면 변화가 없는 변경이나 개발 서버를 띄울 수 없는 저장소처럼 `chucoding:screen-evidence`의 건너뛰는 조건에 해당하면 남기지 않고, 초안을 제시할 때 건너뛴 사실과 이유를 한 줄로 밝힌다.

### 2. 작업 내역 확인

- 현재 브랜치와 원격 저장소의 기본 브랜치를 확인한다.
- 원격 저장소의 기본 브랜치를 확인할 수 없으면 임의로 추정하지 않고 사용자에게 확인한다.
- 기본 브랜치와 현재 브랜치의 병합 기준점부터 `HEAD`까지 커밋과 변경 내용을 분석한다.
- 공통 원칙에 따른 의도 자료와 실제 변경 내용을 함께 기준으로 작성한다.
- 추측하거나 확인되지 않은 변경 사항을 작성하지 않는다.

### 3. PR 제목

- 현재 브랜치명에서 이슈 번호를 추출한다.
- 이슈 번호를 찾을 수 없으면 `NO-ISSUE`를 사용한다.
- 실제 변경 내용을 분석하여 가장 적합한 유형 하나를 선택한다.
- 유형은 `feat`, `fix`, `refactor`, `docs`, `test`, `chore`, `perf`, `build`, `ci`, `style`, `revert` 중 하나만 사용한다.
- 제목은 `유형(이슈 번호): 제목` 형식으로 작성한다.

### 4. PR 본문

- 본문 형식은 IT부문 표준(it-governance-hub의 [부문 공통 엔지니어링 표준 §4-2](https://github.com/dev-rsquare/it-governance-hub/blob/main/bundles/engineering/common-standards.md) `PR 최소 항목`, [워크플로우 7단계](https://github.com/dev-rsquare/it-governance-hub/blob/main/bundles/workflow/steps/S7-merge.md) 규칙 3)을 따른다. 스쿼시 머지에서 PR 제목과 본문이 그대로 본선 커밋 메시지가 되기 때문에 부문이 형식을 정해 두었다.
- 저장소에 PR 템플릿이 있으면 해당 구조와 섹션 순서를 유지하고, 템플릿의 HTML 주석은 지운다. 부문 공용 템플릿(it-ci-gates)은 아래 3항목과 같고, CI가 주석을 지운 뒤 3항목을 검사한다. 3항목과 다른 템플릿이면 아래 3항목의 내용을 템플릿의 가까운 섹션에 옮겨 담는다(목적과 결정 섹션에는 변경 이유를, 테스트 섹션에는 테스트 방법을, 링크나 참고 섹션에는 관련 티켓을). 맞는 섹션이 없는 내용은 버리지 않고 변경 이유에 붙인다.
- 템플릿이 없으면 `## 관련 티켓`, `## 변경 이유`, `## 테스트 방법` 3항목으로 쓴다.
- 관련 티켓에는 티켓 링크를 한 줄로 적는다. 원 작업 티켓이나 이 일이 제기된 PR, Notion과 Figma 같은 관련 문서 링크가 있으면 같은 줄이나 바로 아래에 붙인다. GitHub 이슈로 착수한 작업이면 `chucoding:github-issue`대로 이슈를 `(#번호)`로 적는다. 티켓도 이슈도 없으면 `NO-ISSUE`라고 적는다.
- 변경 이유에는 공통 원칙의 Why를 적는다. 변경 전 문제와 근거, 바꾼 것(동작 단위), 일부러 바꾸지 않은 것과 그 이유를 적고, 배제한 대안이 판단을 바꿨으면 함께 적는다. diff에서 보이는 파일별 변경 목록은 적지 않는다.
- 테스트 방법에는 실제로 실행한 테스트와 결과를 실행한 순서대로 적는다. 명령, 건수, 통과 여부까지 적고, 변경과 무관한 실패도 숨기지 않는다. 실행 기록이 없으면 `- 미실행`과 사유를 적는다. `#### AS-IS와 TO-BE 증빙`으로 만든 블록과 사전 게이트 결과(hd-cloud-wiki의 리뷰 하네스 기록 등)도 이 항목 끝에 둔다.

### 5. Assignee와 라벨

- PR을 생성할 때 Assignee를 지정한다. 기본값은 현재 `gh` 인증 계정이다. `gh pr create --assignee @me`로 지정하고, 사용자가 다른 담당자를 지정하면 그 값을 따른다.
- 리뷰어는 Assignee와 별개다. 사용자가 리뷰어를 지정하지 않으면 `--reviewer`를 임의로 채우지 않는다.
- 라벨은 붙이지 않는다. `gh pr create`에 `--label`을 쓰지 않고, 연 뒤에도 손으로 붙이거나 떼지 않는다. 변경 유형은 PR 제목의 타입에 이미 있고, 라벨이 필요한 저장소는 워크플로가 PR을 열 때 붙인다(예: 허브와 어드민의 `auto-assign.yml`, 팀 파트 라벨). 사용자가 라벨을 직접 지정하면 그 값만 붙인다.
- Assignee는 제목과 본문 초안과 함께 제시해 같은 승인으로 처리한다. 생성 여부를 승인받은 뒤 따로 다시 묻지 않는다.
- 생성 직후 `gh pr view --json assignees`로 실제 반영을 확인한다. 도구 성공 메시지로 대신하지 않는다.
- 지정에 실패하면 PR 링크와 함께 Assignee가 비었다는 사실과 수동 지정이 필요하다는 점을 밝힌다.
- 이미 열린 PR이 푸시로 갱신되기만 한 경우에는 Assignee를 바꾸지 않는다.

### 6. 출력 형식

- 존댓말보다는 제목을 작성하듯이 본문도 간결하게 요지만 작성한다.
- 마크다운으로 출력하여 사용자가 GitHub PR 본문에 붙여넣기 쉽게 한다.
- 승인을 받아 `gh`로 직접 생성하는 경우에는 붙여넣기용 출력 대신 생성된 PR 링크를 알린다.
- PR 제목 예시를 반드시 제시하며, 위 규칙에 따라 선택한 유형과 현재 브랜치에서 추출한 이슈 번호를 포함한다. 이슈 번호가 없으면 `NO-ISSUE`를 사용한다.
- 본문은 마크다운 코드 블록(```markdown ... ```)으로 감싸서 복사하기 편하게 한다. 만약 본문에 코드블럭이 필요한 경우에는 (```)문법 대신 (`)문법을 사용한다.
- 본문에 증빙 블록이 있으면 초안의 `./<키>-to-be.gif` 같은 상대경로가 `--attach`로 생성할 때 업로드 주소로 바뀐다는 점을 함께 알린다.

### 7. PR 생성 후 티켓 상태 전환

- PR 생성이 성공하면 연결된 Jira 티켓 상태를 `리뷰중`으로 전환한다.
- 이 전환은 PR 생성 승인에 포함된 후속 동작으로 본다. 상태 전환 여부를 다시 묻지 않는다.
- 대상 티켓 키는 현재 브랜치명에서, 없으면 PR 제목의 이슈 번호에서 찾는다. 티켓 키를 찾을 수 없거나 `NO-ISSUE`이면 전환하지 않고 그 사실만 알린다. 찾은 키가 HOM이면 HOM에서 전환을 찾지 않고 `chucoding:jira`의 `상태 전환` 규칙에 따라 연결된 HDIT를 대상으로 삼는다. 대상 HDIT의 이슈 유형(`GET /rest/api/3/issue/<키>?fields=issuetype`의 `issuetype.name`)이 `QA_Bug`이면 `리뷰중` 상태가 없는 워크플로이므로 전환을 찾지 않고 그 사실만 알린다.
- 전환 전에 위에서 정한 대상 티켓에서 사용 가능한 전환 목록을 조회한다. `리뷰중`에 해당하는 전환이 없으면 비슷한 상태로 임의 전환하지 않고 사용자에게 알린 뒤 지시를 기다린다.
- 티켓이 이미 `리뷰중`이거나 그보다 진행된 상태면 다시 전환하지 않는다.
- Cloners로 연결된 HDIT 클론 티켓이 있으면 같은 상태로 함께 전환한다. HOM 원본은 함께 전환하지 않는다. HOM 워크플로에는 `리뷰중`이 없기 때문이다.
- 아래 경우에는 전환하지 않는다.
  - PR 초안만 제시하고 실제 생성은 하지 않았을 때
  - PR 생성이 실패했을 때
  - 이미 열린 PR이 푸시로 갱신되기만 했을 때
  - 사용자가 상태를 직접 관리하겠다고 밝혔을 때
- 전환을 마치면 티켓 키와 바뀐 상태를 PR 링크와 함께 알린다. 전환에 실패하면 실패 사유와 함께 수동 전환이 필요하다는 점을 알린다.

### 8. PR 생성 후 리뷰 봇 루프 (hd-cloud-wiki 한정)

- PR 생성이 성공했고 origin이 hd-cloud-wiki이면, 묻지 않고 `Skill` 도구로 `it-plugin:counter-review-loop`를 PR 번호 인자로 호출한다. `### 7. PR 생성 후 티켓 상태 전환`을 마친 뒤에 호출한다. 7절이 전환하지 않고 알리기만 하고 끝났으면 바로 호출하고, 지시를 기다리는 상태로 끝났으면 사용자의 응답을 처리한 뒤에 호출한다.
- hd-cloud-wiki 판정 근거는 `git remote get-url origin`뿐이다. 세션의 작업 디렉터리, 워크스페이스 이름, `--add-dir`로 열린 위키는 근거가 아니다.
  - 호스트는 `### 커밋 제안 시점`의 개인 저장소 판정처럼 `github.com`이거나 `github-`로 시작하는 SSH 별칭이어야 한다.
  - 경로의 소유자와 저장소 이름(`.git` 접미사 제외)이 `dev-rsquare/hd-cloud-wiki`이거나, 이관 전 주소인 `rabyss/homedot-wiki`이면 hd-cloud-wiki로 본다. 이관 전 주소로 클론한 체크아웃은 리다이렉트로 같은 저장소를 가리키기 때문이다.
  - `dev-rsquare/homedot-wiki`는 기획팀 위키라는 별개 저장소이므로 대상이 아니다. 저장소 이름만으로 판정하지 않는 이유다.
- hd-cloud-wiki로 판정되면 `### 1. PR 제안 시점`에서 초안을 제시할 때, 생성 직후 이 루프가 봇 리뷰를 기다려 반영하고 그 과정에서 PR 브랜치에 커밋과 푸시, 반박 답글, 스레드 resolve, 미룬 지적의 이슈 생성을 한다는 사실과 라운드마다 봇 리뷰를 최대 30분씩 최대 3라운드 기다린다는 사실을 한 줄로 함께 알린다. 사용자가 이 예고를 보고 루프를 빼달라고 할 수 있게 하려는 것이다.
- 이 루프 안에서 `it-plugin:counter-review`가 하는 커밋과 푸시는 `### 커밋 제안 시점`의 승인 후 커밋 규칙과 `### 푸시 전 self-review-fix-loop`의 예외로 본다. 위 예고와 함께 받은 PR 생성 승인을 루프 실행 승인으로 간주한다.
- 루프가 어떤 종료 보고로 끝나든(수렴, 라운드 초과, 수렴 가드, 부분 리뷰, 대기 타임아웃, FIX 0건, PR 머지나 클로즈 등) 그 보고를 그대로 전달하고 멈춘다. 결정 요망 항목이 있으면 사용자의 지시를 기다리고, 고른 선택지는 루프 재호출처럼 그 보고 문구대로 처리한다.
- 종료 보고의 누적 REBUT이 1건 이상이면 보고 뒤에 반박 건수와 반박 답글을 확인할 PR 링크, 위키 리뷰 하네스 §4.1에 따라 반박 근거를 도구나 문서에 굳혀야 한다는 사실을 덧붙인다. 루프는 반박을 답글로만 남겨 다음 리뷰가 같은 지적을 다시 올릴 수 있기 때문이다. 근거를 굳히는 작업은 자동으로 시작하지 않는다. 누적 줄이 없는 중단 보고(`❌ 중단`)에는 덧붙이지 않는다. 그 보고가 이미 남은 커밋과 댓글을 PR에서 확인하라고 알리기 때문이다.
- `it-plugin`이 설치되지 않았거나 `Skill` 호출 자체가 거부되어 루프가 시작되지 못하면, 사유와 PR 링크, 수동 실행 명령(`/it-plugin:counter-review-loop <PR 번호>`)을 알린다. 루프가 시작된 뒤 스스로 중단 보고를 내면 이미 커밋이나 댓글이 남았을 수 있으므로 이 항목이 아니라 위의 종료 보고 전달을 따른다.
- 이 루프는 PR 생성 직후의 봇 리뷰 수렴만 맡는다. 루프가 멈춘 뒤의 리뷰 대응과 사람 리뷰 대응은 위키 저장소의 `review-pr` 스킬을 따른다. 루프가 도는 동안은 `review-pr` §4.2.1의 라운드마다 답하지 않는다는 가드의 예외로 보는데, 루프가 최대 3라운드에서 멈춰 그 가드가 막으려는 끝없는 핑퐁이 생기지 않기 때문이다.
- 아래 경우에는 호출하지 않는다.
  - PR 초안만 제시하고 실제 생성은 하지 않았을 때
  - PR 생성이 실패했을 때
  - 이미 열린 PR이 푸시로 갱신되기만 했을 때
  - `main으로 바로 커밋 & 푸시`로 PR 없이 올렸을 때
  - 사용자가 이번 PR은 루프를 돌리지 않겠다고 밝혔을 때
