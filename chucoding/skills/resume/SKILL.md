# 이력서와 포트폴리오

사용자는 채용담당자와 면접관이 이 문서를 **AI가 쓴 문서나 번역 문서처럼** 읽는 것을 가장 경계한다. 그리고 면접에서 한 문장이라도 사실과 다르게 드러나는 것을 경계한다. 이 스킬의 규칙은 모두 이 두 가지에서 나왔다. 지난 지원에서 사용자가 하나씩 지적한 것을 다음 지원에서 다시 지적하지 않게 하는 것이 목적이다.

문장 기준과 사례는 `references/wording.md`, PDF 제작과 검증은 `references/render.md`에 있다. 문장을 쓰거나 고치기 전에 `references/wording.md`를 먼저 읽는다.

## 0. 요청 종류

| 요청 | 할 일 |
|------|------|
| 새 공고에 지원서 작성 | 1~5절을 차례로 하고 8~9절로 반영과 보고. 문장을 고칠 때마다 6절 확인 절차를 거친다 |
| 문장이나 구성 지적 ("이 문장 어색해", "이거 왜 넣었어?") | 6절 확인 절차로 한 건씩 |
| 합격 가능성 분석, 보강할 점 검토 | 7절 형식으로 보고만 하고 파일은 고치지 않음 |

## 1. 공고와 기준본

- 공고 URL을 열어 **지금도 열려 있는지** 확인하고 확인한 날짜를 적는다. 공고 본문을 사용자가 붙여 넣었으면 그 본문을 기준으로 삼는다.
- 공고에 영역이나 트랙이 여럿이면 어느 쪽에 지원하는지 정하고, 그 영역의 자격요건과 우대사항만 대조한다.
- 경력 연수는 사용자가 말한 값과 경력 기간 배지를 맞춘다. 직무 경력과 전체 경력이 다르면 면접에서 어떻게 답할지도 초안 문서에 적어 둔다.
- **기준본은 사용자에게 제출할 PDF다.** 이전 초안 문서(md)의 문장은 PDF를 만들기 전 작업본이라 PDF와 다르다. 보강할 때 초안 문장을 다시 가져오지 않고, PDF에 지금 찍힌 문장만 기준으로 삼는다.
- **PDF를 만드는 원본은 HTML 하나다.** 위치는 `~/Desktop/<이름>_<회사>_원본HTML/`(`resume.html`, `portfolio.html`, `common.css`)다. 사용자가 "원본은 없다"고 해도 먼저 바탕화면과 최근 파일을 찾아본다. 지난 지원에서 원본이 있었는데 없다고 알고 PDF를 직접 고쳐, 화면에 안 보이는 옛 내용이 텍스트 레이어에 남았다.
- PDF를 직접 고치지 않는다. 고칠 때는 원본 HTML을 고치고 PDF를 다시 뽑는다.
- 바탕화면에는 **PDF 한 벌과 원본 폴더만** 둔다. `_v3`처럼 버전 접미사를 붙인 사본을 바탕화면에 만들지 않는다. 사용자가 어느 파일이 최종인지 헷갈린다. 시험본과 백업은 스크래치패드에 둔다.

## 2. 근거 수집

- **숫자는 데이터에서만, 서술은 근거 자료에서만 가져온다.** 근거는 `chucoding:sprint-retro`의 회고 문서, PR 본문, Jira 티켓, 저장소 git 기록, 위키 문서다. 근거가 없으면 쓰지 않는다.
- **사용자의 기억도 확인한다.** 사용자가 "그거 내가 없앴다", "동료 1명과 만들었다"고 해도 코드와 git 기록으로 확인한다. 기억과 다르면 근거와 함께 알린다. 지난 지원에서 사용자가 지웠다고 기억한 타입이 원격 main에 남아 있었고, 함께 만든 인원도 git 기록을 보니 훨씬 많았다.
- **기여 범위는 git 기록으로 센다.** 디렉터리별 `git log --format='%an' -- <경로> | sort | uniq -c`로 참여 인원을 보고, 사용자가 맡은 컴포넌트나 모듈은 커밋 작성자로 확인한다. 저장소가 분리되거나 합쳐졌으면 분리 전 저장소의 기록도 본다.
- 숫자마다 **무엇과 비교한 값인지** 확인한다. 본인 초기 구현과 비교한 값을 기존 솔루션 대비처럼 쓰지 않는다. 전 값과 후 값의 측정 환경이 다르면(dev와 로컬) 다시 재거나 빼고, 다른 팀이 배포해서 나온 결과는 그 팀의 결과로 쓴다.
- 같은 대상을 세는 숫자가 자료마다 다르면(문서마다 세는 기준이 다른 양식 수 등) 정의를 먼저 정하고 하나만 쓴다.

## 3. 구성

지난 지원에서 사용자와 합의한 구성이다. 공고가 분량이나 양식을 따로 정하면 그것을 따른다.

**문서 나누기**
- 이력서 2쪽과 포트폴리오를 따로 낸다. 서류 검토자는 첫 쪽을 몇 초에서 15초 안에 훑는다. 케이스 7개를 한 문서에 같은 무게로 펼치면 강한 케이스가 묻힌다.
- 이력서 1쪽은 한 줄 소개, 소개, 숫자 칸, 경력, 핵심 기술이다. 2쪽은 주요 성과(케이스마다 한두 줄), 그 외 프로젝트, 링크다.
- 포트폴리오는 공고에 가장 잘 맞는 케이스 4~6개만 남긴다. 나머지는 이력서 2쪽 한 줄로 둔다.

**1쪽**
- "요약" 대신 "소개"로 2~3문장. 내가 어떤 개발자인지 먼저 쓰고 지원 동기는 마지막 한 문장으로 붙인다.
- 핵심 강점 카드처럼 소개와 같은 말을 반복하는 상자를 두지 않는다. 1쪽 위쪽에 테두리 상자가 몰리면 답답해 보인다.
- 숫자 칸은 테두리 없이 숫자와 설명만 두고 가운데 정렬한다. 차트는 넣지 않는다.
- 연수는 "N년차" 대신 "경력 N년"으로 쓰고, 경력 칸에 전체와 회사별 기간 배지를 둔다. 회사 배지는 모두 같은 색으로 한다.
- 프로필 사진은 넣지 않는다. AI 느낌은 글과 구조에서 나오고 사진으로는 지워지지 않는다. AI 느낌을 줄이는 데는 실제 PR, 글, 발표 링크가 가장 효과가 크다.

**핵심 기술 칸**
- 분류마다 한 줄씩 세로 목록으로 쓴다. 칩 색은 하나로 통일한다.
- 적는 기준은 두 가지이고 둘 다 통과해야 한다. 이 공고가 보는 역량과 관련이 있는가, 질문을 받으면 5분은 답할 수 있는가.
- "그 외 사용 경험" 줄을 두지 않는다. 공고와 관계없는 기술은 면접 시간을 엉뚱한 곳으로 끌고 간다.
- 기술 이름과 분류 이름은 공고 표기를 따른다(예: "CI" 대신 공고가 쓴 "CI/CD"). 낯선 도구는 한 번 풀어 쓴다(예: "토큰 변환 도구(Style Dictionary)").

**경력과 주요 성과**
- 한 항목에 두 회사의 일을 섞지 않는다. 주요 성과가 한 회사 일이면 목록 위에 회사 이름을 붙인다.
- 끝난 작업에 "현재"를 쓰지 않는다. 만든 기간과 운영한 기간이 다르면 "구현 2025.08 – 2025.12, 운영 2026.01 – 현재"처럼 나눠 적는다.
- 회사 안에서만 쓰는 버전 규칙처럼 정석이 아닌 내용은 면접 질문을 부르므로, 넣을지 사용자에게 먼저 묻는다.

**포트폴리오 케이스**
- 모든 케이스를 같은 틀로 맞춘다. 제목 바로 아래 성과 한 줄, 그다음 문제, 판단, 역할, 기술, 어떻게 해결했는가, 아래 상자 하나.
- 성과는 케이스 제목 아래 한 줄로 강조하고, 문서 맨 위에 숫자 칸을 따로 두지 않는다. 숫자가 의미 없는 케이스는 숫자 없이 성과를 쓴다(예: "백엔드 개발자도 공통 컴포넌트로 화면 개발이 가능해짐").
- 제목은 "무엇 설계 및 구현"처럼 한 일로 짧게 쓰고, 이력서 주요 성과의 소제목과 똑같이 맞춘다. 설계만 쓰지 말고 구현까지 했으면 구현도 쓴다.
- "어떻게 해결했는가"에 성과 숫자를 다시 넣지 않는다. 성과는 제목 아래 한 곳에만 둔다.
- 아래 상자 주제는 공고가 묻는 질문에 맞춘다. "받아들인 대가"처럼 문서마다 쓰던 제목을 기계적으로 쓰지 않고, 그 케이스에서 면접관이 궁금해할 것(예: "동료의 작업 방식은 어떻게 달라졌나")을 고른다. 빼낸 trade-off는 면접 답변으로 초안 문서에 남긴다.

## 4. 기여 표기

- 역할 칸에는 **몇 명이 했는지와 그중 내 담당**만 쓴다. 다른 사람이 각자 무엇을 했는지는 쓰지 않는다.
- 다만 내 케이스에 적힌 결과를 다른 사람이 냈으면 반드시 밝힌다(예: "동료 1명은 브라우저 렌더링을, 저는 서버 렌더링을 만들었습니다", "다른 팀이 여러 저장소에 배포한 뒤").
- 직접 한 일과 **제안만 한 일**을 나눈다. 다른 팀이 구현했으면 "제안했고"까지만 쓴다.
- 독식하는 인상을 주지 않는다. "서비스는 제가 설계하고 구현했습니다" 대신 "5명이 함께 만든 서비스로, 저는 설계와 공통 기반을 맡았습니다"처럼 쓴다. "혼자 진행했습니다"는 쓰지 않는다.
- 내가 주도한 일은 빠뜨리지 않는다(예: "10명 넘는 동료가 컴포넌트를 나눠 맡아 함께 만드는 과정을 주도했고").

## 5. 무엇을 남기고 뺄지

사용자는 면접관 입장에서 의미가 없는 내용을 반복해서 뺐다. 문장을 넣을 때마다 "이 문장을 왜 넣었냐"는 질문에 답할 수 있어야 한다.

- **뺀 것**: 의미가 약한 숫자(PR 건수, 이관한 양식 수, 참여 인원 수), 면접관이 모르는 분류("세 가지 조판 방식"), 제목과 관계없는 곁가지 문장, 성과가 아닌 정리 작업 나열(삭제한 줄 수, 테스트 개수), 일회성 이관 작업, 효과 측정에 실패한 이야기.
- **남긴 것**: 공고 요건에 직접 답하는 판단, 전후 숫자가 있는 결과, 다른 직군 동료의 일하는 방식이 바뀐 이야기.
- 뺀 내용 중 면접에서 쓸 만한 것은 지원서 초안 문서에 면접 답변으로 남긴다(8절).
- 결과 숫자가 아직 없는 작업을 지원 직전에 급히 넣지 않는다. "대시보드를 만들었다" 수준의 문장은 전후 숫자가 있는 다른 케이스 사이에서 오히려 약해 보인다. 지원은 지금 서류로 하고 결과는 면접에서 쓰는 쪽을 권한다.

## 6. 고치기 전 확인

- **고치기 전에 무엇을 어떻게 바꿀지 먼저 보여 주고 승인받는다.** 여러 건이면 번호를 붙여 "현재 → 변경" 형식으로 보여 준다. 사용자가 번호별로 고른다.
- 줄 수가 바뀌는 변경은 스크래치패드 시험 사본으로 먼저 렌더해 몇 줄이 되는지, 쪽에 들어가는지 확인한 뒤 보여 준다.
- 사용자가 문구를 직접 주거나 "반영해줘", "진행해", "바꿔줘"라고 하면 바로 적용한다.
- 사용자가 "이거 왜 넣었어?"라고 물으면 넣은 이유와 뺄 때 잃는 것을 짧게 답하고, 의미가 약하면 빼자고 제안한다. 지시처럼 받아 바로 지우지 않는다.
- 사용자 지시에 사실과 다른 부분이 있으면 근거와 함께 한 번 밝히고 결정을 따른다(`chucoding:critical-reading`).
- 한 문서에서 고친 문장이 다른 문서에도 있으면(이력서와 포트폴리오에 같은 문장) 함께 고칠지 같은 확인 안에서 묻는다.

## 7. 합격 가능성 분석과 보강 제안

공고 대조나 보강 제안을 요청받으면 파일을 고치지 않고 아래 형식으로 보고한다.

1. **공고 요건 대조표**: 자격요건과 우대사항마다 근거 케이스와 판정(충족, 일부, 없음)
2. **강점**: 공고 문장과 케이스가 맞는 곳
3. **약점과 위험**: 서류에서 걸릴 빈칸, 기여 주체가 흐려질 수 있는 숫자, 성과가 특정 기간에 몰린 점
4. **보강 제안**: 효과가 큰 순서. 실제로 하지 않은 일은 쓰지 말라고 분명히 적는다. 회고에서 새로 생긴 근거만 더하고 이미 문서에 있는 성과를 다시 쓰지 않는다
5. **숫자 주의**: 비교 기준이나 측정 환경이 맞지 않는 숫자
6. 영역이나 트랙이 여럿이면 트랙 비교

확률은 근거 없이 퍼센트로 단정하지 않는다. 판단 근거와 함께 범위로 말한다. 사용자가 공고 용어(웹뷰, CSP 등)를 물으면 자기 경험과 어떻게 이어지는지까지 답한다.

## 8. 초안 문서와 PDF 반영

- 지원 건마다 원본 폴더 안에 `~/Desktop/<이름>_<회사>_원본HTML/지원서 초안.md`를 하나 두고 회차가 바뀌면 그 파일을 고친다. 바탕화면에 파일을 늘리지 않기 위해서다.
- 초안 문서는 이 스킬이 있는 공개 저장소(`job-match/docs/` 포함)에 두지 않는다. 사용자가 2026-11-16에 저장소의 초안을 모두 지우고 원본 폴더에 두기로 정했다.
- 초안 문서에는 공고 확인 날짜, 기준본 경로, 근거 자료, "PDF의 현재 문장 → 바꿀 문장" 형식의 변경, 면접 답변, 케이스별 참여 인원과 담당을 남긴다.
- PDF 반영은 `references/render.md` 절차를 따른다. 원본 HTML과 현재 PDF 백업, 한 곳만 바꾸는 치환, 렌더, 잘림과 숨은 텍스트와 링크 검증, 바탕화면 교체 순서다.
