# 문장 기준

이력서와 포트폴리오 문장을 쓰거나 고칠 때 따른다. 사례는 지난 지원에서 사용자가 실제로 지적하고 고친 문장이다. 같은 유형의 문장을 다시 쓰지 않는다.

## 1. 끝맺음

- **본인이 한 일로 끝낸다.** "~됩니다", "~가 잡습니다", "~가 곧 증거가 됩니다"처럼 상태나 무생물 주어로 끝나는 문장은 AI스럽게 읽힌다.
  - "태그가 곧 배포 완료의 증거가 됩니다" → "…일치할 때만 태그를 남겼습니다"
  - "4.1분이 됐습니다" → "4.1분까지 줄였습니다"
  - "빌드 로그에 드러나게 했습니다" → "빌드 로그에 드러나게 해 추적할 수 있게 했습니다"
- 명사로 끊지 말고 동사로 끝낸다.
  - "인터넷이 차단된 현장 PC에서 로컬 LLM으로 답하는 챗봇." → "…답하는 챗봇을 구현했습니다."
- 직접 만든 것은 "대응했습니다"가 아니라 "구현했습니다"다.
- 구어와 비유를 쓰지 않는다.
  - "짜게 됐습니다" → "만들 수 있게 되었습니다"
  - "디자인 쪽 실험이 운영 화면을 바로 흔들지 않습니다" → "디자인팀의 토큰 변경은 개발 및 운영 환경에 영향을 미치지 않도록 제어했습니다"
  - "첫 결함.", "띠용" 같은 가벼운 표현

## 2. "맡았습니다"와 "담당했습니다"

- 개선, 제안, 개편, 이관, 교체처럼 **한 번 하고 끝나는 일**에는 "맡았습니다"를 붙이지 않는다. 동사로 바로 쓰거나 "담당했습니다"를 쓴다.
  - "…개선과 제안을 맡았습니다" → "…개선하고 전사 리뷰 도구 개선을 제안했습니다"
  - "토큰 생성기 교체, 배포 자동화, 저장소 분리를 담당했고"
- "맡았습니다"는 계속 담당하는 역할이나 소유 범위에만 쓴다(예: "설계와 공통 기반을 맡았습니다", "인증 구조 개편을 맡았고").
- 리팩터링을 역할이라고 쓰지 않는다. "계층 의존 정리 담당" → "그 과정에서 계층 의존을 리팩터링하고"
- 일회성 이관을 담당이라고 쓰면 어색하다. 중요하지 않으면 지운다.

## 3. 번역투와 어색한 말

| 쓰지 않음 | 쓴다 |
|------|------|
| 표 머리 | 머리글 |
| 한 모듈로 뽑아 | 공통 모듈로 정리해 |
| 인입 계약 | API 스키마 설계 |
| 형식 | 포맷 |
| 조판 | 렌더링, 페이지 분할 |
| timeout에 닿는다 | timeout에 가까워진다 |
| 예측 가능하게 | 구체적으로 무엇이 줄었는지 |
| 스크롤러 | 스크롤 영역 |
| 버전으로 의존하는, 의존하는 | 쓰지 않고 "버전 단위로", "앱마다 필요한 버전을 골라 쓰게" |
| 두 갈래, 한 갈래 | 갈래를 쓰지 않고 무엇과 무엇인지 적는다 |
| 정해진 모양의 코드 모듈 | 같은 틀, 또는 구체적인 구조 |
| 저장, Excel, 합계 등 6개 넘는 기능 | 변경된 행만 저장, Excel 붙여넣기, 소계 행처럼 기능 이름을 적는다 |

- 개발자가 실제로 쓰는 말을 쓴다(다운로드, 리렌더링, API 스키마, 포맷). 순화어("내려받기")를 쓰지 않는다.
- 한 문장에 정보를 몰아넣지 않는다. 쉼표로 이어진 긴 문장은 둘로 나눈다. 다만 사용자가 "2줄로 맞춰줘"라고 하면 한 문장으로 잇는다.

## 4. 채용담당자가 모르는 말

- **회사 안에서만 쓰는 이름은 풀어 쓴다.** 내부 서비스 이름, 레거시 시스템 약어, 조직 단위, 화면 이름은 채용담당자가 모른다.
  - 사내 서비스 별칭 → "운영 플랫폼"
  - 레거시 시스템 약어 → "급여, 연말정산 같은 레거시 시스템 화면"
  - "파트" → 그 개념이 생긴 맥락을 쓰거나 "작성자 소속 팀"
  - "부문 공통 게이트" → "사내 공통 게이트"(회사 전체가 아니면 "전사"도 쓰지 않는다)
  - 서비스 안에서만 쓰는 화면 이름 → "모델 테스트 화면"처럼 기능으로
- 면접관이 모르는 분류나 개수를 쓰지 않는다("세 가지 조판 방식").
- 앞뒤 맥락 없이 나오는 말을 쓰지 않는다. 저장소를 분리한 이유를 쓰지 않고 "분리 전까지"가 나오면 읽는 사람이 의아해한다. 이유를 쓰거나 뺀다.
- 지나치게 구체적인 업무 서식 이름(특정 영수증 양식 이름)은 "퇴직 리포트"처럼 묶는다.
- 날짜로 시작하는 문장("2026.02에")은 AI스럽다. "운영부터는"처럼 흐름으로 쓴다.

## 5. 주어와 의미가 뒤집히는 문장

- 목록 끝에 동사를 두면 주어가 바뀌어 읽힌다. "경험이 적은 동료도 조합만으로 화면을 만드는 UI 패키지, …그리드를 만들었고"는 동료가 만든 것처럼 읽힌다. 내가 만든 것을 주어 가까이 둔다.
- 남이 만든 것을 도입한 일을 성과처럼 쓰지 않는다. "PR CI에 공통 게이트를 붙이고 실행 시간을 줄였습니다"는 사내 게이트를 도입해서 빨라졌다고 읽힌다. 내가 한 일(게이트 설정 조정, 병렬화 제안)을 주어로 쓴다.
- "검사 규칙을 새로 만들지 않고 사내 공통 게이트를 붙였다"처럼 남의 도구를 가져다 쓴 것으로만 읽히는 판단은 왜 그 선택이 나았는지(공통 게이트를 고쳐야 다른 저장소도 함께 빨라진다)를 쓴다.
- 레거시 화면 이야기와 신규 화면 이야기가 섞이면 면접관은 신규로 읽는다. 헷갈리면 뺀다.
- 기술 사실이 맞는지 확인한다. "화면에 그린 행만 DOM에 있어 인쇄로는 보이는 행만 찍힌다"는 데이터 기반 인쇄 서비스에는 해당하지 않았다.

## 6. 공고 문구와 지원 동기

- 기술 이름과 분류는 공고 표기를 따른다. 검토자가 바로 대조할 수 있다.
- **지원 동기와 소개 문장에는 공고 문구를 그대로 옮기지 않는다.** 공고를 맞춰 주는 것처럼 읽히고, 옮긴 표현이 원문과 다른 뉘앙스(예: "코딩 에이전트까지 고객으로 보는"은 비꼬는 듯하게 읽힘)를 줄 수 있다.
- 지원 동기는 사용자의 말을 살려 쓴다. "이러한 저의 성향과 경험이 지향하는 업무 방향과 잘 맞을 것 같아 지원했습니다"처럼 사용자가 쓴 문장을 바탕으로 다듬는다.
- 소개에서 B2B 경력 같은 배경을 앞세우면 "왜 이 회사에 지원했지?"라는 의문이 생길 수 있다. 배경보다 어떤 방식으로 일해 왔는지를 쓴다.
- 과장하지 않는다. "여러 팀" → "여러 사람", 플랫폼 조직이 직접 만들지 않는 일을 했다고 강조하지 않는다.

## 7. 문장 부호

- 낫표 「」를 쓰지 않는다. 따옴표 “ ” ‘ ’를 쓴다.
- 줄표(—)와 가운뎃점(·)을 새로 쓰지 않는다(전역 `문서 작성 지침`).

## 8. AI 느낌 줄이기

- 모든 케이스가 같은 리듬의 문장, 같은 길이의 항목으로 끝나지 않게 한다. 짧은 문장과 긴 문장을 섞는다.
- 판단을 일반론으로 쓰지 않는다. "조사와 초안 구현은 에이전트에 맡기고 판단은 직접 합니다" 같은 원칙 선언 대신 실제로 있었던 일(무엇을 확인했고 무엇을 고쳤는지)을 쓴다.
- 사례가 앞뒤 맥락 없이 시작하면 "뭔 소리지"가 된다. 무엇을 하던 중이었는지 한 문장으로 먼저 깔아 준다.
- 사용자가 직접 쓴 문장이 있으면 그 문장을 다듬는다. 새로 쓰지 않는다. 필요하면 `humanizer` 스킬로 한 번 더 본다.
