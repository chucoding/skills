# Jira 지침

Jira 티켓을 생성하거나 상태를 바꾸고, 완료 처리한 티켓의 HC나 HOM 원본에 댓글을 남기고, FE 저장소의 티켓을 BE로 넘기거나 SP를 산정할 때 이 규칙을 따른다. 티켓, 이슈, 스프린트, SP, HDIT, HOM이 언급되는 작업이 모두 적용 대상이다.

## 티켓 생성

- Jira 티켓은 사용자가 명시적으로 생성을 요청한 경우에만 생성한다.
- 작업 중 티켓이 필요해 보인다고 스스로 판단해 생성하지 않는다. 하위 작업, 복제 티켓, 후속 티켓도 마찬가지다.
- 티켓이 필요하다고 판단되면 생성하지 말고 대화로 제안한 뒤 사용자의 지시를 기다린다.
- 이 규칙은 하위 에이전트와 스킬, MCP 도구를 통한 생성에도 동일하게 적용한다.
- 생성이 승인되면 아래 기본값을 사용한다. 사용자 요청으로 HDIT에 이동하거나 복제해 들어오는 티켓에도 같은 기본값을 적용한다.

| 항목 | 값 |
|------|-----|
| 워크스페이스 | HDIT |
| 이슈 유형 | 작업_개발 |
| 작업자 | 서현석 |
| 보고자 | 사용자가 지정한 사람 |
| 팀 | `HC_DEV` (필드 `customfield_10001`, 값 `9d0fedb4-dc2b-4699-b112-a27baa2908d4`) |
| 스프린트 | 현재 활성 스프린트 (필드 `customfield_10020`) |

- 보고자는 기본값이 없다. 사용자가 밝히지 않으면 임의로 채우지 말고 누구로 할지 되묻는다.
- 사용자가 위 항목을 다르게 지정하면 사용자가 말한 값을 따른다.
- 스프린트는 `sprint in openSprints()`로 조회해 넣고, 활성 스프린트가 여럿이면 되묻는다.
- 생성이나 이동을 마치면 표의 항목을 다시 조회해 확인한다. 아래 `현재 티켓 연결`로 링크를 만든 생성이면 링크도 함께 조회한다. 도구 성공 메시지로 대신하지 않고, 못 채운 항목은 보고의 `하지 않은 것`에 남긴다.

### 현재 티켓 연결

작업 중에 사용자가 별도, 후속, 분리 티켓 생성을 요청하면 지금 작업 중인 티켓을 새 티켓에 연관(`Relates`)으로 연결한다. 사용자가 따로 말하지 않아도 기본으로 넣는다. QA는 연관 티켓을 따라가며 검토 범위를 잡으므로, 파생 티켓에 현재 티켓 링크가 없으면 같은 화면을 함께 검토해야 한다는 사실이 드러나지 않는다.

- 현재 티켓은 현재 브랜치 이름의 티켓 키나 워크스페이스 착수 입력의 티켓 키로 찾는다. 찾지 못하거나 후보가 여럿이면 되묻고, 사용자가 현재 티켓이 없다고 답하면 `연결` 항목을 비운 채 진행한다.
- 현재 티켓의 이슈 링크에서 클론 관계로 이어진 HOM 원본이나 HDIT 클론을 조회해, 찾은 쪽에도 같은 링크를 건다. QA가 읽는 곳이 HOM이라 HDIT에만 걸면 QA 쪽에 드러나지 않는다. 클론 관계가 없으면 현재 티켓에만 건다.
- 생성을 승인받을 때 보여주는 초안에 `연결` 항목을 두고 현재 티켓(HOM 원본 포함)을 넣는다. 원인 커밋의 티켓처럼 대화에서 확인된 다른 연관 티켓이 있으면 함께 적고, 같은 `Relates` 링크로 만든다.
- 링크는 연결할 티켓마다 `POST /rest/api/3/issueLink`로 만든다.

  ```json
  {"type":{"name":"Relates"},"inwardIssue":{"key":"<새 티켓>"},"outwardIssue":{"key":"<현재 티켓>"}}
  ```

- 링크 생성이 실패하거나 재조회에서 링크가 보이지 않으면 다시 시도하지 말고 보고의 `하지 않은 것`에 남긴다.
- 사용자가 연결하지 말라고 하면 따른다.

## 상태 전환

- 티켓 상태 전환은 티켓 생성 규칙과 별개로 판단한다. 생성은 명시적 요청이 있을 때만 하지만, 상태 전환은 작업 흐름에서 정해진 시점에 수행한다.
- PR 생성 후 `리뷰중` 전환은 `chucoding:commit-pr` 스킬의 `7. PR 생성 후 티켓 상태 전환`을 따른다.
- 상태 전환은 상태 필드만 바꾼다. 티켓에 배정된 스프린트는 지난 스프린트라도 그대로 두고, `티켓 생성`의 활성 스프린트 기본값을 적용하지 않는다.
- 스프린트가 비어 있는 백로그 티켓만 예외다. 활성 스프린트(`sprint in openSprints()`)와 다음 스프린트(`sprint in futureSprints()`)를 조회해 어느 레인에 넣을지 되묻고, 임의로 활성 스프린트에 넣지 않는다.

## 원본 티켓 완료 댓글

HDIT 티켓을 `개발완료`로 바꾸면, 그 티켓과 Cloners로 연결된 원본 티켓에 완료 댓글을 남긴다. 원본은 기획 티켓인 HC와 QA 티켓인 HOM 두 종류이고, 읽는 사람이 달라 문구와 본문이 다르다.

| 원본 | 읽는 사람 | 멘션 대상 | 첫 줄 문구 | 본문 제목 |
|------|------|------|------|------|
| HC | 기획자 | HC 담당자 | `해당 티켓 개발 완료되었습니다.` | `[PRD에 없어 정한 동작]` |
| HOM | QA | HOM 보고자 | `수정 완료되었습니다.` | `[추가로 수정된것]` |

- 원본 티켓은 완료 처리한 HDIT를 `GET /rest/api/3/issue/<HDIT키>?fields=issuelinks`로 읽어 정한다. `issuelinks` 중 링크 유형이 `Cloners`이고 상대 티켓의 프로젝트 키(링크된 티켓 키의 `-` 앞 접두사)가 `HC` 또는 `HOM`인 것이다. 링크 방향(`clones`, `is cloned by`)은 가리지 않는다.
- 원본 티켓이 없으면 댓글을 남기지 않는다. 같은 프로젝트의 원본이 2개 이상이면 임의로 고르지 말고 어느 티켓에 남길지 되묻는다. HC와 HOM이 하나씩 있으면 각자의 형식으로 둘 다 남긴다.
- 사용자의 완료 처리 요청이든, PR 머지를 확인하고 에이전트가 스스로 전환한 경우든 똑같이 댓글을 남긴다. `개발완료` 전환 자체를 댓글 게시 승인으로 보고 게시 승인은 다시 묻지 않는다. 단 아래에서 대상이나 본문이 정해지지 않을 때의 되묻기는 따른다.
- 순서는 `개발완료` 전환, 원본 댓글, 위키 정리 질문(전역 AGENTS.md `완료 처리 후 위키 정리`)이다.

### 댓글 형식

```
{@멘션 대상} {첫 줄 문구} (cc. {@cc 대상})
[본문 제목]
- ...
```

- **첫 줄 문구**는 위 표를 따른다. HOM은 `해당 티켓`을 붙이지 않는다. QA 티켓에 붙이면 티켓 작성이 완료되었다는 뜻으로 읽힌다.
- **멘션 대상**은 HC면 담당자, HOM이면 보고자(`reporter`)다. HOM 담당자는 `BE 이관` 규칙대로 HDIT 담당자와 같아 대개 나여서, 담당자를 멘션하면 QA가 아니라 나를 부르게 된다. 멘션 대상이 비어 있거나 나이면 HC와 HOM 모두 멘션 없이 게시하지 말고 누구를 멘션할지 되묻는다. 나를 멘션하면 댓글을 읽어야 할 사람에게 알림이 가지 않기 때문이다.
- **cc 대상**은 원본 티켓의 `issuelinks` 중 링크 유형이 `Cloners`이고 프로젝트 키가 `HDIT`인 티켓 가운데, 완료 처리한 티켓을 뺀 나머지의 담당자다. 담당자가 비어 있는 티켓은 건너뛴다. 나(인증 계정 `JIRA_EMAIL`, accountId는 `GET /rest/api/3/myself`)와 멘션 대상은 빼고 중복도 없앤다. 여러 명이면 `(cc. @A, @B)`처럼 쉼표와 공백으로 잇는다. 남는 사람이 없으면 `(cc. ...)`를 통째로 생략한다. Blocks 같은 다른 링크 유형의 담당자는 넣지 않는다.
- **PR**은 완료 처리한 HDIT 티켓의 PR이다. HDIT 키는 뒤에 숫자가 더 이어지지 않는 정확한 키로 비교한다. `HDIT-12`는 `HDIT-123`과 일치하지 않는다. 머지 없이 닫힌 PR(`state`가 `CLOSED`)은 어느 경로에서든 쓰지 않는다.
  1. `gh pr view --json number,state,title,headRefName,body,commits`로 현재 브랜치의 PR을 읽는다. 제목이나 브랜치명에 HDIT 키가 있고 `CLOSED`가 아니면 그 PR의 `body`와 `commits`를 그대로 쓴다.
  2. 조회 결과가 없거나 1단계 조건에 맞지 않으면 `gh pr list --state all --search <HDIT키> --json number,title,headRefName,state`로 찾고, 같은 조건에 맞는 PR만 후보로 삼는다. 후보가 여럿이면 어느 것을 쓸지 되묻는다. 고른 PR은 `gh pr view <번호> --json body,commits`로 본문과 커밋을 읽는다.
- **HC 본문**은 PR 본문의 `PRD에 없어 정한 동작` 섹션을 옮긴다. 이 섹션은 `chucoding:commit-pr`의 기본 PR 구조에는 없고 저장소 PR 템플릿에 있을 때만 생긴다. 읽는 사람이 기획자이므로 구현 용어를 쉬운 말로 다듬는다. 예를 들어 "전송"은 "저장"으로 바꾸고, "공백을 제거하지 않은 값으로" 같은 구현 세부는 뺀다. 결정의 내용 자체는 바꾸지 않는다. PR을 찾지 못했거나, 그 섹션이 없거나, 섹션 내용이 비었거나 `없음`, `해당 없음`뿐이면 본문을 지어내지 말고 어떻게 할지 되묻는다.
- **HOM 본문**은 PR 본문과 커밋에서 QA가 지적한 문제 외에 함께 고친 것만 추려 옮긴다. QA가 지적한 문제는 HOM 티켓의 제목과 설명(`fields=summary,description`)으로 판단한다. QA가 재검증할 범위를 알리려는 것이므로 화면에서 달라지는 동작 위주로 쉽게 쓴다. 해당하는 것이 없으면 `[추가로 수정된것]` 제목까지 통째로 생략하고 첫 줄만 남긴다. PR을 찾지 못했으면 생략으로 단정하지 말고 되묻는다.

### 게시 절차

인증은 `~/.config/homedot-worktime/config.env`의 `JIRA_EMAIL`과 `JIRA_API_TOKEN`, 사이트는 `https://rsquare.atlassian.net`이다. 원본 티켓마다 아래를 따로 수행한다.

1. **멘션 대상과 담당자를 모은다.** 먼저 `GET /rest/api/3/myself`로 나(인증 계정)의 accountId를 읽어, 멘션 대상이 나인지 판정하고 cc에서 뺄 때 쓴다. `GET /rest/api/3/issue/<원본키>?fields=assignee,reporter,issuelinks,summary,description`로 멘션 대상과 링크를 읽고, Cloners로 연결된 HDIT 티켓마다 `fields=assignee`로 담당자를 읽는다.
2. **accountId와 이름을 정한다.** 담당자와 보고자 필드의 `accountId`와 `displayName`을 그대로 쓴다. 사용자가 멘션할 사람을 이름으로 직접 지정했을 때처럼 accountId를 필드에서 얻을 수 없을 때만 `GET /rest/api/3/user/search?query=<이름>`으로 찾고, `accountType`이 `atlassian`인 결과만 남긴다. 0건이거나 2건 이상이면 임의로 고르지 말고 되묻는다.
3. **ADF로 게시한다.** `POST /rest/api/3/issue/<원본키>/comment`에 ADF 본문을 보낸다. 멘션은 텍스트 `@이름`이 아니라 mention 노드로 넣어야 알림이 간다.

   ```json
   {"type": "mention", "attrs": {"id": "<accountId>", "text": "@<displayName>"}}
   ```

   첫 줄과 본문 제목은 각각 `paragraph`로 두고, 첫 줄 안에서 멘션 사이 문구는 `text` 노드로 잇는다. 본문 제목 아래 목록은 `bulletList` > `listItem` > `paragraph` 구조로 만든다. 게시가 실패하면 재시도하지 말고 응답 상태와 오류 메시지를 보고한다. 원본이 둘이면 실패한 쪽과 관계없이 남은 원본은 계속 게시하고, 모든 원본을 처리한 뒤 위키 정리 질문으로 넘어간다. 한쪽 원본에서 되묻기가 걸리면 다른 원본은 먼저 게시하고, 위키 정리 질문은 되묻기에 대한 답을 받아 그 원본까지 처리한 뒤에 한다. `개발완료` 전환은 되돌리지 않는다.

4. **멘션을 확인한다.** 게시 응답의 `body.content`를 안쪽 `content`까지 재귀로 훑어 mention 노드의 `attrs.id`를 모으고, 의도한 사람 모두에게 멘션이 걸렸는지 확인한다. 빠진 사람이 있으면 그 사실을 보고하고, 댓글을 수정할지 되묻는다. 같은 댓글을 다시 게시하지 않는다.
5. **링크를 보고한다.** `https://rsquare.atlassian.net/browse/<원본키>?focusedCommentId=<댓글 id>`를 보고에 남긴다.

## BE 이관

FE 저장소에서 착수한 티켓이 조사 결과 FE에서 수정할 것이 없고 BE에서 수정해야 하는 것으로 판별되면, 티켓을 BE 쪽으로 넘기고 이 세션이 남긴 착수 흔적을 지운다. 판별 근거 없이 넘기지 않는다.

1. **판별을 먼저 끝낸다.** 응답 스펙(`/v3/api-docs`)과 FE 코드를 함께 확인해 FE에서 고칠 여지가 없음을 확정한다. 아래 두 가지를 모두 확인한다.
   - 응답 DTO에 필요한 필드가 없고, 요청 파라미터에도 그 값을 켜는 플래그가 없다. 프론트가 요청할 방법 자체가 없어야 한다.
   - 같은 값을 쓰는 형제 엔드포인트나 다른 화면에서는 정상 동작한다. 이 대조가 설계 의도와 누락을 가른다.

   판별이 갈리지 않으면 이관하지 않고 무엇이 불확실한지 밝힌다.

2. **담당자를 확정한다.** 사용자가 이름을 말하면 `/rest/api/3/user/search?query=<이름>`으로 accountId를 조회한다. 결과가 0건이거나 2건 이상이면 임의로 고르지 말고 되묻는다. 사용자가 이름을 말하지 않았으면 담당자를 추측하지 않고 누구에게 넘길지 묻는다.

3. **HDIT와 HOM 양쪽 담당자를 함께 바꾼다.** 한쪽만 바꾸면 QA 원본과 개발 클론의 담당자가 어긋나, 다음 세션의 담당자 정렬이 QA 기준으로 되돌린다.

4. **댓글은 HOM 원본에만 남긴다.** QA가 읽는 곳이 HOM이다. 문구는 아래 형식을 따른다.

   ```
   BE에서 확인이 필요한 티켓이므로 담당자 {이름}님으로 변경해놓겠습니다
   ```

5. **HDIT 상태를 `Backlog`로 되돌린다.** 내 작업이 아니게 됐는데 개발중으로 두면 작업시간이 계속 쌓인다.

6. **착수 흔적을 지운다.** 이 세션이 작업시작 때 채운 Actual start(`customfield_10008`)와 시작 날짜(`customfield_10015`)를 HDIT와 HOM 양쪽에서 `null`로 비운다. 내가 채우지 않은 값은 건드리지 않는다.

7. **SP와 스프린트는 그대로 둔다.** SP는 계획값이라 불변이고, 스프린트는 `상태 전환` 규칙을 따른다.

8. **HOM 상태는 되돌리지 않는다.** `in progress`에서 나가는 전환이 `Known Issue`, `Won't Do`, `개발완료`(도착 상태 `resolve`)뿐이라 `open`으로 가는 경로가 워크플로우에 없다. 뜻이 다른 상태로 임의 전환하지 말고, HOM이 `in progress`로 남았다는 사실을 보고에 적는다.

9. **대시보드를 갱신한다.** `refresh.py --release`를 실행한다.

보고에는 판별 근거, 바꾼 항목, HOM 상태가 남은 사실을 함께 적는다. BE 작업 티켓을 새로 만들지 않는다. 필요해 보이면 `티켓 생성` 규칙대로 제안만 하고 지시를 기다린다.

## SP 산정

- SP의 정본 근거는 **Jira 업무 로그**(`timetracking.timeSpentSeconds`)다. 상태 체류 시간을 근무 시간으로 환산한 값을 실적으로 쓰지 않는다. 두 값은 2배 이상 벌어진다.
- 환산은 **1 SP = 8시간**이고, 순수 예상 시간에 **여유 15%**를 더해 `예상 시간 × 1.15 ÷ 8`로 계산한다. 이 값은 폴러의 `estimate_sp.py` 상수와 같아야 하므로 과거 티켓에서 비율을 새로 도출하지 않는다.
- 손으로 산정할 때는 아래 명령으로 유사 실적 후보를 받아, 근거로 삼은 티켓 키와 그 업무 로그 시간을 함께 남긴다. `suggestion`이 `null`이면 닮은 티켓이 없다는 뜻이므로 아래 `유사 티켓을 찾지 못하면` 항목을 따른다.

  ```bash
  cd <플러그인>/skills/sprint-worktime-report/scripts
  python3 estimate_sp.py --json --key <티켓키>   # 설정은 스크립트가 알아서 읽는다
  ```

- SP는 계획값이라 한 번 들어가면 덮지 않는다. 비어 있는 칸만 채운다.
- 넣기 직전에 SP 칸을 다시 조회하고, 이미 값이 있으면 덮지 않고 그 값을 보고한다. 생성 직후 비어 있던 칸을 폴러나 사용자가 몇 분 사이에 먼저 채울 수 있다.
- 유사 티켓을 찾지 못하면(`suggestion: null`) 비교한 건수(`--json` 출력의 `corpus`)와 유사 티켓이 없다는 사실을 사용자에게 그대로 밝힌다. 이어서 작업 단계별 예상 시간(예: 구현, 경계 처리, E2E, 리뷰 대응)을 나눠 합산하고, `예상 시간 × 1.15 ÷ 8`로 SP를 직접 산정해 비어 있는 칸에 넣는다. 스크립트와 같게 최소 0.13 SP(1시간)를 하한으로 두고 소수 둘째 자리로 반올림한다. 기입은 `estimate_sp.py --key <티켓키> --sp <값> --note "<근거>"`로 하고, 3 SP를 넘으면 쪼개기 검토가 필요하다는 점을 함께 보고한다.
- 직접 산정했으면 단계별 시간, 합계, 유사 티켓이 없었다는 사실을 보고에 남긴다.
