# Jira 지침

Jira 티켓으로 워크스페이스를 만들어 착수하거나, 티켓을 생성하거나 상태를 바꾸고, 완료 처리한 티켓의 원본(HOM, QA가 올린 `QA_Bug`, PM이나 운영의 스토리 원장)에 완료 댓글을, 원장이 없으면 HDIT 티켓에 화면 증빙 댓글을 남기고, FE 저장소의 티켓을 BE로 넘기거나 SP를 산정할 때, 다른 팀 저장소의 변경을 담당자에게 티켓으로 넘기거나 티켓 설명을 쓸 때 이 규칙을 따른다. HDIT 티켓을 만들면 요청이 없어도 보고 전에 SP까지 채운다(AX 같은 다른 팀 저장소 티켓은 제외). 티켓, 이슈, 스프린트, SP, HDIT, HOM, QA_Bug, 원장이 언급되는 작업이 모두 적용 대상이다.

## 착수 브랜치 이름

Orca가 Jira 티켓으로 만든 워크스페이스 브랜치는 `feature/hdit-4173-fe-pr-pr-it-it-ci-gates-conventions-ty`처럼 티켓 키가 소문자이고 48자에서 잘린다. IT부문 런북 §3과 이를 PR마다 검사하는 it-ci-gates conventions 게이트는 `<접두>/<티켓키>[-설명]` 형식을 요구한다. 접두 `feature/`는 전환 기간이라 경고에 그치지만, 소문자 키는 형식 위반이라 그대로 두면 첫 푸시 뒤 게이트가 실패한다. Orca에는 키 소문자화를 막거나 작업 유형별 접두를 고르는 설정이 없어 착수 시점에 이름을 맞춘다.

- 정본: [it-governance-hub RUNBOOK §3](https://github.com/dev-rsquare/it-governance-hub/blob/main/bundles/workflow/RUNBOOK.md)
- 시점은 착수 직후, `개발중` 전환이나 첫 커밋보다 앞이다. `chucoding:commit-pr`이 PR 제목의 티켓 키를 브랜치 이름에서 읽기 때문이다. 늦어도 첫 푸시 전에는 맞춘다.

### 바꾸는 조건

형식과 키를 먼저 보고, 어긋날 때만 원격 여부를 본다.

1. **형식 판정.** 현재 이름이 아래 정규식과 일치하고 그 안의 티켓 키가 `새 이름 정하기`의 키 규칙으로 정한 키와 같으면 아무것도 하지 않고 보고에도 적지 않는다. 키가 HOM이거나 이슈 유형이 `QA_Bug`인 HDIT 키면 접두도 `fix/`여야 같은 것으로 본다. QA 클론인데 `feat/HDIT-4173-x`처럼 HDIT 키를 쓰거나 `feat/HOM-2417-x`처럼 HOM 키에 다른 접두를 쓴 브랜치는 정규식이 맞아도 맞출 대상이다. `feature/`는 런북에서 전환 기간 경고 대상이지만 이번에 맞출 대상이라 불일치로 본다.

   ```
   ^(feat|fix|hotfix|docs|chore)/[A-Z][A-Z0-9]+-[0-9]+(-[a-z0-9]+)*$
   ```

2. **원격 판정.** 형식이나 키가 어긋나면 원격에 같은 브랜치가 있는지 본다. upstream만 보면 추적 설정 없이 푸시된 브랜치를 놓치므로 두 명령을 모두 확인한다. upstream은 `git rev-parse --abbrev-ref @{u}` 결과가 `origin/<현재 브랜치>`일 때만 원격에 있다는 근거로 본다. `origin/main`처럼 다른 브랜치를 추적하면 upstream이 없는 것과 같게 보고 `ls-remote` 결과로만 판정한다.
   - 현재 브랜치를 가리키는 upstream이 없고, `git ls-remote --exit-code --heads origin <현재 브랜치>`가 종료 코드 2(일치하는 ref 없음)로 끝나면 원격에 없는 것으로 보고 이름을 바꾼다.
   - 현재 브랜치를 가리키는 upstream이 있거나 `ls-remote`가 ref를 찾으면(종료 코드 0) 바꾸지 않는다. 형식이나 키가 어긋났다는 사실과 런북 형식으로 정한 이름을 사용자에게 알린다.
   - `origin`이 없거나 네트워크, 인증 오류로 `ls-remote`가 그 밖의 코드로 끝나면 원격 여부를 확정할 수 없으므로 바꾸지 않는다. 실패 메시지를 그대로 보여주고 어떻게 할지 되묻는다.

키와 접두를 정하는 데 필요한 티켓 조회(`GET /rest/api/3/issue/<키>?fields=issuelinks,issuetype,summary,description`. `QA_Bug` 판정은 `issuetype.name`)가 인증이나 네트워크 오류로 실패하면 이름을 바꾸지 않는다. 실패 메시지를 그대로 보여주고 어떻게 할지 되묻는다.

### 새 이름 정하기

새 이름은 `<접두>/<티켓키>-<설명>`이다.

- **접두**는 티켓의 이슈 유형과 제목, 설명으로 정한다. 아래 5종 밖의 접두는 쓰지 않는다. `refactor/`, `bugfix/`, `ci/`, 이름이나 도구 접두는 런북이 금지하고, 봇 전용 `dependabot/`, `automation/`도 쓰지 않는다.

  | 접두 | 대상 |
  |------|------|
  | `feat/` | 기능 추가와 변경 |
  | `fix/` | 결함 수정, QA 결함 |
  | `hotfix/` | 긴급 운영 수정 |
  | `docs/` | 문서만 바꾸는 작업 |
  | `chore/` | 빌드, CI, 의존성, 설정, 리팩터링처럼 제품 동작이 바뀌지 않는 작업 |

  둘 이상에 걸치거나 근거가 부족하면 추측하지 말고 후보 접두를 선택지로 묻는다.

- **티켓 키**는 대문자 Jira 키다. HDIT 티켓이 HOM 원본의 QA 클론이면 HOM 키를 쓴다. 클론 판정은 `원본 티켓 완료 댓글`과 같이 `issuelinks`에서 링크 유형이 `Cloners`이고 상대 프로젝트 키가 `HOM`인지로 한다. 착수 입력이 HOM 키 자체면 그 키를 그대로 쓴다. Cloners로 연결된 HOM 원본이 둘 이상이면 임의로 고르지 말고 어느 키를 쓸지 되묻는다. HOM 키를 쓰는 두 경우(HOM 직접 착수, HDIT 클론) 모두 접두는 위 표의 판정 없이 `fix/`로 정한다. QA 배포 자동화가 PR 제목의 HOM 키로 QA 티켓을 찾으므로, homedot-cloud-devteam `ticket-start`의 HOM 키 규칙(`fix/HOM-2417`)과 결과가 같아야 한다.
- 이슈 유형이 `QA_Bug`인 HDIT는 HOM 원본이 없으므로 HDIT 키를 그대로 쓰고, 접두는 위 표의 판정 없이 `fix/`로 정한다. 예: `fix/HDIT-4857-period-filter-keep`. QA 배포 자동화가 PR 제목의 HDIT 키로도 QA 티켓을 찾는지는 확인되지 않았다(2026-10-21). 자동화가 QA_Bug를 못 찾는 사례가 나오면 이 규칙을 다시 본다.
- **설명**은 영문 소문자 kebab-case 2~4단어다. 생략하지 않는다. 제목이 한글이면 의미를 영문으로 요약하고, Orca가 잘라 만든 꼬리를 그대로 옮기지 않는다. 예: `chore/HDIT-4173-ci-gates`, `fix/HOM-2417-meter-reading-date`

### 실행과 보고

1. `git branch -m <현재 이름> <새 이름>`으로 바꾼다. 같은 이름이 이미 있어 실패해도 `-M`으로 덮어쓰지 않는다. 실패 메시지를 그대로 보여주고 어떤 이름으로 할지 되묻는다.
2. `git branch --show-current`로 바뀐 이름을 확인한다.
3. 보고에 `이전 이름 → 새 이름`과 접두를 고른 근거를 남긴다. Orca 워크스페이스 이름은 그대로 남으므로 사용자가 둘을 대조할 근거가 필요하다.

## 티켓 생성

- Jira 티켓은 사용자가 명시적으로 생성을 요청한 경우에만 생성한다.
- 작업 중 티켓이 필요해 보인다고 스스로 판단해 생성하지 않는다. 하위 작업, 복제 티켓, 후속 티켓도 마찬가지다.
- 티켓이 필요하다고 판단되면 생성하지 말고 대화로 제안한 뒤 사용자의 지시를 기다린다.
- 이 규칙은 하위 에이전트와 스킬, MCP 도구를 통한 생성에도 동일하게 적용한다.
- 생성이 승인되면 아래 기본값을 사용한다. 사용자 요청으로 HDIT에 이동하거나 복제해 들어오는 티켓에도 같은 기본값을 적용한다. 이 표는 HDIT 티켓 기본값이다. 다른 팀 저장소의 변경을 그 팀 담당자에게 넘기는 티켓은 아래 `다른 팀 저장소 티켓`의 기본값을 쓴다.
- 설명(`description`)을 쓰거나 고칠 때는 아래 `티켓 본문`을 따른다. 어느 소절이 어느 티켓에 적용되는지는 그 절의 첫 목록에 있다.

| 항목 | 값 |
|------|-----|
| 워크스페이스 | HDIT |
| 이슈 유형 | 작업_개발 |
| 작업자 | 서현석 |
| 보고자 | 사용자가 지정한 사람 |
| 팀 | `HC_DEV` (필드 `customfield_10001`, 값 `9d0fedb4-dc2b-4699-b112-a27baa2908d4`) |
| 스프린트 | 현재 활성 스프린트 (필드 `customfield_10020`) |
| 컴포넌트 | `파트 1` (필드 `components`, 값 `[{"id":"10276"}]`) |
| SP | 생성 직후 아래 `SP 산정`으로 기입 (필드 `customfield_10028`) |

- 보고자는 기본값이 없다. 사용자가 밝히지 않으면 임의로 채우지 말고 누구로 할지 되묻는다.
- 사용자가 위 항목을 다르게 지정하면 사용자가 말한 값을 따른다.
- 스프린트는 `sprint in openSprints()`로 조회해 넣고, 활성 스프린트가 여럿이면 되묻는다.
- 컴포넌트는 이름이 아니라 id로 넣는다. HDIT 컴포넌트 이름은 `파트 1`처럼 띄어쓰기가 있어 `파트1`로 넣으면 일치하지 않는다. 사용자가 다른 파트를 지정하면 `GET /rest/api/3/project/HDIT/components`에서 이름으로 id를 찾는다(2026-10-23 실측: `파트 2` `10277`, `파트 3` `10278`). 일치하는 이름이 없으면 임의로 고르지 말고 조회한 목록을 보여 주며 되묻는다.
- 새로 만드는 티켓은 생성 payload의 `fields.components`에 `[{"id":"10276"}]`을 넣는다. 사용자가 다른 파트를 지정하면 `파트 1` 대신 그 파트 id만 넣는다.
- 이동이나 복제로 들어온 티켓은 먼저 `fields=components`로 조회한다. 파트 컴포넌트(`파트 1`, `파트 2`, `파트 3`)가 하나라도 있으면 컴포넌트를 건드리지 않는다. 다만 사용자가 지정한 파트가 이미 붙은 파트와 다르면 바꿀지 더할지 되묻는다. 없으면 기존 컴포넌트를 덮지 않도록 `PUT /rest/api/3/issue/<키>`에 `{"update":{"components":[{"add":{"id":"10276"}}]}}`로 더하고, 사용자가 다른 파트를 지정했으면 그 id로 더한다.
- SP는 HDIT 티켓 생성 요청에 포함된 단계다(다른 팀 저장소 티켓은 제외, 아래 `다른 팀 저장소 티켓` 참고). 사용자가 산정을 따로 요청하지 않아도 생성 직후 아래 `SP 산정`을 수행하고, 기입까지 마친 뒤 생성을 보고한다. 이동이나 복제로 HDIT에 들어온 티켓도 같다.
- 생성 payload에는 SP를 넣지 않는다. `estimate_sp.py --sp --note`로 넣어야 근거 문단과 원래 추정 시간(`originalEstimate`), 플러그인이 넣은 값이라는 기록이 함께 남는다.
- 폴러의 자동 기입은 보조 안전망일 뿐 기본 경로가 아니다. 폴러는 맥이 깨어 있는 06~23시에만 돌고, 한 주기에 2건만, 작업자가 나인 티켓만 처리한다. 2026-10-01에 만든 HDIT-3746, 3768 등 5건은 폴러가 멈춘 날이 이어져 1~5일 뒤에야 SP가 들어갔다.
- 생성이나 이동을 마치면 표의 항목을 다시 조회해 확인한다. 아래 `현재 티켓 연결`로 링크를 만든 생성이면 링크도 함께 조회한다. 도구 성공 메시지로 대신하지 않고, 못 채운 항목은 보고의 `하지 않은 것`에 남긴다.

### 현재 티켓 연결

작업 중에 사용자가 별도, 후속, 분리 티켓 생성을 요청하면 지금 작업 중인 티켓을 새 티켓에 `연결됨`으로 연결한다. 사용자가 따로 말하지 않아도 기본으로 넣는다. QA는 연결된 티켓을 따라가며 검토 범위를 잡으므로, 파생 티켓에 현재 티켓 링크가 없으면 같은 화면을 함께 검토해야 한다는 사실이 드러나지 않는다.

`연결됨`의 API 유형명은 `Discovery - Connected`(outward `connects to`, inward `is connected to`)다. `관련됨`(`Relates`)을 쓰지 않는 이유는 PM 원장 티켓을 완료 처리할 때 `연결됨`으로 이어진 티켓만 함께 완료로 바뀌기 때문이다(2026-11-05 사용자 확인). 원장이 `connects to` 쪽에 선다. 예: HDIT-4389(RFMS 이관 원장) `connects to` HDIT-5796.

현재 티켓이 원장으로 쓰이면, 원장을 완료할 때 다음 스프린트로 미룬 후속 티켓까지 함께 완료될 수 있다. 그래도 같은 링크를 쓰기로 사용자가 정했으므로(2026-11-05) 링크 유형을 바꾸지 않는다. 대신 완료 처리 직전에 남은 파생 티켓을 확인해 보고한다. 절차는 아래 `원본 티켓 완료 댓글`의 `남은 파생 티켓 확인`이다.

- 현재 티켓은 현재 브랜치 이름의 티켓 키나 워크스페이스 착수 입력의 티켓 키로 찾는다. 찾지 못하거나 후보가 여럿이면 되묻고, 사용자가 현재 티켓이 없다고 답하면 `연결` 항목을 비운 채 진행한다.
- 현재 티켓의 이슈 링크에서 클론 관계로 이어진 HOM 원본이나 HDIT 클론을 조회해, 찾은 쪽에도 같은 링크를 건다. QA가 읽는 곳이 HOM이라 HDIT에만 걸면 QA 쪽에 드러나지 않는다. 클론 관계가 없으면 현재 티켓에만 건다.
- 생성을 승인받을 때 보여주는 초안에 `연결` 항목을 두고 현재 티켓(HOM 원본 포함)을 넣는다. 원인 커밋의 티켓처럼 대화에서 확인된 참고용 티켓이 있으면 함께 적되, 파생 관계가 아니므로 `Relates`(관련됨)로 만든다. 원인 티켓에 `연결됨`을 걸면 원장 완료 처리에 휩쓸릴 수 있다.
- 링크는 연결할 티켓마다 `POST /rest/api/3/issueLink`로 만든다.

  ```json
  {"type":{"name":"Discovery - Connected"},"inwardIssue":{"key":"<현재 티켓>"},"outwardIssue":{"key":"<새 티켓>"}}
  ```

  방향이 아래 `Relates` 링크와 반대다. `inwardIssue`가 outward 설명(`connects to`)의 주어가 되므로 현재 티켓을 `inwardIssue`에 넣어야 `<현재 티켓> connects to <새 티켓>`이 된다. 재조회에서 현재 티켓의 링크가 `connects to <새 티켓>`으로 보이는지 확인한다.

  원인 커밋의 티켓 같은 참고용 링크는 아래처럼 `Relates`로 만든다. 새 티켓이 inward, 참고 티켓이 outward다. 2026-11-05 전의 파생 티켓 링크도 이 형태라서 `chucoding:orca-jira-workbench`가 이 방향으로 메인 티켓을 추정한다.

  ```json
  {"type":{"name":"Relates"},"inwardIssue":{"key":"<새 티켓>"},"outwardIssue":{"key":"<참고 티켓>"}}
  ```

- 링크 생성이 실패하거나 재조회에서 링크가 보이지 않으면 다시 시도하지 말고 보고의 `하지 않은 것`에 남긴다.
- 사용자가 연결하지 말라고 하면 따른다.

### 다른 팀 저장소 티켓

`dev-rsquare/it-ai-toolkit`, `dev-rsquare/it-ci-gates`처럼 다른 팀 저장소의 변경에 적용한다. 다른 팀 저장소는 `chucoding:handoff`의 `2. 대상 저장소 판별` 표에 없고, 지금 작업 중인 티켓이 HDIT나 HOM이 아닌 저장소다. 판정이 애매하면 아래 권한 확인을 그대로 돌려 결과로 정한다. 2026-10-28에 AX-370, AX-371로 이어진 두 세션은 구현과 커밋을 마친 뒤에야 `git push`가 거부됐다. `hyeonseok-suh` 계정이 그 저장소에 `push: false`였고, 사용자는 두 번 모두 "작업하지 말고 담당자로 적합한 사람에게 할당"하라고 답했다.

**푸시 권한 먼저 확인**

- 다른 팀 저장소에서 파일을 고치기 전에 `gh api repos/<owner>/<repo> --jq .permissions.push`를 본다. `<owner>/<repo>`는 `git remote get-url origin`에서 읽는다. 핸드오프 브리핑에 이미 결과가 적혀 있어도 착수 시점에 한 번 더 본다.
- `true`면 평소대로 구현한다.
- `false`면 구현하지 않는다. 아래 `기본값`의 담당자 선정으로 고른 사람이 그대로 구현할 수 있게 티켓을 완성해 넘긴다. 이 절의 `담당자`는 그 선정 결과를 말한다.
  - 착수 입력이나 핸드오프 브리핑에 티켓 키가 있으면 그 티켓을 아래 `티켓 본문`대로 채우고 담당자를 바꾼다.
  - 브리핑이나 사용자가 생성을 이미 지시했으면("티켓 없으면 생성") 아래 기본값으로 만든다.
  - 둘 다 없으면 위 `티켓 생성` 원칙대로 만들지 않는다. 푸시 권한이 없다는 사실, 티켓 초안, 담당자 후보와 근거를 제시하고 지시를 기다린다.
- 조회가 인증이나 네트워크 오류로 실패하거나, 원격이 GitHub가 아니거나, 응답에 `permissions`가 없으면 권한을 짐작하지 않는다. 실패 메시지를 그대로 보여 주고 되묻는다.

**기본값**

- 프로젝트 `AX`, 이슈 유형 `작업`(id `10839`)
- 보고자는 나(`GET /rest/api/3/myself`의 accountId)다. HDIT와 달리 되묻지 않는다.
- 담당자는 두 근거로 고른다.
  - 그 기능을 들인 티켓의 담당자. 바꿀 파일의 `git log --format='%h %s' -- <파일>`에서 티켓 키(`AX-320` 등)를 찾고, 그 티켓의 `assignee`를 조회한다.
  - 저장소의 최근 머지 PR 작성자. `gh pr list -R <owner>/<repo> --state merged --limit 10 --json number,author,title`로 본다.
  - 두 근거가 같은 사람을 가리키면 그 사람으로 한다. 갈리거나, 후보가 여럿이거나, 한쪽 근거를 찾지 못하면 찾은 근거를 붙여 되묻는다.
  - Jira accountId는 기능 티켓의 `assignee.accountId`를 쓴다. 그 티켓이 없어 사람 이름만 정해졌으면 `GET /rest/api/3/user/search?query=<이름>`으로 찾고, 결과가 하나가 아니면 되묻는다. 예: AX-370, AX-371은 기능을 들인 AX-320의 담당자이자 최근 PR #59~#61 작성자인 복영균이었다.
- 팀, 스프린트, 컴포넌트, SP는 넣지 않는다. 2026-10-28 AX `작업` 생성 화면(createmeta)에 스프린트(`customfield_10020`)와 SP(`customfield_10028`) 필드가 없고, AX-371 수정 화면(editmeta)에도 SP가 없다. 팀(`customfield_10001`) 필드는 있지만 정한 값이 없다.
- `SP 산정`은 하지 않는다. 필드가 없을 뿐 아니라 `estimate_sp.py --sp`는 담당자가 내가 아니면 기입을 건너뛴다(`collect.write_allowed`). `chucoding` 플러그인의 Stop 훅(`sp-estimate-guard.py`)도 `project = HDIT`만 조회하므로 AX 티켓으로 턴 종료를 막지 않는다.
- 생성 뒤에는 위 항목(프로젝트, 이슈 유형, 보고자, 담당자)을 다시 조회해 확인한다.

### 티켓 본문

티켓 설명은 사용자와 담당자가 Jira 화면에서 바로 읽는 문서다. 적용 범위는 아래와 같다.

- 다른 팀 저장소 티켓: 이 절 전부
- `chucoding:dev-ticket-design`으로 만드는 HDIT 개발 티켓: `표 대신 쓰는 형식`, `다이어그램`, `AS-IS와 TO-BE는 항상 좌우`만. 설명 순서와 근거, 초안 승인은 그 스킬 5단계를 따른다. 그 스킬의 생성 승인 초안이 `수정 전 초안 검토`를 대신하므로 승인을 두 번 받지 않는다.
- 그 밖의 티켓(일반 HDIT 생성, 기존 설명 수정): `수정 전 초안 검토`, `표 대신 쓰는 형식`, `다이어그램`, `AS-IS와 TO-BE는 항상 좌우`. 절 구성은 사용자 요청을 따른다.

 2026-10-28 AX-370, AX-371에서 사용자가 같은 수정을 반복 요청한 내용을 기본 형식으로 정한다. "리치하게 구성하되 표는 사용하지마", "AS-IS, TO-BE는 항상 위아래가 아닌 왼쪽, 오른쪽", "머메이드로 변경해줘. 색상만 유지", "근거없는거면 빼줘"가 그 요청이다.

**수정 전 초안 검토**

- 설명을 새로 쓰거나 고치기 전에 초안 전문을 대화에 출력하고 승인받는다. 사용자가 매번 요청하지 않아도 기본으로 한다.
- 출력 방식은 `게시 전 전문 출력`과 같다. 전문을 선택지 질문 밖의 본문으로 먼저 출력하고, 선택지 질문 안에는 출력한 내용을 가리키기만 한다. 다이어그램은 렌더한 PNG의 전체 경로와 Mermaid 원본을 함께 보인다.
- 사용자가 고치게 하면 고친 전문을 다시 출력하고 다시 승인받는다.
- `SP 산정`의 `estimate_sp.py --note`가 설명 끝에 붙이는 근거 문단은 검토 대상이 아니다. 그 근거는 `SP 산정` 보고에 이미 드러난다.

**구성**

- 다른 팀 저장소 티켓은 `문제`(또는 `배경`), `변경`, `바꾸지 않는 것` 세 절로 쓴다.
- `참고 구현`, `호출 쪽 반영`, `수용 기준`, `구현 상태`, `참고` 절은 넣지 않는다. 사용자가 두 티켓 모두에서 불필요하다고 뺐다.
- 근거는 출처 링크로 확인되는 것만 넣는다. 링크를 열어 출처가 그 주장을 직접 말하는지 확인하고, 직접 뒷받침하지 않으면 빼고 뺐다는 사실을 초안과 함께 알린다. AX-371에서 CodeRabbit 공식 문서는 병렬 에이전트까지만 말했고, 결과를 모아 반환한다는 내용은 제3자 글에만 있어 뺐다.

**표 대신 쓰는 형식**

- ADF `table` 노드를 쓰지 않는다. 부피가 크고 열 폭이 같아 보기 좋지 않다는 것이 사용자 판단이다. v2 위키 마크업으로 쓸 때도 `||`, `|` 표 문법을 쓰지 않는다.
- 제목(`heading`), 글머리 목록, `panel`, 굵은 글씨로 구성한다. 비교는 아래 좌우 배치나 목록으로, 나열은 목록으로 바꾼다.

**다이어그램**

- drawio 도형으로 그리지 않고 Mermaid로 그려 PNG로 첨부한다. 핵심 노드만 남긴다.
- 이 절의 `classDef`와 `TB`, `LR` 규칙은 `flowchart`에만 적용된다. 설명에 `sequenceDiagram`을 넣을 때와 PR, 개발완료 댓글에 넣는 AS-IS와 TO-BE `sequenceDiagram`은 `chucoding:screen-evidence`의 `시퀀스 다이어그램`을 따른다. 렌더 명령과 세 색 값은 이 절과 같게 유지하고, 바꿀 때는 두 곳을 함께 고친다.
- 렌더는 drawio CLI의 Mermaid 변환을 쓴다. AX-371 PNG를 이 명령으로 만들었다. `drawio`가 없으면 다른 렌더 수단을 짐작해 고르지 않고 되묻는다. 크기는 `sips -g pixelWidth -g pixelHeight <png>`로 잰다.

  ```bash
  drawio -x -f xml --mermaid-image 1 -o <이름>.drawio <이름>.mmd \
    && drawio -x -f png -e -b 10 -s 2 -o <이름>.png <이름>.drawio
  ```

- 색상은 아래 세 가지만 쓴다.

  ```
  %% 바뀐 부분
  classDef changed fill:#fff2cc,stroke:#d6b656,stroke-width:3px,color:#000
  %% 효과
  classDef good fill:#d5e8d4,stroke:#82b366,stroke-width:3px,color:#000
  %% 문제
  classDef pain fill:#f8cecc,stroke:#b85450,stroke-width:2px,color:#000
  ```

- 방향은 놓일 자리로 정한다. AS-IS와 TO-BE처럼 좌우 반쪽 칸에 들어가는 차트는 `flowchart TB`, 전체 폭에 혼자 놓이는 차트는 `flowchart LR`이다. 2026-10-28에 AX-371 원본을 반쪽 칸 폭 442px(HDIT-4229 실측)로 렌더해 비교했을 때, `LR`로 그린 6단 TO-BE는 442×125로 줄어 글자를 읽을 수 없었고 `TB`는 두 칸 모두 원래 크기로 읽혔다. 사용자가 이 기준을 골랐다.
- 그래도 작게 보이면 나눈다. 전체 폭 `LR` 차트가 단계가 많아 축소되면 두 장으로 나눈다. 반쪽 칸의 `TB` 차트는 한 단에 나란히 놓인 노드 수가 폭을 정하므로 그 수를 줄인다.
- Mermaid 원본은 본문에 펼쳐 두지 않는다. 다이어그램 아래 최상위에 `expand` 노드(`attrs.title`은 `Mermaid 원본`)를 두고 그 안에 `codeBlock`으로 접어 넣는다. `layoutColumn` 안에 넣지 않는다. AS-IS와 TO-BE를 좌우로 둔 경우에는 `layoutSection` 뒤에 `expand` 하나를 두고 AS-IS, TO-BE 원본을 그 순서로 넣는다.
- PNG 첨부와 media 노드 만들기는 `chucoding:screen-evidence`의 `미디어 블록 만들기`와 같은 v2에서 v3로 다시 쓰는 방식을 쓴다. 댓글 대신 설명에 적용해 `PUT /rest/api/2/issue/<키>`의 `fields.description`에 승인받은 설명 전문을 위키 마크업으로 담고, 다이어그램 자리에 `!<파일명>|width=<w>,height=<h>!`를 넣는다. 그다음 다시 읽은 media id로 v3 설명 전체를 쓴다. AX-371도 v2 본문에 `h2.` 제목과 문단, 이미지 마크업을 함께 담았다.
- 설명 전체를 덮어쓰므로 쓰기 전에 현재 설명(`fields=description`)을 읽어 스크래치패드에 JSON으로 저장한다. SP를 기입할 때 붙은 근거 문단(`SP 산정`에서 넘긴 `--note` 문구, 폴러가 쓴 `SP 추정`으로 시작하는 문단)이 설명 끝에 있으면 v2와 v3 본문 끝에 그대로 다시 붙인다.
- v2 쓰기 뒤 단계에서 실패하면 다시 시도하지 않는다. v2로 쓴 설명이 남아 있다는 사실, 실패한 단계, 저장한 이전 설명 파일의 전체 경로를 보고한다.

**AS-IS와 TO-BE는 항상 좌우**

- `layoutSection` 하나에 `width` 50인 `layoutColumn` 두 개를 두고 왼쪽에 AS-IS, 오른쪽에 TO-BE를 넣는다. 위아래로 쌓지 않는다.
- 놓는 자리는 티켓 종류로 정한다. 다른 팀 저장소 티켓은 `변경` 절 안의 변경 설명 목록 뒤에 둔다. `chucoding:dev-ticket-design` 티켓은 `배경` 절 끝에 둔다. 그 밖의 티켓은 변경 내용을 설명하는 절 끝에 두고, 그런 절이 없으면 초안에 자리를 적어 승인받는다.
- AS-IS가 없는 신규 흐름이면 `layoutSection` 없이 `TO-BE` 캡션과 `mediaSingle` 하나만 두고, 전체 폭이므로 `LR`로 그린다.
- 각 칸은 캡션 paragraph와 `mediaSingle`(`layout: center`, `width: 100`, `widthType: percentage`)이다. JSON 구조는 `chucoding:screen-evidence`의 `미디어 블록 만들기`에 있는 `layoutSection` 예시를 그대로 쓴다.
- 칸 안의 차트는 위 `다이어그램`대로 `TB`로 그린다. 두 칸의 높이가 달라도 칸을 위아래로 바꾸지 않는다.

## 상태 전환

- 티켓 상태 전환은 티켓 생성 규칙과 별개로 판단한다. 생성은 명시적 요청이 있을 때만 하지만, 상태 전환은 작업 흐름에서 정해진 시점에 수행한다.
- PR 생성 후 `리뷰중` 전환은 `chucoding:commit-pr` 스킬의 `7. PR 생성 후 티켓 상태 전환`을 따른다. 브랜치 이름의 키가 HOM이면(`착수 브랜치 이름`의 QA 클론) 전환 대상은 그 HOM과 Cloners로 연결된 HDIT 티켓이다. HOM 워크플로에는 `리뷰중`이 없으므로 HOM에서 전환을 찾지 않고 HDIT만 전환한다. 연결된 HDIT가 둘 이상이면 착수 입력이나 현재 대화에 나온 HDIT 키가 후보 안에 있을 때 그 티켓을 쓰고, 없을 때만 되묻는다. HOM으로 직접 착수해 연결된 HDIT가 없으면 전환하지 않고 그 사실을 알린다.
- PR 머지를 확인하고 `개발완료`로 전환할 때는 `gh pr view <PR URL> --json state`로 머지 여부를 조회한다. 번호만 쓰면 현재 저장소의 PR로 해석되므로 URL이나 `--repo <owner>/<repo>`로 지정하고, 티켓의 PR이 여럿이면 PR마다 조회한다.
- 이슈 유형이 `QA_Bug`인 HDIT는 HDIT 안에 있어도 별도 워크플로를 쓴다. 상태는 `open`, `진행 중`(changelog에는 `In Progress`), `resolve`, `DONE`, `REOPEN`, `Known Issue`, `Won't Do`이고 `개발중`, `리뷰중`, `개발완료`, `Backlog`가 없다. HOM과 비슷하지만 전환 이름과 종류가 달라 HOM 규칙을 그대로 쓰지 않는다. `진행 중`에서 나가는 전환은 `개발 완료`(도착 `resolve`), `확인 완료`(`DONE`), `재오픈`(`REOPEN`), `기존 이슈로 분류`(`Known Issue`), `수정 안 함`(`Won't Do`)이다(2026-10-21 실측).
  - 착수 전환은 전환 목록에서 도착 상태가 `진행 중`인 것을 고른다. `open`에서는 `개발 시작`이다. QA가 재오픈한 `REOPEN`에서 다시 착수할 때도 같은 기준으로 고르고, 그런 전환이 없으면 임의로 고르지 말고 알린다. homedot-cloud-devteam `ticket-start`의 HOM↔HDIT 동기화는 HOM 링크가 없으므로 적용되지 않는다.
  - PR 생성 후 `리뷰중` 전환은 하지 않고 그 사실만 알린다.
  - 머지를 확인한 완료 처리는 전환 이름 `개발 완료`(도착 상태 `resolve`)로 한다. 이 스킬에서 `개발완료` 전환이라고 쓴 곳은 QA_Bug에서 이 전환으로 읽는다.
  - 이 전환 전에 아래 `QA_Bug 처리결과 필드`의 세 필드(발생원인 `customfield_10859`, 조치내용 `customfield_10860`, 영향범위 `customfield_10861`)를 채운다. 비어 있으면 전환이 `400 {"errorMessages":["내용을 입력해주세요."],"errors":{}}`로 거부된다(HDIT-5920, 2026-11-04 실측). 전환 검증기가 이슈 필드를 검사하는 것이라 `GET .../transitions?expand=transitions.fields`에는 이 필드가 나오지 않는다. 전환 목록 조회로는 요구 사항을 알 수 없으므로 필드 id로 직접 확인한다.
  - `확인 완료`(도착 `DONE`)와 `재오픈`은 QA가 검증하고 옮기는 전환이므로 하지 않는다. `기존 이슈로 분류`와 `수정 안 함`은 QA와 합의가 필요한 판정이라 사용자가 지시할 때만 한다.
  - 재오픈 뒤 다시 `resolve`로 옮기면 그때도 `원본 티켓 완료 댓글`의 `QA_Bug 티켓`대로 완료 댓글을 새로 남긴다. QA는 그 알림으로 재검증을 시작한다. 재작업으로 화면이 바뀌었으면 `chucoding:screen-evidence`대로 TO-BE를 다시 남기고, 바뀌지 않았으면 증빙 미디어 없이 멘션 문단과 본문만 남긴다. 첫 댓글에 이미 같은 증빙이 있어서다.
- 상태 전환은 상태 필드만 바꾼다. 티켓에 배정된 스프린트는 지난 스프린트라도 그대로 두고, `티켓 생성`의 활성 스프린트 기본값을 적용하지 않는다.
- 스프린트가 비어 있는 백로그 티켓만 예외다. 활성 스프린트(`sprint in openSprints()`)와 다음 스프린트(`sprint in futureSprints()`)를 조회해 어느 레인에 넣을지 되묻고, 임의로 활성 스프린트에 넣지 않는다.

### QA_Bug 처리결과 필드

QA_Bug를 `resolve`로 옮기기 전에 채우는 세 필드다. QA가 티켓에서 읽는 처리 결과이므로 외부 게시물로 다룬다. 다른 사람이 처리한 QA_Bug도 세 필드를 채운 뒤 `resolve`로 옮겼다(HDIT-5969, HDIT-5904 changelog).

| 필드 | id | 쓰는 내용 | 형식 |
|------|------|------|------|
| 발생원인 | `customfield_10859` | 무엇이 어떻게 동작해 결함이 났는지 | 문단 1개 |
| 조치내용 | `customfield_10860` | 바꾼 동작과 PR | 글머리 목록. 바꾼 동작 항목들 뒤에 PR마다 `PR: <owner 뺀 저장소>#<번호>` 항목을 하나씩 두고, PR 항목에는 그 PR URL 링크 mark를 단다 |
| 영향범위 | `customfield_10861` | 바뀐 화면과 레이어(FE, BE). 영향 없는 범위는 손대지 않은 다른 화면이나 레이어만 한 줄로 | 문단 1개 |

- 세 필드 모두 textarea이고 값은 ADF doc(`{"type":"doc","version":1,"content":[...]}`)이다. `PUT /rest/api/3/issue/<HDIT키>`의 `fields`에 한 번에 넣는다. 성공은 204다. 문단은 `paragraph`, 목록은 `게시 절차` 4단계와 같은 `bulletList` > `listItem` > `paragraph` 구조다. PR 항목의 문단은 아래처럼 만든다.

  ```json
  {"type": "paragraph", "content": [
    {"type": "text", "text": "PR: "},
    {"type": "text", "text": "hd-cloud-client#2817", "marks": [{"type": "link", "attrs": {"href": "https://github.com/dev-rsquare/hd-cloud-client/pull/2817"}}]}
  ]}
  ```

- 먼저 `GET /rest/api/3/issue/<HDIT키>?fields=customfield_10859,customfield_10860,customfield_10861`로 현재 값을 읽는다. 값이 있는 필드는 덮지 않고, 빈 필드만 채운다. 값이 `null`이거나 안쪽까지 훑어 공백 아닌 `text` 노드가 하나도 없으면 빈 필드로 본다. 셋 다 차 있으면 기입 없이 전환한다. 재오픈 뒤 다시 `resolve`로 옮길 때 재작업 내용을 더할지는 사용자가 지시할 때만 한다.
- 작성 근거는 `댓글 형식`의 **PR**에서 찾은 PR의 본문과 커밋, 그 HDIT의 제목과 설명(`fields=summary,description`)이다. 근거에 없는 원인이나 영향은 지어내지 않는다. PR 본문과 커밋은 사실을 확인하는 근거일 뿐 문장을 옮겨 오는 출처가 아니다. 둘 다 개발자용이라 그대로 옮기면 개발자 말이 되므로, 확인한 사실을 아래 `QA가 읽는 말로 쓰기`대로 다시 쓴다. PR 항목의 URL은 `댓글 형식`의 PR 조회(`gh pr view`)에 `--json`의 `url` 필드를 더해 읽고, 저장소 이름은 그 URL 경로에서 owner 다음 부분을 쓴다. 그 절차에서 머지된 후보가 여럿이면 되묻지 않고 전부 근거로 쓰고 조치내용에 PR 항목을 하나씩 둔다. 이 필드는 티켓의 처리 결과 전체를 적는 곳이기 때문이다. 다른 저장소의 PR(예: FE와 디자인 시스템)은 `gh pr list --repo <owner>/<repo> --state merged --search <키>`로 찾고, 어느 저장소인지 대화와 브랜치에서 알 수 없으면 되묻는다. PR을 찾지 못했거나 원인을 근거에서 판단할 수 없으면 되묻는다.
- 예시(HDIT-5920)
  - 발생원인: `퇴사 정보 모달과 직원 상세의 퇴직일 입력은 오늘 이후 날짜를 직접 입력하면 오류 툴팁만 띄우고 값은 그대로 넘겼음. 그래서 모달의 저장 버튼이 켜진 채 남아 미래 퇴직일로 저장됐음.`
  - 조치내용: 바꾼 동작 목록과 `PR: hd-cloud-client#2817`
  - 영향범위: 바뀐 화면과 FE, BE 중 어느 쪽인지를 한 문단으로. 영향 없는 범위는 손대지 않은 다른 화면이나 레이어만 한 줄로 덧붙인다
- QA가 읽는 말로 쓰기: 세 필드를 읽는 사람은 QA다. 이 규칙은 아래 `댓글 형식`의 **HOM 본문**(`[추가로 수정된것]` 목록)에도 똑같이 적용하며, 정본은 여기다.
  - 화면, 메뉴, 버튼, 입력값, 사용자가 하는 조작과 그 결과로 보이는 것으로 쓴다.
  - 라이브러리, 프레임워크, 함수, 변수, 컴포넌트, 파일 이름, API 경로를 쓰지 않는다. 상태 구독, 렌더, 키, 인덱스 같은 개발 개념도 쓰지 않고 화면에서 보이는 말로 풀어 쓴다(예: "행 위치 기준" → "몇 번째 줄인지로", "행 고유 키로 기록" → "행마다 따로 기록").
  - 코드 수준 원인은 PR에 이미 있으므로 필드에 옮기지 않는다.
  - 전문을 출력하기 전에 세 필드와 HOM 본문의 `[추가로 수정된것]` 목록에 영문 식별자나 괄호 `()`가 붙은 이름이 남았는지 점검하고, 있으면 고친다. 멘션, cc, 증빙 머리 문단, 미디어 캡션은 점검 대상이 아니다. 조치내용의 `PR: <저장소>#<번호>` 항목, 영향범위의 FE와 BE 표기, 화면에 영문 그대로 보이는 메뉴나 버튼 이름은 점검 대상이 아니다.
  - 나쁜 예(HDIT-6357 발생원인, 2026-11-10 사용자 지적 "react-hook-form은 QA가 봐도 모를것 같은데 QA눈높이로 다시 작성해줘"): `이름 칸 필수 입력 오류 표시를 행 위치 기준의 '건드림' 상태로 판정했음. react-hook-form 의 move()는 이 화면이 구독하지 않은 건드림 상태를 행과 함께 옮기지 않아, ...`
  - 고쳐 쓴 예: `'이름 칸을 건드렸다'는 기록을 그 행이 아니라 몇 번째 줄인지로 저장하고 있어서, 행을 드래그, 순서 이동 메뉴, 순서 칸 입력으로 옮기면 기록은 원래 줄에 남고 옮긴 행은 아직 건드리지 않은 행처럼 보였음. 그래서 옮긴 행의 문구와 테두리가 함께 사라졌음.`
  - 같은 날 조치내용에도 `행 고유 키로 기록해`처럼 개발 개념이 섞였다. 발생원인만이 아니라 세 필드 모두 점검한다.
  - 같은 화면에서 바뀌지 않은 동작을 하나씩 늘어놓지 않는다. QA는 늘어놓은 동작을 다시 확인할 범위나 남은 결함으로 읽는다. 영향 없는 범위는 손대지 않은 다른 화면이나 레이어(FE, BE)를 밝히는 데까지만 쓴다.
  - QA가 지적하지 않았고 일부러 범위 밖으로 둔 동작은 세 필드와 HOM 본문에 쓰지 않는다. 범위 밖으로 둔 근거는 PR 본문에 둔다.
  - 나쁜 예(HDIT-6429 영향범위, 2026-11-11 사용자 지적 "이 문장은 더 헷갈리기만하고 불필요한 정보인거 같은데? 제거하고 올리도록하고 요거 스킬 보강 필요한지 검토해줘."): `... FE만 바뀌었음. 사용 중인 행의 순서 변경, 저장 동작, 다른 행을 옮길 때 사용 안 함 행의 번호가 함께 밀리는 동작은 바뀌지 않았음.` 둘째 문장은 같은 화면의 바뀌지 않은 동작을 늘어놓았고, PR에서 일부러 범위 밖으로 둔 동작(다른 행을 옮기면 사용 안 함 행 번호가 밀림)까지 담아 QA에게는 결함이 남은 것으로 읽혔다.
  - 고쳐 쓴 예: `직원정보 > 부서·직위 설정 패널의 부서 탭과 직위 탭(우리 회사에 적용, 관리하는 단지에 적용 모두)에 해당하며 FE만 바뀌었음.`
- 기입 전에 채울 필드마다 필드 이름과 전문을 코드 블록으로 대화에 출력한다. `게시 전 전문 출력`과 같은 이유로 요약으로 대신하지 않는다. 완료 처리 요청이나 PR 머지 확인을 기입 승인으로 보고 승인은 다시 묻지 않는다. 출력한 뒤 바로 기입한다. 기입 뒤 사용자가 문구를 고치게 하면 고친 전문을 다시 출력하고 그 필드를 다시 쓴다. 이번 작업에서 이 스킬이 쓴 값을 고치는 것이므로 위의 덮지 않는다는 규칙의 예외다. 다른 사람이 쓴 값은 사용자가 지시해도 고치기 전에 기존 값을 보여 준다.
- 기입이 실패하면 재시도하지 말고 응답 상태와 오류 메시지를 보고하고, 전환과 완료 댓글로 넘어가지 않는다.
- 세 필드를 전환 요청의 `update.comment` 같은 댓글로 대신하지 않는다. 멘션 없는 댓글이 하나 더 생겨 `QA_Bug 티켓`의 댓글 하나로 합치는 규칙(HDIT-4857)과 어긋난다.

## 원본 티켓 완료 댓글

HDIT 티켓을 `개발완료`로(`QA_Bug`는 `resolve`로) 바꾸면, 그 티켓의 원본 티켓에 완료 댓글을 남긴다. 원본은 세 가지다.

- Cloners로 연결된 QA 티켓 HOM
- QA가 HDIT에 직접 올린 `QA_Bug`. 그 티켓 자신을 QA 원본으로 본다(아래 `QA_Bug 티켓`).
- PM이나 운영이 올린 스토리 원장. 작업 티켓이 `연결됨`이나 `관련됨`으로 이어진 이슈 유형 `스토리` 티켓이다(아래 `원장 완료 댓글`).

원장이 없으면 화면 증빙이 있을 때 HDIT 티켓 자신에도 아래 `HDIT 증빙 댓글`을 남긴다. 원장이 있으면 남기지 않는다. 기획 티켓 HC는 더 이상 원본으로 쓰지 않으므로 완료 댓글을 남기지 않는다.

| 원본 | 읽는 사람 | 멘션 대상 | 첫 줄 문구 | 본문 제목 |
|------|------|------|------|------|
| HOM | QA | HOM 보고자 | `수정 완료되었습니다.` | `[추가로 수정된것]` |
| HDIT `QA_Bug` | QA | 그 HDIT 보고자 | `수정 완료되었습니다.` | `[추가로 수정된것]` |
| 원장(스토리) | PM, 운영 | 매번 묻는다. 기본 후보는 원장 담당자 | `완료되었습니다. 개발 서버에서 확인 부탁드립니다.` | `[기획 외 추가 적용]` |

- 원본 티켓은 완료 처리한 HDIT를 `GET /rest/api/3/issue/<HDIT키>?fields=issuelinks,description,issuetype`으로 읽어 정한다. 이 한 번의 조회로 HOM 원본, `QA_Bug` 해당 여부, 원장 후보, 남은 파생 티켓을 모두 판정한다.
  - HOM: `issuelinks` 중 링크 유형이 `Cloners`이고 상대 티켓의 프로젝트 키(링크된 티켓 키의 `-` 앞 접두사)가 `HOM`인 것이다. 링크 방향(`clones`, `is cloned by`)은 가리지 않는다.
  - `QA_Bug`: 응답의 `issuetype.name`으로 판정한다.
  - 원장 후보: 아래 `원장 판정`대로 고른다.
- 원본 티켓(HOM, `QA_Bug`, 원장)이 모두 없으면 원본 댓글을 남기지 않는다. `QA_Bug`는 그 HDIT 자신이 원본이므로 Cloners로 연결된 HOM 원본이 없어도 아래 `QA_Bug 티켓`의 합친 댓글을 남긴다. 아래 `HDIT 증빙 댓글`은 원장이 없을 때만 남긴다. 원장이 있으면 증빙은 원장 댓글에만 넣는다. QA와 PM이 읽는 곳은 원장이고, 작업 티켓 댓글은 아무도 읽지 않는다는 것이 사용자 판단이다(2026-11-06). 단 `QA_Bug`는 증빙을 아래 `QA_Bug 티켓`의 합친 댓글 하나에만 넣고 따로 남기지 않는다. 같은 프로젝트의 원본이 2개 이상이면 임의로 고르지 말고 어느 티켓에 남길지 되묻는다.
- 원장이 HOM이나 `QA_Bug`와 함께 있으면 각 원본의 댓글을 따로 남긴다. HOM 댓글과 `QA_Bug`의 합친 댓글은 QA가 받는 알림이라 원장 유무와 관계없이 그대로 남기고, HDIT 증빙 댓글만 뺀다.
- 사용자의 완료 처리 요청이든, PR 머지를 확인하고 에이전트가 스스로 전환한 경우든 똑같이 댓글을 남긴다. HOM 원본 댓글은 `개발완료` 전환 자체를 댓글 게시 승인으로 보고 게시 승인은 다시 묻지 않는다. 아래 `HDIT 증빙 댓글`과 `QA_Bug`의 `resolve` 전환과 합친 댓글도 같다. 원장 댓글만 예외로, 전환을 게시 승인으로 보지 않고 아래 `원장 완료 댓글`대로 매번 검수받는다. 승인을 묻지 않아도 아래 `게시 전 전문 출력`은 생략하지 않는다. 단 아래에서 대상이나 본문이 정해지지 않을 때의 되묻기는 따른다. 증빙 파일을 보관 폴더가 아니라 PR에서 다시 받았으면 이 승인에 들어가지 않으므로, `chucoding:screen-evidence`의 재다운로드 절차대로 게시 전에 묻는다.
- 순서는 원장 후보 찾기와 남은 파생 티켓 확인(전환 전 한 번의 조회), `개발완료` 전환, 원장 후보 확정, HDIT 증빙 댓글(원장이 없을 때만), HOM 원본 댓글, 원장 완료 댓글, 위키 정리 질문(전역 AGENTS.md `완료 처리 후 위키 정리`)이다. 컴팩션 뒤 이 스킬을 다시 불러도 원장 판정을 빠뜨리지 않도록 첫 단계로 둔다.
- `QA_Bug`는 원장 후보 찾기와 남은 파생 티켓 확인, 처리결과 세 필드 기입(`QA_Bug 처리결과 필드`), `resolve` 전환, 원장 후보 확정, 합친 완료 댓글, 원장 완료 댓글(원장이 있을 때만), 위키 정리 질문 순이다.
- 남은 파생 티켓 확인은 전환하기 전에 위 원본 판정 조회를 먼저 해서 그 `issuelinks`로 한다. 전환 뒤에 읽으면 원장 완료 자동화가 이미 파생 티켓을 완료로 바꿔 놓아 남은 티켓이 보이지 않는다. 링크 유형이 `Discovery - Connected`이고 상대가 `outwardIssue`(`connects to <상대>`)인 티켓을 고르고, 그중 `status.statusCategory.key`가 `done`이 아닌 것의 키와 상태를 전환 직전에 사용자에게 알린다. 전환을 막거나 묻지는 않는다. 해당 링크가 없으면 완료하는 티켓 자신이 파생 티켓을 거느린 원장이 아니므로 알리지 않는다.

### 원장 판정

원장은 PM이나 운영이 요청을 모아 둔 스토리 티켓이고, 개발 티켓은 그 원장에서 나온 후속 티켓이다. 2026-10-30(HDIT-5463의 원장 HDIT-4990)과 2026-11-06(HDIT-5719의 원장 HDIT-4517)에 에이전트가 HOM이 없다는 이유로 원본이 없다고 보고 원장 댓글을 빠뜨렸다. 그래서 완료 처리의 첫 조회에서 원장을 함께 판정한다.

이 절의 원장은 완료하는 작업 티켓의 상위 스토리다. 위 `남은 파생 티켓 확인`은 완료하는 티켓 자신이 원장으로 쓰여 파생 티켓을 거느린 경우를 보는 것이라 대상이 다르다.

- 후보는 위 원본 판정 조회의 `issuelinks`에서 아래 두 조건을 모두 만족하는 상대 티켓이다. `issuelinks`의 상대 티켓에는 `fields.issuetype`과 `fields.status`가 들어 있으므로 후보를 고르는 데는 조회를 더 하지 않는다. 보고자와 담당자는 들어 있지 않으므로, 후보가 있으면 후보 키마다 `GET /rest/api/3/issue/<키>?fields=summary,assignee,reporter`로 읽는다.
  - 링크: 유형이 `Discovery - Connected`이고 링크 객체에 상대가 `inwardIssue`로 들어 있는 것(작업 티켓이 `is connected to <원장>`), 또는 유형이 `Relates`인 것(방향 무관). 2026-11-05 이후 티켓은 `Discovery - Connected`, 그 전 티켓은 `Relates`로 이어져 있다.
  - 유형: 상대 티켓의 `issuetype.name`이 `스토리`다.
- 작업 티켓 설명의 `요청 출처:` 뒤에 적힌 키(`chucoding:dev-ticket-design` 5단계가 쓴다)가 후보 안에 있으면 그 티켓을 첫 후보로 둔다.
- 후보는 하나뿐이어도 항상 사용자에게 보여 주고 확정받는다. `Relates`와 `스토리` 조건에 무관한 스토리가 걸린 사례가 있다(HDIT-5458과 HDIT-4386). 보여 줄 때는 키, 제목, 링크 유형과 방향, 보고자, 담당자를 함께 적는다. 후보 찾기는 전환 전 조회에서 하되 확정은 전환 뒤, 댓글 단계 전에 받는다. 확정 질문으로 전환을 막지 않기 위해서다. 사용자가 원장이 아니라고 하면 원장이 없는 것으로 보고 진행한다.
- 후보가 없으면 원장이 없는 것으로 보고 묻지 않는다.
- 원장에는 배포 티켓이 `Tasks` 링크로 걸린다(HDIT-4517의 HDIT-6140 `[QA][클라우드][RFMS] 정기배포 #13`). 위 링크 조건에 들지 않으므로 후보가 되지 않는다.

**원장이 있는 작업의 검토 요청**

원장이 있는 작업에서 PM이나 운영에게 하는 검토 요청과 멘션은 완료 처리가 아니어도 PR 코멘트가 아니라 원장 Jira 댓글이 기본이다. PM과 운영은 PR을 보지 않는다. 2026-11-05 HDIT-6136 작업에서 PM 검토 요청을 PR 코멘트로 보냈다가 사용자가 "아니 PR이 아니라 원장티켓에 댓글 말한거야"라고 고쳤다. 원장 후보는 그 시점에 작업 티켓을 위 조회로 읽어 같은 조건으로 찾고 사용자에게 확정받는다. 어디에 남길지 모호하면 묻는다. 멘션 대상과 본문은 매번 묻고, 아래 `원장 완료 댓글`의 형식을 쓰지 않는다. 게시는 `게시 전 전문 출력`과 `게시 절차`의 멘션과 ADF 규칙을 따르고, 게시 승인은 따로 받는다.

### QA_Bug 티켓

2026-10-15부터 QA는 HOM 대신 HDIT에 이슈 유형 `QA_Bug`로 결함을 직접 올린다(첫 티켓 HDIT-4402). HOM 신규 등록은 2026-09-21의 HOM-2481이 마지막이다. QA_Bug에는 HOM 클론이 없어 위 Cloners 판정으로는 원본이 잡히지 않는다. 그래서 QA가 지적한 결과를 확인하는 그 티켓 자신을 QA 원본으로 본다.

- 판정은 위 원본 판정 조회에서 읽은 이슈 유형(`issuetype.name`)이 `QA_Bug`인지로만 한다. 보고자로 판정하지 않는다. 보고자가 내가 아닌 `작업_개발`에는 기획, 디자인QA, 리드가 올린 티켓이 섞여 있고, QA가 아닌 사람도 `QA_Bug`를 올린다. QA 인원은 Jira 그룹으로도 구분되지 않는다.
- 문구와 본문은 위 표의 HOM 형식을 따른다. 멘션 대상은 그 HDIT의 보고자(`reporter`)이고, 비어 있거나 나이면 `댓글 형식`대로 되묻는다. `HOM 본문`의 "QA가 지적한 문제"는 그 HDIT의 제목과 설명으로 판단한다.
- cc는 쓰지 않고 `(cc. ...)`를 생략한다. 아래 `댓글 형식`의 cc 규칙은 원본의 Cloners HDIT를 전제로 하는데, QA_Bug는 그 HDIT 자신이 원본이다.
- 아래 `HDIT 증빙 댓글`과 따로 두지 않고 하나로 합친다. 같은 티켓에 두 댓글이 달리면 QA가 멘션 없는 증빙 댓글만 보고 검증하고, 완료 알림은 가지 않는다(HDIT-4857). 합친 댓글은 멘션 문단, `[추가로 수정된것]`과 목록, 증빙 머리 문단(`[개발완료]`와 `테스트방법 :` 두 줄), 미디어 블록 순이다. 화면 증빙과 함께 시퀀스 다이어그램을 남겼으면 미디어 블록에 화면 미디어 아래로 포함한다. 다이어그램만 남겼으면 증빙이 없는 것과 같이 다룬다(`chucoding:screen-evidence`의 `다이어그램을 넣는 범위`). 증빙이 없으면 앞의 두 부분만 남기고, 추가로 수정된 것이 없으면 그 제목과 목록을 뺀다.
- 게시는 `게시 전 전문 출력`과 `게시 절차`를 따르되 원본 키 자리에 그 HDIT 키를 쓴다. 증빙 파일은 댓글 하나에 한 번만 첨부한다. HDIT 증빙 댓글과 원본 댓글에 같은 파일을 두 번 붙이지 않는다는 뜻이다.
- 남아 있는 HOM 티켓(2026-10-21 기준 열린 HOM 6건)을 위해 HOM Cloners 경로는 그대로 둔다.

### HDIT 증빙 댓글

PR을 만들 때 `chucoding:screen-evidence`로 GIF나 이미지 증빙을 남겼으면, `개발완료`로 바꾼 HDIT 티켓에 그 파일을 담은 댓글을 남긴다. QA와 기획자가 PR을 열지 않고도 티켓에서 변경 전후를 보게 하려는 것이다. 원본(HOM)이 없는 HDIT 단독 작업에도 남긴다. 위 `원장 판정`으로 원장이 확정된 작업에는 남기지 않고, 증빙은 아래 `원장 완료 댓글`에만 넣는다. `QA_Bug`는 위 `QA_Bug 티켓`대로 완료 댓글과 합쳐 하나로 남긴다.

- 증빙을 남겼는지는 `chucoding:screen-evidence`의 보관 폴더(HDIT 키 폴더, 없으면 연결된 HOM 키 폴더)로 판정한다. 폴더의 `meta.txt`에 적힌 브랜치가 이번 작업 브랜치와 같을 때만 남긴 것으로 본다. 다르거나 `meta.txt`가 없으면 예전 작업의 파일이므로 쓰지 않는다. `meta.txt`의 `format`이 `none`이면 시퀀스 다이어그램만 남긴 작업이라 화면 증빙이 없는 것으로 본다. 폴더에 없으면 PR 본문에 보관 파일 이름을 alt로 쓴 `private-user-images` 이미지가 있는지 본다. 이때 `<키>-diagram-*` alt만 있으면 화면 증빙이 없는 것으로 본다. 둘 다 없으면 증빙이 없는 작업으로 보고 이 댓글을 건너뛴다.

- `Skill` 도구로 `chucoding:screen-evidence`를 호출해 그 스킬의 `Jira 댓글에 넣기`를 따른다. 머리 문단(`[개발완료]`와 `테스트방법 :` 두 줄)과 미디어 배치의 정본은 그 스킬의 `HDIT 댓글 형식`이다. 형식을 바꿀 때는 그쪽만 고친다.

- GitHub 링크와 PR 링크는 넣지 않는다.
- PR 생성 뒤 리뷰 반영으로 화면이나 판정이 바뀌었으면 댓글을 쓰기 전에 화면 TO-BE나 다이어그램 TO-BE를 다시 남긴다.
- 증빙을 남기지 않은 작업(화면 변화 없음, 개발 서버 불가 등)이면 이 댓글을 남기지 않고, 건너뛴 사실을 완료 보고에 한 줄로 남긴다. 원본 댓글은 미디어 블록 없이 그대로 남긴다.
- 시퀀스 다이어그램도 남겼으면 화면 미디어 블록 아래에 넣는다. 넣는 범위(설명에 같은 다이어그램이 있으면 생략)와 배치는 `chucoding:screen-evidence`의 `다이어그램을 넣는 범위`를 따른다.
- 원본 티켓이 있으면 원본 댓글에도 같은 화면 미디어 블록을 붙인다. 원장 댓글의 미디어는 아래 `원장 완료 댓글`을 따른다. 다이어그램은 HOM 원본 댓글과 원장 댓글에 넣지 않는다. `QA_Bug`의 합친 댓글은 HDIT 증빙 댓글을 겸하므로 화면 증빙이 있을 때 넣는다. 아래 `게시 절차`의 4단계를 따른다.
- 아래 `게시 전 전문 출력`대로 댓글 전문을 출력한다. 출력은 `chucoding:screen-evidence`의 `미디어 블록 만들기` 1단계(파일 첨부)보다 먼저 한다. `QA_Bug`의 합친 댓글은 `게시 전 전문 출력`의 항목을 모두 출력한다. 그 밖의 HDIT 댓글에는 멘션과 본문 제목이 없으므로 대상 티켓 키, 머리 문단 두 줄, 미디어 캡션 문구와 배치, 붙일 미디어 파일 이름과 순서를 출력한다.
- 게시 뒤에는 `게시 절차`의 6단계와 같은 방식으로 댓글 링크와 실제 게시한 전문을 보고에 남긴다. 링크는 `https://rsquare.atlassian.net/browse/<HDIT키>?focusedCommentId=<댓글 id>`다.

### 원장 완료 댓글

위 `원장 판정`으로 원장이 확정됐을 때 원장 티켓에 남기는 댓글이다. 원장은 PM과 운영이 읽는 외부 게시물이고, 사용자가 매번 멘션 대상과 본문을 고쳤다(2026-10-30, 2026-11-06). 그래서 `개발완료` 전환을 게시 승인으로 보지 않고 매번 검수받는다.

**후속 개발 티켓이 모두 끝났을 때 한 번만 단다**

후속 티켓을 하나 완료할 때마다 원장에 댓글을 달지 않는다. 원장 담당자가 부분 완료마다 알림을 받지 않고, 전부 끝났을 때 한 번 확인하게 하려는 것이다(사용자 결정, 2026-11-06).

1. `개발완료` 전환 뒤 `GET /rest/api/3/issue/<원장키>?fields=issuelinks,assignee,reporter,summary,description`으로 원장을 읽는다. 전환 뒤에 읽어야 이번 티켓이 완료로 보인다. 같은 응답을 아래 멘션 후보와 `게시 절차` 1단계에도 쓴다.
2. 원장의 `issuelinks`에서 후속 개발 티켓 후보를 고른다. 유형이 `Discovery - Connected`이고 링크 객체에 상대가 `outwardIssue`로 들어 있는 것(원장이 `connects to <상대>`)과 `Relates`인 것(방향 무관)이다.
3. 아래는 후속 개발 티켓에서 뺀다.
   - `Tasks` 같은 다른 링크 유형으로 걸린 티켓. QA 정기배포 티켓이 여기에 걸린다.
   - 이슈 유형이 `작업_개발`도 `QA_Bug`도 아닌 티켓
   - 사용자가 기획 티켓이라고 고른 티켓. 기획 티켓을 가르는 이슈 유형은 확인되지 않았으므로 짐작으로 빼지 않는다. 남긴 후보를 보여 줄 때 사용자가 고르게 한다.
4. 남긴 티켓과 뺀 티켓을 키, 이슈 유형, 상태, 제목, 뺀 이유와 함께 보여 주고, 남긴 목록을 사용자에게 확정받는다. 사용자가 빼거나 더한 티켓은 그대로 반영한다. 남긴 티켓이 0건이거나 이번 티켓이 빠졌으면 판정하지 않고 어떻게 할지 묻는다.
5. 원장 댓글 목록(`GET /rest/api/3/issue/<원장키>/comment`)을 `startAt`과 `maxResults`로 `total`까지 끝까지 읽어, 그중 인증 계정이 쓴 댓글 중 첫 줄 문구 `완료되었습니다. 개발 서버에서 확인 부탁드립니다.`가 든 것이 있으면 새로 달지 않고 그 댓글 링크를 보여 주며 어떻게 할지 묻는다. 한 번만 단다는 규칙을 지키려는 것이다.
6. 확정한 티켓의 `status.statusCategory.key`가 모두 `done`이면 아래 형식으로 초안을 만든다. 하나라도 아니면 원장 댓글을 미룬다. 남은 티켓의 키와 상태, 담당자(`fields=assignee`로 읽음)를 보고하고, 이번 티켓의 증빙이 보관 폴더와 PR 본문에 남아 있다는 사실을 함께 적는다.
7. 미룬 원장 댓글은 같은 원장의 후속 티켓을 이 스킬로 완료할 때 1단계부터 다시 판정한다. 사용자가 원장 댓글을 직접 요청하면 사용자가 지목한 원장 키(지목이 없으면 묻는다)로 1단계부터 하되, 전환이 없으므로 1단계의 전환 전제와 4단계의 이번 티켓 검사는 건너뛴다. 남은 티켓이 다른 사람 담당이면 그 사람의 완료 처리는 이 스킬을 거치지 않으므로, 그 티켓이 끝난 뒤 사용자가 요청해야 한다는 사실을 미룰 때 함께 알린다.

**형식**

```
@<멘션 대상> 완료되었습니다. 개발 서버에서 확인 부탁드립니다. (cc. @<cc 대상>)
[기획 외 추가 적용]
- ...
```

- **멘션 대상과 cc 대상**은 고정하지 않고 매번 묻는다. 2026-10-30에는 원장 보고자를 멘션했고, 2026-11-06에는 보고자와 요청자를 빼고 원장 담당자(김지혜)를 멘션하고 유한승을 cc했다. 원장 담당자를 기본 후보로 제시한다. 담당자가 비었거나 나이면 보고자를 기본 후보로 둔다. 나를 멘션하지 않는 이유는 `댓글 형식`과 같다. `댓글 형식`의 Cloners 기반 cc 규칙은 쓰지 않는다. cc가 없으면 `(cc. ...)`를 생략한다.
- **본문**은 `[기획 외 추가 적용]` 아래에 기획에 없었지만 따로 정해 적용한 것만 짧게 쓴다. 근거는 후속 개발 티켓들의 설명과 PR 본문, `chucoding:dev-ticket-design` 4단계 기록(사용자 결정, 에이전트 기본값)이다. 기획대로 만든 것, PM과 합의된 기준, 배포 일정처럼 당연한 내용은 쓰지 않는다. 해당 항목이 없으면 제목까지 뺀다.
- **이미지**는 후속 티켓의 AS-IS와 TO-BE 화면에 `[기획 외 추가 적용]` 항목의 화면 캡처를 더한다. 어떤 파일을 어떤 순서와 배치로 넣는지는 `chucoding:screen-evidence`의 `원장 댓글의 미디어`가 정본이다. 시퀀스 다이어그램은 넣지 않는다. 원장이 있는 작업의 다이어그램은 PR에만 남는다.
- 예: HDIT-4517(2026-11-06 초안). 멘션 김지혜, cc 유한승, `[기획 외 추가 적용]` 두 항목, 이미지 네 장(AS-IS, TO-BE, 0명 안내, 발송 횟수 소진 시 버튼 비활성)

**게시**

- 게시 전에 `게시 전 전문 출력`대로 전문과 붙일 이미지 파일의 전체 경로와 순서를 출력하고, 이미지는 Read로 열어 함께 보인 뒤 승인받는다. 사용자가 고치게 하면 고친 전문을 다시 출력하고 다시 승인받는다.
- 게시는 `게시 절차`를 따르되 원본 키 자리에 원장 키를 쓴다. 멘션 대상과 cc 대상은 사용자가 고른 사람이다.
- 이미 게시한 HDIT 증빙 댓글은 원장이 있어도 지우지 않는다.

### 댓글 형식

```
{@멘션 대상} {첫 줄 문구} (cc. {@cc 대상})
[본문 제목]
- ...
```

- 증빙을 남긴 작업이면 본문 아래에 HDIT 댓글과 같은 화면 미디어 블록을 붙인다(`HDIT 증빙 댓글` 참고). 시퀀스 다이어그램은 HOM 원본 댓글에 붙이지 않는다. `QA_Bug`의 합친 댓글은 위 `QA_Bug 티켓`대로 넣는다. 멘션, 첫 줄 문구, 본문 규칙은 미디어가 있어도 그대로다.

- **첫 줄 문구**는 위 표를 따른다. HOM은 `해당 티켓`을 붙이지 않는다. QA 티켓에 붙이면 티켓 작성이 완료되었다는 뜻으로 읽힌다.
- **멘션 대상**은 HOM이면 보고자(`reporter`)다. `QA_Bug`면 그 HDIT의 보고자다. HOM 담당자는 `BE 이관` 규칙대로 HDIT 담당자와 같아 대개 나여서, 담당자를 멘션하면 QA가 아니라 나를 부르게 된다. 멘션 대상이 비어 있거나 나이면 HOM, QA_Bug 모두 멘션 없이 게시하지 말고 누구를 멘션할지 되묻는다. 나를 멘션하면 댓글을 읽어야 할 사람에게 알림이 가지 않기 때문이다.
- **cc 대상**은 원본 티켓의 `issuelinks` 중 링크 유형이 `Cloners`이고 프로젝트 키가 `HDIT`인 티켓 가운데, 완료 처리한 티켓을 뺀 나머지의 담당자다. 담당자가 비어 있는 티켓은 건너뛴다. 나(인증 계정 `JIRA_EMAIL`, accountId는 `GET /rest/api/3/myself`)와 멘션 대상은 빼고 중복도 없앤다. 여러 명이면 `(cc. @A, @B)`처럼 쉼표와 공백으로 잇는다. 남는 사람이 없으면 `(cc. ...)`를 통째로 생략한다. Blocks 같은 다른 링크 유형의 담당자는 넣지 않는다.
- **PR**은 완료 처리한 HDIT 티켓의 PR이다. PR을 찾는 키는 HDIT 키이고, HOM 원본이 있으면 그 HOM 키도 함께 쓴다. `착수 브랜치 이름`에 따라 QA 클론의 브랜치와 PR 제목에는 HOM 키만 들어가기 때문이다. 키는 뒤에 숫자가 더 이어지지 않는 정확한 키로 비교한다. `HDIT-12`는 `HDIT-123`과 일치하지 않는다. 머지 없이 닫힌 PR(`state`가 `CLOSED`)은 어느 경로에서든 쓰지 않는다.
  1. `gh pr view --json number,state,title,headRefName,body,commits`로 현재 브랜치의 PR을 읽는다. 제목이나 브랜치명에 찾는 키 중 하나가 있고 `CLOSED`가 아니면 그 PR의 `body`와 `commits`를 근거로 쓴다.
  2. 조회 결과가 없거나 1단계 조건에 맞지 않으면 찾는 키마다 `gh pr list --state all --search <키> --json number,title,headRefName,state`로 찾고, 같은 조건에 맞는 PR만 후보로 삼는다. 후보가 여럿이면 어느 것을 쓸지 되묻는다. 고른 PR은 `gh pr view <번호> --json body,commits`로 본문과 커밋을 읽는다.
- **HOM 본문**은 PR 본문과 커밋에서 QA가 지적한 문제 외에 함께 고친 것만 추려 QA가 읽는 말로 다시 쓴다. QA가 지적한 문제는 HOM 티켓의 제목과 설명(`fields=summary,description`)으로 판단한다. QA가 재검증할 범위를 알리려는 것이므로 화면에서 달라지는 동작 위주로 쉽게 쓴다. 쓰는 말과 점검은 위 `QA_Bug 처리결과 필드`의 `QA가 읽는 말로 쓰기`를 따른다. 해당하는 것이 없으면 `[추가로 수정된것]` 제목까지 통째로 생략하고 첫 줄만 남긴다. PR을 찾지 못했으면 생략으로 단정하지 말고 되묻는다.

### 게시 전 전문 출력

댓글은 QA와 기획자가 읽는 외부 게시물이다. 사용자가 무엇이 게시되는지 대화 내역에서 그대로 확인할 수 있도록, 게시하기 전에 댓글 전문을 선택지 질문 밖의 본문으로 출력한다. 요약으로 대신하지 않는다. 선택지만 띄우고 전문을 출력하지 않으면 사용자는 무엇을 승인하는지 알 수 없다.

- 출력에는 아래를 모두 넣는다.
  - 대상 티켓 키
  - 멘션 대상 이름, cc 대상 이름 (없으면 없다고 적는다)
  - 첫 줄 문구
  - 본문 제목과 목록 전부 (생략했으면 생략한 사실과 이유)
  - 미디어 캡션 문구(`AS-IS: <한 줄 설명>`, `TO-BE: <한 줄 설명>`)와 배치(좌우 두 열 또는 TO-BE 하나)
  - 붙일 미디어 파일 이름과 순서 (없으면 미디어 항목 전체를 없다고 적는다)
- HOM과 `QA_Bug` 댓글은 출력하기 전에 `[추가로 수정된것]` 목록을 `QA_Bug 처리결과 필드`의 `QA가 읽는 말로 쓰기`대로 점검한다.
- 전문은 게시될 모양 그대로 코드 블록에 담는다. 멘션은 `@이름`으로 적고, 실제 게시에서는 mention 노드로 바뀐다는 점을 함께 적는다.
- `개발완료` 전환을 게시 승인으로 보는 경우처럼 승인을 묻지 않을 때도 이 출력은 생략하지 않는다. 출력한 뒤 바로 게시한다.
- 원장 댓글은 위 항목의 예외다. 출력한 뒤 바로 게시하지 않고 아래 `원장 완료 댓글`대로 승인받은 뒤 게시한다.
- 이 절차에서 초안이 있는 채로 선택지를 띄울 때는 이유와 관계없이 전문을 먼저 선택지 질문 밖의 본문으로 출력하고 그다음에 선택지를 띄운다. 선택지 질문(AskUserQuestion) 안에는 전문을 넣지 않고 "위 초안 기준으로 정해 주세요"처럼 출력한 내용을 가리키기만 한다. 선택지 UI가 앞의 텍스트를 가리거나 질문 속 요약만 남기면, 사용자가 요약만 보고 승인하게 되기 때문이다. 이 규칙은 질문을 띄우는 방식만 정하며, 게시 승인을 새로 묻는 절차를 만들지 않는다.
- 멘션 대상이 비었거나 나일 때, 같은 프로젝트의 원본이 둘 이상일 때처럼 초안을 만들 수 없는 되묻기는 전문 없이 먼저 묻는다. 답을 받으면 그 답을 반영한 최종 전문을 `게시 절차`의 3단계에서 출력한 뒤 게시한다.
- 증빙 파일을 PR에서 다시 받았으면 `chucoding:screen-evidence`의 재다운로드 절차에 있는 게시 여부 질문을 그대로 쓴다. 질문을 새로 만들지 않고, 그 질문을 띄우기 전에 그 파일을 쓰는 댓글의 전문을 출력한다는 순서만 더한다. 답에 따른 처리는 그 절차를 따른다.
- 사용자가 내용을 고치게 하면 고친 전문을 다시 출력한 뒤 게시한다. 고친 부분만 보여 주지 않는다.

### 게시 절차

인증은 `~/.config/homedot-worktime/config.env`의 `JIRA_EMAIL`과 `JIRA_API_TOKEN`, 사이트는 `https://rsquare.atlassian.net`이다. 원본 티켓마다 아래를 따로 수행한다.

1. **멘션 대상과 담당자를 모은다.** 먼저 `GET /rest/api/3/myself`로 나(인증 계정)의 accountId를 읽어, 멘션 대상이 나인지 판정하고 cc에서 뺄 때 쓴다. `GET /rest/api/3/issue/<원본키>?fields=assignee,reporter,issuelinks,summary,description`로 멘션 대상과 링크를 읽고, Cloners로 연결된 HDIT 티켓마다 `fields=assignee`로 담당자를 읽는다.
2. **accountId와 이름을 정한다.** 담당자와 보고자 필드의 `accountId`와 `displayName`을 그대로 쓴다. 사용자가 멘션할 사람을 이름으로 직접 지정했을 때처럼 accountId를 필드에서 얻을 수 없을 때만 `GET /rest/api/3/user/search?query=<이름>`으로 찾고, `accountType`이 `atlassian`인 결과만 남긴다. 0건이거나 2건 이상이면 임의로 고르지 말고 되묻는다.
3. **전문을 출력한다.** 위 `게시 전 전문 출력`대로 댓글 전문을 대화에 출력한다. 출력하지 않았으면 다음 단계로 가지 않는다. 원장 댓글은 출력한 뒤 승인을 받아야 다음 단계로 간다.
4. **ADF로 게시한다.** 멘션은 텍스트 `@이름`이 아니라 mention 노드로 넣어야 알림이 간다. 게시 방법은 증빙 파일 유무로 갈린다.
   - 파일이 없으면 `POST /rest/api/3/issue/<원본키>/comment`에 ADF 본문을 한 번에 보낸다.
   - `QA_Bug`의 합친 댓글은 아래 ADF 전체와 미디어 블록 사이에 증빙 머리 문단(`[개발완료]`와 `테스트방법 :`)을 둔다. 파일이 없으면 머리 문단도 넣지 않는다.
   - 파일이 있으면 `chucoding:screen-evidence`의 `미디어 블록 만들기`를 따른다. 원본 티켓에 파일을 따로 첨부하고, 멘션(`[~accountid:<accountId>]`)과 파일을 담은 댓글을 v2로 먼저 만들어 media id와 멘션을 확인한 뒤, `PUT /rest/api/3/issue/<원본키>/comment/<id>`로 아래 ADF 전체 뒤에 미디어 블록을 붙여 다시 쓴다. 멘션은 처음 만들 때 넣어야 알림이 확실히 간다. media는 티켓 단위라 HDIT에 첨부한 파일을 원본에서 쓸 수 없다.

   ```json
   {"type": "mention", "attrs": {"id": "<accountId>", "text": "@<displayName>"}}
   ```

   첫 줄과 본문 제목은 각각 `paragraph`로 두고, 첫 줄 안에서 멘션 사이 문구는 `text` 노드로 잇는다. 본문 제목 아래 목록은 `bulletList` > `listItem` > `paragraph` 구조로 만든다. 게시가 실패하면 재시도하지 말고 응답 상태와 오류 메시지를 보고한다. `개발완료` 전환은 되돌리지 않는다.

5. **멘션을 확인한다.** 게시 응답(증빙 파일이 있으면 마지막 PUT 응답)의 `body.content`를 안쪽 `content`까지 재귀로 훑어 mention 노드의 `attrs.id`를 모으고, 의도한 사람 모두에게 멘션이 걸렸는지 확인한다. 빠진 사람이 있으면 그 사실을 보고하고, 댓글을 수정할지 되묻는다. 같은 댓글을 다시 게시하지 않는다.
6. **링크와 게시한 전문을 보고한다.** `https://rsquare.atlassian.net/browse/<원본키>?focusedCommentId=<댓글 id>`와 함께, 실제로 게시된 댓글 전문을 보고에 남긴다. 전문은 출력한 초안이 아니라 게시 응답(증빙 파일이 있으면 마지막 PUT 응답)의 `body`를 텍스트로 풀어 쓴다. mention 노드는 `attrs.text`로 적는다. media 노드의 `attrs`에는 파일 이름이 없으므로, `미디어 블록 만들기` 3단계에서 읽은 media id 순서를 2단계 v2 댓글에 적은 파일 마크업(`!<파일명>|…!`) 순서와 맞춰 파일 이름으로 적는다. 1단계의 첨부 순서와는 맞추지 않는다. 출력한 초안과 다른 곳이 있으면 그 차이를 밝힌다.

## 댓글 정정

이미 게시한 댓글의 결정이나 내용이 바뀌면 기존 댓글을 지우거나 덮어쓰지 않는다. 기존 댓글은 취소선으로 남기고 정정 내용은 새 댓글로 단다. 읽은 사람이 무엇이 바뀌었는지 비교할 수 있어야 하고, 이미 알림을 받은 사람은 수정된 본문을 다시 열어 보지 않기 때문이다.

1. **기존 댓글을 읽는다.** `GET /rest/api/3/issue/<키>/comment/<id>`로 ADF `body`를 받는다. 응답의 `author.accountId`가 `GET /rest/api/3/myself`의 accountId와 다르면 남의 댓글이므로 취소선을 긋지 않고 되묻는다.
2. **정정 초안을 출력한다.** 취소선을 그을 범위와 새 댓글 전문을 `게시 전 전문 출력`대로 출력하고 승인받는다. 새 댓글 첫 줄은 `위 댓글을 정정합니다.`로 시작하고, 멘션 대상은 기존 댓글과 같게 하되 사용자가 바꾸면 따른다. 기존 댓글의 멘션은 1단계에서 받은 `body`의 mention 노드(`attrs.id`, `attrs.text`)를 그대로 다시 쓴다. 사용자가 대상을 바꿨을 때만 `게시 절차` 2단계로 accountId를 찾는다. 상위 스킬이 취소선 범위와 정정 전문을 모두 출력하고 승인받았으면 이 출력과 승인은 다시 하지 않는다.
3. **취소선을 긋는다.** 받은 `body`에서 정정 대상 `text` 노드의 `marks`에 `{"type":"strike"}`를 더해 `PUT /rest/api/3/issue/<키>/comment/<id>`로 다시 쓴다. mention, media 같은 다른 노드는 그대로 둔다. 바뀌지 않은 항목까지 긋지 않는다.
4. **정정 댓글을 단다.** `게시 절차`의 4단계부터 6단계대로 게시하고 멘션과 링크를 확인한다.

PUT이나 게시가 실패하면 재시도하지 말고 응답 상태와 오류 메시지를 보고한다. 취소선만 실패했으면 정정 댓글은 그대로 게시하고, 기존 댓글을 사용자가 직접 편집하도록 안내한다.

## BE 이관

FE 저장소에서 착수한 티켓이 조사 결과 FE에서 수정할 것이 없고 BE에서 수정해야 하는 것으로 판별되면, 티켓을 BE 쪽으로 넘기고 이 세션이 남긴 착수 흔적을 지운다. 판별 근거 없이 넘기지 않는다.

1. **판별을 먼저 끝낸다.** 응답 스펙(`/v3/api-docs`)과 FE 코드를 함께 확인해 FE에서 고칠 여지가 없음을 확정한다. 아래 두 가지를 모두 확인한다.
   - 응답 DTO에 필요한 필드가 없고, 요청 파라미터에도 그 값을 켜는 플래그가 없다. 프론트가 요청할 방법 자체가 없어야 한다.
   - 같은 값을 쓰는 형제 엔드포인트나 다른 화면에서는 정상 동작한다. 이 대조가 설계 의도와 누락을 가른다.

   판별이 갈리지 않으면 이관하지 않고 무엇이 불확실한지 밝힌다.

2. **담당자를 확정한다.** 사용자가 이름을 말하면 `/rest/api/3/user/search?query=<이름>`으로 accountId를 조회한다. 결과가 0건이거나 2건 이상이면 임의로 고르지 말고 되묻는다. 사용자가 이름을 말하지 않았으면 담당자를 추측하지 않고 누구에게 넘길지 묻는다.

3. **HDIT와 HOM 양쪽 담당자를 함께 바꾼다.** 한쪽만 바꾸면 QA 원본과 개발 클론의 담당자가 어긋나, 다음 세션의 담당자 정렬이 QA 기준으로 되돌린다.

4. **댓글은 HOM 원본에만 남긴다.** QA가 읽는 곳이 HOM이다. 문구는 아래 형식을 따른다.

   ```
   BE에서 확인이 필요한 티켓이므로 담당자 {이름}님으로 변경해놓겠습니다
   ```

5. **HDIT 상태를 `Backlog`로 되돌린다.** 내 작업이 아니게 됐는데 개발중으로 두면 작업시간이 계속 쌓인다.

6. **착수 흔적을 지운다.** 이 세션이 작업시작 때 채운 Actual start(`customfield_10008`)와 시작 날짜(`customfield_10015`)를 HDIT와 HOM 양쪽에서 `null`로 비운다. 내가 채우지 않은 값은 건드리지 않는다.

7. **SP와 스프린트는 그대로 둔다.** SP는 계획값이라 불변이고, 스프린트는 `상태 전환` 규칙을 따른다.

8. **HOM 상태는 되돌리지 않는다.** `in progress`에서 나가는 전환이 `Known Issue`, `Won't Do`, `개발완료`(도착 상태 `resolve`)뿐이라 `open`으로 가는 경로가 워크플로우에 없다. 뜻이 다른 상태로 임의 전환하지 말고, HOM이 `in progress`로 남았다는 사실을 보고에 적는다.

9. **대시보드를 갱신한다.** `refresh.py --release`를 실행한다.

이슈 유형이 `QA_Bug`인 HDIT는 HOM이 없으므로 그 HDIT가 QA 원본을 겸한다. 3단계의 담당자 변경과 4단계의 댓글, 6단계의 착수 흔적 정리는 그 HDIT에서만 한다. 워크플로에 `Backlog`가 없고 `진행 중`에서 `open`으로 가는 전환도 없으므로 5단계는 하지 않는다. 8단계처럼 상태를 임의로 바꾸지 말고 `진행 중`으로 남았다는 사실을 보고에 적는다.

보고에는 판별 근거, 바꾼 항목, HOM 상태가 남은 사실을 함께 적는다. BE 작업 티켓을 새로 만들지 않는다. 필요해 보이면 `티켓 생성` 규칙대로 제안만 하고 지시를 기다린다.

## SP 산정

SP는 지난 스프린트에서 내가 실제로 쓴 시간을 근거로 직접 산정한다. 폴러의 유사도 추천(`estimate_sp.py --json`의 `suggestion`)과 위키 MCP는 근거로 쓰지 않는다. 처음 이 전략을 쓸 때(2026-09-02) "실제 작업 시간"이 어느 측정값인지 정하지 않아 체류 시간으로 나눈 비율이 만들어졌으므로(HDIT-2836이 0.86이 아니라 0.38로 매겨짐, 전역 AGENTS 저장소 커밋 `7cccb20`), 실적은 아래처럼 업무 로그로만 잰다.

- 산정 시점은 티켓 생성 직후, 생성을 보고하기 전이다. 사용자가 요청하지 않아도 수행한다. 사용자가 기존 티켓의 산정을 따로 요청할 때도 같은 절차를 따른다.
- 실적은 **Jira 업무 로그**(`timespent`, `timetracking.timeSpentSeconds`)다. 상태 체류 시간을 근무 시간으로 환산한 값을 실적으로 쓰지 않는다. 두 값은 2배 이상 벌어진다. 이미 매겨진 SP를 실적처럼 쓰지도 않는다.
- 환산은 **1 SP = 8시간**이고, 순수 예상 시간에 **여유 15%**를 더해 `예상 시간 × 1.15 ÷ 8`로 계산한다. 과거 티켓의 SP 대비 시간 비율을 새로 도출하지 않는다. 최소 0.13 SP(1시간)를 하한으로 두고 소수 둘째 자리로 반올림한다.

### 절차

1. **실적 후보를 모은다.** 지난 스프린트에서 내가 맡았고 업무 로그가 있는 HDIT 티켓을 조회한다. `[데일리 스크럼]`, `[회의]` 제목과 연차 유형은 뺀다.

   ```bash
   source ~/.config/homedot-worktime/config.env   # JIRA_EMAIL, JIRA_API_TOKEN
   curl -s -u "$JIRA_EMAIL:$JIRA_API_TOKEN" -H 'Content-Type: application/json' \
     -X POST https://rsquare.atlassian.net/rest/api/3/search/jql \
     -d '{"jql":"project = HDIT AND assignee = currentUser() AND sprint in closedSprints() AND timespent > 0 AND updated >= -90d ORDER BY updated DESC","fields":["summary","timespent","issuetype"],"maxResults":100}'
   ```

   응답의 `nextPageToken`이 있으면 같은 요청에 넣어 다음 페이지를 받는다.

2. **닮은 티켓을 고른다.** 산정 대상의 제목과 설명을 읽고, 작업 종류(화면 수정, 공통 컴포넌트, 문서와 지침, 조사)와 범위가 비슷한 티켓을 2~3건 고른다. 제목만으로 애매하면 그 티켓의 설명을 조회해 범위를 대조한다.
3. **예상 시간을 정한다.** 닮은 티켓의 업무 로그 시간을 기준으로, 대상 티켓과 범위가 다른 만큼 더하거나 뺀다. 단계별(예: 구현, 경계 처리, E2E, 리뷰 대응)로 나눠 합산한다.
4. **다시 조회한다.** 넣기 직전에 SP 칸(`customfield_10028`)을 다시 조회한다. 이미 값이 있으면 덮지 않고 그 값을 보고한다. 생성 직후 비어 있던 칸을 폴러나 사용자가 몇 분 사이에 먼저 채울 수 있다. SP는 계획값이라 한 번 들어가면 덮지 않는다.
5. **기입한다.** `homedot-cloud-devteam` 플러그인의 `estimate_sp.py --sp --note`로 넣는다. 산정 판단은 위 절차에서 끝났고, 이 스크립트는 기입 수단으로만 쓴다. 이 경로로 넣어야 설명의 근거 문단과 원래 추정 시간(`originalEstimate`), 플러그인이 넣은 값이라는 기록이 함께 남는다. 캐시에 여러 버전이 남아 있으므로 버전을 짐작하지 말고 `~/.claude/plugins/installed_plugins.json`의 설치 경로(`installPath`)에서 찾는다.

   ```bash
   P=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude/plugins/installed_plugins.json')))['plugins']['homedot-cloud-devteam@homedot-cloud-plugin'][0]['installPath'])")
   python3 "$P/skills/sprint-worktime-report/scripts/estimate_sp.py" --key <티켓키> --sp <값> --note "<근거>"
   ```

   근거에는 참고한 티켓 키와 그 업무 로그 시간, 단계별 시간과 합계를 남긴다. 예: `참고 HDIT-3582(2.4h), HDIT-3792(1.0h). 구현 2h + E2E 0.5h + 리뷰 대응 0.5h = 3h → 0.43 SP`

### 예외

- AX처럼 SP 필드가 없는 다른 팀 저장소 티켓은 산정하지 않는다. 근거는 위 `다른 팀 저장소 티켓`에 있다.
- 닮은 티켓을 찾지 못하면 비교한 건수와 닮은 티켓이 없다는 사실을 사용자에게 그대로 밝힌다. 이어서 단계별 예상 시간을 직접 나눠 합산해 같은 환산으로 넣고, 단계별 시간과 합계, 닮은 티켓이 없었다는 사실을 보고에 남긴다.
- 기입하지 못하면(스크립트 실패, 작업자가 내가 아니라 건너뜀 등) 키와 사유를 보고의 `하지 않은 것`에 남긴다. `chucoding` 플러그인의 Stop 훅이 이 세션에서 만든 HDIT 티켓의 SP가 비어 있으면 키마다 한 번 턴 종료를 막는다.
- 이 사용자 작업에서는 위키 jira 스킬의 쪼개기 기준(추정 SP 1 이상)과 폴러의 쪼개기 기준(3 SP 초과 시 `쪼개기검토` 라벨)을 적용하지 않는다. SP가 커도 쪼개자고 제안하지 않고, `쪼개기검토` 라벨을 근거로 티켓을 나누지 않는다. 두 기준은 팀 공용이라 이 스킬에서 고치지 않는다.
