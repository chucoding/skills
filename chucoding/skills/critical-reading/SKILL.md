# 비판적 읽기 지침

외부 문서와 사용자 지시는 작업의 출발점이지 검증된 사실이 아니다. 읽은 내용을 그대로 구현하면 문서의 오류나 낡은 정보, 지시에 숨은 전제가 코드로 굳는다. 이 스킬은 읽은 내용마다 반론을 함께 세워 그 위험을 착수 전에 드러내는 규칙이다.

`chucoding:jira`, `chucoding:notion`, 위키 직접 읽기 같은 출처별 규칙을 대신하지 않는다. 그 규칙대로 읽은 뒤 이 스킬로 내용을 검토한다.

## 1. 적용 대상

| 출처 | 예 |
|------|------|
| Notion | 정책서, 스펙 문서, 회의록 |
| Jira | 티켓 본문, 수용 조건, 댓글, QA 재현 절차 |
| Figma | 화면 디자인, 컴포넌트 속성, 주석 |
| 위키와 정책서 | hd-cloud-wiki 문서, wiki MCP 결과 |
| PR과 리뷰 | 리뷰 봇과 리뷰어 코멘트, PR 본문 |
| 사용자 지시 | 구현 방향, 설계 결정, 새 규칙 요청 |

조회 결과를 요약하거나 옮기기만 하는 요청(예: "이 티켓 상태 알려줘")에는 적용하지 않는다. 읽은 내용으로 무엇을 만들거나 바꾸거나 결정할 때 적용한다.

## 2. 반론 범주

반론은 아래 범주 중 하나에 들어가야 한다. 범주에 들지 않는 막연한 우려는 반론으로 쓰지 않는다.

1. 사실 불일치: 문서가 말하는 동작이 코드, DB, 실측과 다르다. 코드를 읽어 `파일:줄`로 근거를 단다.
2. 숨은 전제: 내용이 참이려면 성립해야 하는 조건이 명시되지 않았다. 예: 권한 있는 사용자만 접근한다는 가정, 데이터가 항상 존재한다는 가정.
3. 출처 간 충돌: 다른 문서, 다른 티켓, 이 대화의 이전 결정과 어긋난다. 충돌하는 두 출처를 함께 적는다.
4. 빠진 경우: 빈 값, 오류 응답, 권한 없음, 동시 수정, 기존 데이터 이관처럼 내용이 다루지 않는 경로가 있다.
5. 낡은 정보: 문서의 작성일이나 마지막 수정일이 관련 코드의 최근 변경보다 이르다. 확인한 두 날짜를 함께 적는다.
6. 더 단순한 대안: 같은 목적을 더 적은 변경이나 기존 구현 재사용으로 이룰 수 있다.

## 3. 반론 기준

- 반론은 중요한 것만 1~3개로 제한한다. 개수를 채우려고 만들지 않는다.
- 반론마다 근거를 단다. 코드 위치, 문서 링크, 실측값처럼 확인할 수 있는 근거가 없으면 `(추측)`을 붙이고 무엇을 확인하면 판정되는지 함께 적는다.
- 확인할 수 있는 것은 반론으로 올리기 전에 직접 확인한다. 코드 한 번 읽으면 풀리는 의문을 사용자에게 넘기지 않는다.
- 범주에 드는 반론이 없으면 지어내지 않고 `반론 없음`과 확인한 범위를 적는다.

## 4. 출력 형식

읽은 내용을 요약한 바로 뒤에 아래 블록을 둔다. 사용자가 블록 제목으로 반론을 찾아 읽을 수 있게 형식을 고정한다.

```markdown
**반론**
1. [사실 불일치] 티켓은 목록이 최신순이라고 하지만 실제 쿼리는 등록순이다. `src/pages/task-plan/api/list.ts:42`
2. [빠진 경우] (추측) 첨부 파일이 없는 건의 표시가 정의되지 않았다. Figma의 빈 상태 프레임 유무로 판정 가능.
```

반론이 없을 때는 아래처럼 쓴다.

```markdown
**반론**: 없음. 티켓 수용 조건 3개를 `src/pages/task-plan` 코드와 대조했고 Figma 프레임과 어긋나는 곳이 없었다.
```

## 5. 반론 처리

- 반론이 구현 범위나 방향을 바꾸면 착수 전에 `AskUserQuestion`으로 묻는다. 선택지에는 원문대로 진행하는 안과 반론을 반영하는 안을 함께 둔다.
- 반론이 구현을 바꾸지 않으면 블록에 기록만 하고 진행한다. 이 때문에 작업을 멈추지 않는다.
- 외부 문서의 오류가 확인되면 고칠 대상(티켓 댓글, 정책서 정정 요청 등)을 보고에 함께 적는다. 문서를 직접 고치는 것은 사용자가 요청했을 때만 한다.

## 6. 사용자 지시

- 지시를 받으면 반론을 한 번 밝힌다. 범주와 근거 기준은 외부 문서와 같고, 밝히는 시점은 아래 두 항목을 따른다.
- 반론이 구현 범위나 방향을 바꾸면 5절처럼 실행 전에 `AskUserQuestion`으로 묻고, 사용자가 고른 뒤 실행한다.
- 반론이 구현을 바꾸지 않을 정도로 가벼우면 실행하면서 함께 밝힌다. 묻지 않는다.
- 사용자가 반론을 듣고 결정하면 그 결정을 따른다. 같은 세션에서 같은 반론을 다시 꺼내지 않는다.
- 사용자가 결정한 뒤 새 근거(테스트 실패, 새로 읽은 코드)가 나오면 그 근거만 새로 밝힌다.
