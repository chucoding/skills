# 다른 저장소로 핸드오프

지금 열려 있는 워크스페이스와 다른 저장소에 속하는 작업을 새 워크스페이스로 넘기고, 넘긴 뒤에는 감시하지 않는다. 소유권 이전이지 감독이 아니다.

## 1. 이 스킬을 쓰는 경우

| 상황 | 처리 |
|------|------|
| 요청이 지금 저장소 밖 저장소에 속하고, 결과를 기다릴 필요가 없다 | 이 스킬 |
| 요청이 지금 저장소에 속한다 | 핸드오프하지 않고 직접 한다 |
| 사용자가 감독, 대기, 결과 취합, DAG, 결정 게이트를 명시적으로 요구한다 | `orchestration` 스킬 |
| 지금 저장소 안에서 에이전트만 하나 더 띄우면 된다 | `orca terminal create --worktree active --command "claude"` |

- 사용자가 "핸드오프", "넘겨줘", "다른 워크스페이스에서", "다른 에이전트한테"라고 말하면 감독 요구가 함께 없는 한 이 스킬이다.
- `orca orchestration task-create`, `orca orchestration dispatch --inject`, `orca orchestration check --wait`은 이 스킬에서 쓰지 않는다. 그 명령들은 코디네이터가 결과를 기다린다는 뜻이다.

## 2. 대상 저장소 판별

| 요청 | 저장소 선택자 | displayName | 경로 |
|------|------|------|------|
| 위키 문서 작성이나 수정 | `id:8654953e-f2f4-4113-8cb8-0d88ee47a381` | hd-cloud-wiki | `/Users/hyeonseoksuh/homedot/hd-cloud-wiki` |
| today-i-learned, TIL, 학습 기록 | `id:1c6e1311-4b74-4e18-a756-c02700999bcc` | 공부봇 | `/Users/hyeonseoksuh/chucoding/today-i-learned` |
| 스킬 생성이나 수정, 플러그인 훅 | `id:21a598b8-a367-4b33-9f2b-db5951ba8e7b` | skills | `/Users/hyeonseoksuh/chucoding/skills` |
| 전역 AGENTS.md 수정 | `id:fa350229-dad6-4de3-8974-4829886eda79` | AGENTS.md | `/Users/hyeonseoksuh/chucoding/a548473d5c3a2a954e1a633adfcd636b` |

- 표에 없는 요청은 추측하지 말고 어느 저장소로 보낼지 되묻는다.
- 선택자는 `name:<displayName>`이 아니라 `id:<repoId>`를 쓴다. displayName은 Orca에서 바꿀 수 있는 표시 이름이라 폴더 이름과 다를 수 있고, 바뀌면 `repo_not_found`로 깨진다. today-i-learned가 `공부봇`으로 등록되어 `name:today-i-learned`가 실패한 일이 있었다.
- 표의 id와 경로는 macOS 작업 머신의 Orca에 등록된 값이다. repo id는 각 머신의 Orca에 등록할 때 정해지는 값이라 다른 머신에서는 맞지 않을 수 있다.
- id가 맞지 않거나 저장소를 다시 등록했다면 `orca repo list --json`에서 표의 경로와 `path`가 같은 항목을 찾아 그 `id`를 쓴다. 다른 머신이라 경로가 다르면 `path`의 마지막 폴더 이름이 표 경로의 마지막 폴더 이름과 같은 항목을 찾는다.
- 표의 id가 낡았으면 이번 핸드오프는 찾은 id로 진행하고, 표 수정은 사용자에게 알린다. 표는 skills 저장소에 있으므로 지금 세션이 skills 저장소 밖이면 직접 고치지 않고, 사용자가 원하면 skills 저장소로 따로 핸드오프한다.
- Orca에 등록되지 않은 저장소면 `orca repo add --path <절대경로> --json`으로 먼저 등록하고, 결과에 나온 `id`로 선택자를 만든다.
- 이미 그 저장소 워크스페이스 안에 있으면 핸드오프하지 않는다. `orca worktree current --json`의 저장소와 대상이 같은지 먼저 본다.

## 3. 맥락 전달 방식 선택

두 가지 중 하나를 고르고, 무엇을 왜 골랐는지 보고에 한 줄로 남긴다.

| 조건 | 방식 |
|------|------|
| 이번 대화에서 조사하거나 판단한 내용이 결과물의 근거다 | 세션 fork |
| 요청만으로 작업이 자족적이다 | 브리핑 파일 |

- 세션 fork는 대화 전체가 그대로 따라가서 누락이 없지만, 무관한 맥락과 토큰까지 따라간다. 이번 세션에서 디버깅한 내용을 TIL로 남기거나, 방금 정한 규칙을 AGENTS.md에 반영하는 경우가 여기 해당한다.
- 브리핑 파일은 새 세션이 깨끗하고 토큰이 싸지만 요약한 만큼만 넘어간다. 주제만 주고 문서를 새로 쓰게 하는 경우가 여기 해당한다.
- 애매하면 브리핑 파일을 고르고, 브리핑에 이번 대화에서 나온 결론을 빠짐없이 적는다.

## 4. 확인 받기

워크트리를 만들기 전에 아래를 묶어서 보여주고 승인을 받는다. 승인 없이 만들지 않는다.

- 대상 저장소와 워크스페이스 이름
- 맥락 전달 방식과 그 이유
- 새 세션에 실제로 보낼 내용 전문

보낼 내용은 요약으로 대신하지 않고 전문을 대화에 출력한다. 사용자가 대화 내역에서 새 세션이 받을 지시를 그대로 읽고 승인할 수 있어야 하기 때문이다. 브리핑 파일 경로나 명령 인자 안에만 있는 지시는 사용자가 확인할 수 없다.

| 방식 | 출력할 것 |
|------|------|
| 5-A 세션 fork | `orca terminal send --text`로 보낼 지시 전문을 코드 블록으로 |
| 5-B 브리핑 파일 | 브리핑 파일을 먼저 쓴 뒤 그 절대경로와 파일 내용 전문을 마크다운 코드 블록으로, 이어서 `--prompt`에 넣을 문자열을 그대로 |

- 전문을 먼저 선택지 질문 밖의 본문으로 출력하고, 그다음에 승인 질문을 띄운다. 선택지 질문(AskUserQuestion) 안에는 전문을 넣지 않고 "위 전문대로 보낼까요?"처럼 앞서 출력한 내용을 가리킨다. 선택지 UI가 앞의 텍스트를 가리거나 질문 속 요약만 남겨, 요약만 보고 승인하게 되는 일을 막기 위해서다.
- 브리핑 파일을 쓰는 것은 승인 전에 해도 된다. 승인 전에 하지 않는 것은 워크트리 생성과 새 세션 착수다.
- 사용자가 내용을 고치라고 하면 반영한 뒤 고친 전문을 다시 출력하고 다시 승인받는다. 고친 부분만 보여 주고 승인받지 않는다.

## 5-A. 세션 fork로 넘기기

현재 세션 id는 시스템 프롬프트의 스크래치패드 경로에서만 읽는다. 경로 형태는 운영체제마다 다르므로 형태를 외우지 말고 UUID 구간을 세션 id로 읽는다.

```
macOS    /private/tmp/claude-501/<프로젝트슬러그>/<세션id>/scratchpad
Windows  C:\Users\<사용자>\AppData\Local\Temp\claude\<프로젝트슬러그>\<세션id>\scratchpad
```

- 시스템 프롬프트에 스크래치패드 경로가 없으면 세션 id를 추정하지 않는다. 그 사실을 밝히고 `5-B. 브리핑 파일로 넘기기`로 돌아간다. 이때 승인받은 것은 5-A 지시뿐이므로, 브리핑 파일을 쓴 뒤 `4. 확인 받기`로 돌아가 5-B 전문을 출력하고 다시 승인받는다.
- `~/.claude/projects/<슬러그>/*.jsonl`을 수정 시각으로 골라 쓰지 않는다. 같은 저장소에 다른 세션이 함께 떠 있으면 최신 파일이 내 세션이 아니고, 잘못 고르면 남의 대화를 fork한다.

```bash
orca worktree create --repo id:<repoId> --name <작업이름> --no-parent --json
orca terminal create --worktree "id:<repoId>::<worktreePath>" --title <작업이름> \
  --command "claude --resume <세션id> --fork-session" --json
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 90000 --json
orca terminal send --terminal <handle> --text "<새 세션이 할 일>" --enter --json
```

- `--fork-session`은 필수다. 빼면 원본 세션에 턴이 덧붙어 지금 이 대화의 기록이 오염된다.
- fork된 세션은 작업 디렉터리를 새 워크트리로 잡고, 그 저장소의 CLAUDE.md와 AGENTS.md를 새로 읽는다. 대화만 따라가고 작업 위치는 따라가지 않는다.
- `worktree create`에 `--agent`를 붙이지 않는다. `--agent`는 맨 claude를 띄우므로 fork가 되지 않는다. 이 경로에서만 두 단계로 나눈다.
- `terminal wait`를 건너뛰면 TUI가 뜨기 전에 입력이 흘러 프롬프트를 잃는다.
- `--command`에는 실행할 명령만 넣고 작업 지시는 전부 `terminal send`로 보낸다. `--command`는 셸을 거치므로 따옴표나 줄바꿈이 든 한글 지시를 붙이면 명령이 깨진다.
- 전달할 지시에는 fork된 대화의 어느 부분을 근거로 삼아야 하는지 한 줄로 밝힌다. 대화가 길면 새 세션이 무엇이 과제인지 못 고른다.

## 5-B. 브리핑 파일로 넘기기

```bash
mkdir -p ~/.claude/handoffs
# ~/.claude/handoffs/<YYYYMMDD-HHMM>-<슬러그>.md 작성
orca worktree create --repo id:<repoId> --name <작업이름> --no-parent --agent claude \
  --prompt "먼저 /Users/<사용자>/.claude/handoffs/<파일명>.md 를 읽고 그 지시대로 작업해" --json
```

- 브리핑 파일 경로는 `~` 대신 절대경로로 적는다. 프롬프트는 셸이 아니라 에이전트가 읽는다.
- 브리핑 파일은 대상 저장소 안이 아니라 `~/.claude/handoffs/`에 둔다. 작업 저장소에 추적되지 않는 파일을 남기지 않기 위해서다.
- 브리핑에는 다음을 적는다.

  ```markdown
  # <작업 제목>

  ## 목적
  ## 배경 (이번 대화에서 확인한 사실)
  ## 해야 할 일
  ## 참고 경로
  ## 하지 말 것
  ```

- 새 세션이 권한 확인 모드면 워크스페이스 밖 경로를 읽을 때 한 번 확인을 요청할 수 있다. 사용자에게 미리 알린다.

### 전달 확인

`worktree create` 직후 `--prompt`가 새 세션의 첫 입력으로 들어갔는지 한 번 확인한다. 5-A는 `tui-idle`을 기다린 뒤 `terminal send`로 보내므로 이 확인 대상이 아니다. Orca 결과의 `prompt.outcome`(`handed-to-terminal`)은 터미널에 넘겼다는 뜻일 뿐 claude가 받았다는 증거가 아니다. Orca의 claude 기본 실행 인자 끝에 `--add-dir <경로>`가 붙어 있으면 가변 인자인 `--add-dir`이 뒤에 붙은 프롬프트까지 디렉터리로 먹고, 새 세션은 경고 없이 빈 화면으로 뜬다. 2026-10-19에 이렇게 위키 핸드오프 3건이 비어 있었다.

먼저 `worktree create` 결과에서 handle을 얻는다. `result.launch.outcome.kind`가 `terminal`이 아니거나 handle이 없으면 아래 명령을 돌리지 않고 확인 불가로 보고한다. `result.launch`가 없는 구 호스트는 `kind`를 볼 수 없으므로 `result.agentTerminalHandle`이 있으면 terminal로 보고 진행한다.

```bash
# handle: result.launch.outcome.handle (구 호스트는 result.agentTerminalHandle)
orca terminal wait --terminal <handle> --for tui-idle --timeout-ms 15000 --json
orca terminal read --terminal <handle> --screen --json
```

| 화면(`result.terminal.tail`) | 판정 | 처리 |
|------|------|------|
| 입력란 위(제출된 대화 영역)에 `❯`로 시작하고 브리핑 파일명이 든 줄이 있다 | 정상 | 다시 보내지 않는다 |
| 입력란(가로줄 사이의 `❯`)이 있고 그 위에 그런 줄이 없으며, 입력란 안에도 파일명이 없다 | 미전달 의심 | 아래 transcript 조회 결과로 다시 판정 |
| 파일명이 입력란 안에만 있다 (제출되지 않은 채 남음) | 확인 불가 | 재전송하지 않는다. `terminal send --text`는 입력란을 비우지 않아 같은 지시가 이어 붙은 채 제출된다 |
| 입력란이 없다 (TUI가 아직 안 그려졌거나 신뢰 확인 같은 대화상자) | 판정 보류 | `wait`와 `read`를 한 번 더 하고, 그래도 입력란이 없으면 확인 불가 |
| `read`가 실패했다 | 확인 불가 | 재전송하지 않고 보고에 적어 사용자에게 알린다 |

- `wait`는 TUI가 그려질 때까지만 기다린다. 결과를 기다리는 것이 아니다. 정상 전달이면 새 세션이 첫 턴을 도느라 idle이 늦게 오므로, 15초 타임아웃으로 끝나도 실패로 보지 않고 그대로 화면을 읽는다. Orca는 `wait` 타임아웃을 오류로 끝내므로, `wait`의 종료 코드와 결과는 판정에 쓰지 않고 항상 `read`로 넘어간다. 15초는 실측에서 TUI가 2초 안팎에 그려진 것에 여유를 둔 값이고, 그보다 늦게 뜨는 경우는 위 `판정 보류` 행이 받는다. 5-A의 90초는 TUI가 idle이 된 뒤에야 보낼 수 있어서 길게 잡은 값이라 목적이 다르다.
- `❯`가 있는지만 보지 않는다. 미전달 화면에도 입력란에 `❯ Try "..."` 안내문이 있다. 기본 `read`가 아니라 `--screen`으로 읽는다.
- 프롬프트는 실행 인자라 배너와 같은 프레임에 그려지고, 배너는 떴는데 프롬프트 줄만 없는 중간 상태는 관찰되지 않았다. 다만 새 세션이 이미 도구를 많이 돌렸으면 그 줄이 화면 밖으로 밀릴 수 있으므로, 화면에 없을 때는 재전송 전에 transcript를 본다. 브리핑 파일명은 핸드오프마다 시각이 붙어 유일하므로, `~/.claude/projects/` 전체에서 찾고 보낸 쪽 세션(브리핑을 쓴 지금 세션)의 파일만 뺀다. 보낸 쪽 세션 id는 5-A와 같은 방법으로 스크래치패드 경로에서 읽는다. 워크트리 경로로 슬러그를 계산하지 않는 것은, 계산이 어긋나면 정상 세션을 미전달로 보고 지시를 두 번 보내기 때문이다.

  ```bash
  grep -rl "<브리핑 파일명>" ~/.claude/projects/ > <스크래치패드>/transcript-hits.txt; echo "rc=$?"
  grep -v "<보낸 쪽 세션id>" <스크래치패드>/transcript-hits.txt
  ```

  첫 `grep`의 종료 코드를 파이프 없이 따로 받는다. 파이프로 이으면 보이는 종료 코드가 뒤 `grep -v`의 것이라, 조회 실패가 "남는 파일 없음"으로 읽혀 지시를 두 번 보낸다.

  | 결과 | 판정 |
  |------|------|
  | `rc=0`이고 남는 파일이 있다 | 정상 |
  | `rc=0`이고 보낸 쪽 세션 파일만 나와 남는 파일이 없다 | 미전달. 재전송한다. 프롬프트를 잃은 세션은 첫 턴이 없어 transcript를 만들지 않는다 |
  | 첫 `grep`이 `rc=1`이나 `rc=2`로 끝났거나(`rc=1`은 브리핑을 쓴 보낸 쪽 transcript조차 못 찾은 것이라 조회 경로가 어긋났다는 뜻), `grep`을 쓸 수 없는 환경(Windows 기본 셸 등)이거나, 스크래치패드 경로가 없어 보낸 쪽 세션 id를 모른다 | 확인 불가 |

  남은 파일이 새 워크트리 슬러그 디렉터리가 아니어도 정상으로 본다. 사용자가 다른 세션에 같은 파일명을 붙여 넣었을 수도 있지만, 지시를 두 번 보내는 쪽보다 덜 해롭다고 보고 다시 보내지 않는다. 이때는 보고에 그 경로를 적는다.

- `ps`로 claude 인자를 보는 방법은 쓰지 않는다. 정상 세션과 실패 세션 모두 인자 끝에 프롬프트가 보이고, 갈리는 것은 앞 플래그 순서뿐이다.
- 재전송은 같은 `--prompt` 문자열을 한 번만 보낸다. `--wait-submit 20`은 제출을 20초 동안 관찰하라는 뜻이고, 실측에서 `turn_started`가 몇 초 안에 찍힌 것에 여유를 둔 값이다. `terminal send` 결과의 `result.send.prompt.stages`에 `turn_started`가 있으면 재전송함이고, 없으면 다시 보내지 말고 확인 불가로 보고한다.

  ```bash
  orca terminal send --terminal <handle> --text "<--prompt와 같은 문자열>" --enter --wait-submit 20 --json
  ```

- 구 Orca 호스트는 `--wait-submit`을 입력 전에 거부한다. 오류 출력에 `does not support --wait-submit`과 `No input was sent`가 함께 들어 있을 때만 이 거부로 보고 `--wait-submit` 없이 한 번 보낸 뒤, 제출을 증명할 수 없으니 확인 불가로 보고한다. 그 밖의 이유로 `send`가 실패하면 입력이 나갔는지 알 수 없으므로 다시 보내지 않고 확인 불가로 보고한다. `send` 실패 메시지 끝에 붙는 `--retry-request … --wait-submit` 재시도 안내도 따르지 않는다. 그 안내는 이미 입력이 나갔을 수 있는 실패에도 붙는다.

- 확인 절차는 한 번뿐이다. `판정 보류` 때의 재조회 1회와 transcript 조회, 재전송은 이 절차에 포함된다. 판정을 확정한 뒤에는 그 터미널을 다시 읽지 않는다.

## 6. 보고와 종료

- 만든 워크트리 id, 터미널 handle, 맥락 전달 방식, 브리핑 파일 경로를 보고에 적는다.
- 실제로 보낸 내용이 `4. 확인 받기`에서 승인한 전문과 같다는 것을 보고에 남긴다. 5-B면 브리핑 파일 경로와 보낸 `--prompt` 문자열을, 5-A면 `terminal send`로 보낸 지시가 승인한 전문 그대로임을 적는다.
- 5-B면 `전달 확인` 결과를 `정상`, `재전송함`, `확인 불가` 중 하나로 적는다. `재전송함`이면 `turn_started`를 확인했다는 것을, `확인 불가`면 무엇이 실패했는지, 재전송을 보냈는지 안 보냈는지, 사용자가 새 워크스페이스를 직접 열어 봐야 한다는 것을 함께 적는다.
- 방식과 관계없이 보고 후에는 그 터미널을 읽어 진행을 확인하지 않는다. 5-B의 착수 직후 `전달 확인` 절차만 예외다. 진행 감시는 이 스킬의 몫이 아니다. 사용자가 따로 물어보면 그때 읽는다.
- 넘긴 작업의 커밋, 테스트, PR은 새 세션의 몫이다. 원래 세션에서 `chucoding:commit-pr`을 대신 돌리지 않는다.
- 새 세션이 실패하거나 잘못 착수한 것을 사용자가 알려오면, 워크트리를 다시 만들지 말고 `orca terminal send`로 같은 터미널에 보정 지시를 보낸다.

## 7. 하지 않는 것

- 판별이 애매한데 짐작으로 저장소를 고르지 않는다.
- 승인 없이 워크트리를 만들지 않는다.
- 핸드오프했다는 이유로 원래 세션의 진행 중인 작업을 중단하지 않는다.
- 만든 워크트리를 사용자 확인 없이 지우지 않는다. 잘못 만들었으면 그 사실과 함께 `orca worktree rm --worktree <id> --force`를 제안한다.
