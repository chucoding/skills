# 1. 요약

## **01. 회사와 단지를 한 라우트에 얹은 통합업무계획을 만들고 곧바로 다시 합쳤다**

`/task` 단일 라우트에 회사·단지 두 조직 스코프를 얹어 통합업무계획을 새로 구축했다(PR #1963, +9444/−1028, 107파일). 2주 안에 후속 PR 5건이 더 붙었는데, 그중 #1967은 이미 갈라진 회사·단지 로직을 다시 공용 훅과 공용 컬럼으로 모으는 작업이었다. 화면을 만들면서 스코프별 분기를 먼저 쓰고, 어긋난 규칙을 확인한 뒤 경계를 다시 그은 셈이다. 티켓 6건에 51.5시간이 들어갔고, 이는 티켓별 실적 합 116.5h의 44%다.

## **02. 잘리는 달력을 옮기지 않고 렌더링 위치를 바꿨다**

사이드패널 안에서 DS 캘린더 드롭다운이 부모 컨테이너에 가려지던 문제를, 스크롤 부모를 찾아 띄우던 `useScrollParentPortal`을 버리고 `document.body` 포털 + fixed 좌표 계산으로 교체해 해결했다(hd-ds #94, 13파일, DS 1.8.1). 날짜·시간 입력 5종이 `useDropdownPortal` 하나를 공유하게 됐고, 이 훅은 이후 스프린트에서 floating-ui 배치 계산이 들어앉는 자리가 된다.

## **03. Contrast 테마가 드러낸 것은 색이 아니라 토큰 병합 순서였다**

DS 1.8.2에서 Contrast 테마를 적용하자 Figma와 실제 렌더링 색이 어긋나고 브랜드 테마 전환 시 팔레트가 뒤섞였다. 원인은 하드코딩된 색상 값과, `$metadata.tokenSetOrder`를 무시한 토큰 세트 병합 순서였다. 병합 순서를 정렬하고 전역 폴백으로 해석된 참조는 빌드 후 경고로 드러나게 했다(hd-ds #96, 27파일). 앱 쪽은 ag-grid 텍스트 색 hex를 `base.fg.text` 토큰으로 바꿨다(#1905, 5파일).

## **04. 문서 한 건이 인접 티켓 두 건을 흡수하며 11.2시간이 됐다**

디자인 가이드 3건을 위키 `SKILL.md`에 추가했다. 이 중 HDIT-753은 섹션 구분 레이아웃과 저장 CTA 이후 화면 이동을 정하는 것이 원래 범위였는데, 나흘 전 HDIT-740이 쓴 페이지 헤더 버튼 섹션을 다시 쓰고 HDIT-317 가이드를 끌어오면서 diff가 `+190/−18`까지 늘었다. 문서 티켓 한 건이 스프린트 실적 4위(11.2h)에 올랐다.

# 2. 첼린지 상세

## Challenge 01 : 스코프 분기를 먼저 쓰고 경계를 다시 그었다

`화면 구축 · 도메인 경계 설계`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-317 (개발완료) 외 5건 — 1243 · 1289 · 1290 · 1288 · 1301 |
| 실적 | 51.5h (317 40.0h · 1243 6.0h · 1301 2.5h · 1289 · 1290 · 1288 각 1.0h) |
| PR | #1963 · #1967 · #1971 · #1970 · #1969 · #1976 · hd-ds#96 |
| 산출 | `/task` 라우트 신설, 회사·단지 공용 훅·컬럼 |

**상황**
통합업무계획은 회사와 단지가 같은 화면을 다르게 쓴다. 회사는 배포계획과 자체계획을 모두 등록하고 단지는 자체계획만 등록하며, 목록 집계와 상세 이동, 회차 조작 허용 범위가 스코프마다 다르다. 이 차이를 `/task` 라우트 하나 안에서 조직 선택으로 분기해 구현했다.

**어려웠던 지점**

1. **회사와 단지가 비슷한 일을 각자 다르게 처리하고 있었다.** #1967 본문이 증상을 그대로 적고 있다 — RFMS 상세 링크가 데이터를 가진 조직 스코프로 열리지 않고, 총 건수 필드가 `totalItemCount`와 `totalCount`로 어긋났다. 화면 두 벌을 나란히 만든 결과라 어느 쪽이 정본인지 코드만 봐서는 판정되지 않았다.
2. **PRD와 Figma가 상충한 항목은 개발과 분리되지 않았다.** 기본 지정기간과 계획명 길이가 그 자리다. 당해연도 전체 조회를 기본값으로 넣고 계획명을 20자로 통일하면서 회차 계획명도 100자에서 20자로 내렸는데, #1971 리뷰 요청에 「기존 조회 동작(전체 기간 조회)과 달라지는 점이 의도한 정책인지 확인」이라고 남겼다. 확정하고 나서도 되물어야 하는 상태로 머지했다는 뜻이다.
3. **날짜 교차 검증이 스키마와 입력 컴포넌트 양쪽에 있었다.** 시작일이 종료일보다 늦는 조합을 zod `refine`도 막고 `DateRangePicker`의 입력 제한도 막았다. 어느 층을 정본으로 둘지가 갈렸다.

**판단**
공통 로직은 `pages/task-plan` 안으로 모으고 스코프별로 달라야 하는 규칙만 분기로 남겼다. 등록 패널의 범위 판단과 미리보기 계산은 `useTaskPlanCreateScope`·`useTaskPlanPreview`로 갈라, 화면 두 벌이 아니라 훅 하나에 조건을 모았다. 교차 검증은 입력 컴포넌트가 이미 순서를 막는다는 근거로 스키마에서 제거했다 — 검증을 한 층에 모으는 대신, `DateRangePicker`를 거치지 않는 입력 경로가 생기면 순서 역전이 그대로 통과한다는 것을 받아들였다. 등록 패널 상태는 `createMode`(nullable) 하나를 `createMode`와 `isCreateOpen` 둘로 쪼갰는데, 닫힘 애니메이션 도중 `createMode`가 `null`이 되면서 문구가 사라지던 문제를 열림 여부와 유형을 분리해 막은 것이다.

**남은 것**
연결 해제 판정은 `isComplexDisconnected` 필드 하나로 트리 행에 실려, 흐림 처리·배지·상세 이동 차단이 같은 값을 본다. 조건을 화면마다 다시 계산하지 않는다.

## Challenge 02 : 잘리는 달력을 컨테이너 밖으로 꺼냈다

`디자인 시스템 · 오버레이 렌더링`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-1164 (개발완료) |
| 실적 | 4.0h |
| PR | hd-ds#94 · +398/−347 · 13파일 |
| 산출 | DS 1.8.1 · `useDropdownPortal` |

**상황**
스크롤 영역 안에서 날짜·시간 입력 드롭다운을 열면 부모 컨테이너에 가려지거나, 드롭다운 높이만큼 스크롤 범위가 늘어났다. 사이드패널 안에서 달력이 잘리는 형태로 드러났다.

**어려웠던 지점**

1. **가려지는 위치를 보정하는 것과 렌더링 위치를 옮기는 것 중에 골라야 했다.** 기존 `useScrollParentPortal`은 스크롤 부모를 찾아 그 안에 띄우는 방식이라, 그 부모가 다시 `overflow`를 가지면 같은 증상이 되풀이된다. 보정을 쌓는 쪽은 사용처가 늘수록 예외가 늘어난다.
2. **`body`로 옮기면 위치 계산이 통째로 새 책임이 된다.** fixed 좌표, z-index, 뷰포트 경계 보정, 스크롤·리사이즈 재배치, 드롭다운 크기 변경 감지가 전부 따라온다. 컴포넌트 안에 있던 동안에는 부모가 해주던 일이다.
3. **입력 5종이 각자 다른 포털을 갖고 있었다.** `DateInput`·`DateRangeInput`·`DateTimeInput`·`MonthInput`·`TimeInput`이 같은 문제를 각각 겪는다.

**판단**
`useScrollParentPortal`을 없애고 `useDropdownPortal` 하나가 body 포털과 위치 계산을 모두 맡게 해 입력 5종이 같은 훅을 쓰도록 했다. 입력 영역이 화면 밖으로 벗어나면 드롭다운을 따라 움직이지 않고 닫는다 — 끝까지 따라붙는 대신 닫는 쪽을 택한 것이다. 외부 클릭 닫힘이 포털 이후에도 유지되는지는 코드로 증명하지 못해 리뷰 확인 항목으로 넘겼다.

**남은 것**
`InScrollContainer` 스토리가 스크롤 컨테이너 안 동작을 고정했다. 다만 오버레이를 `body`로 옮긴 대가는 나중에 나왔다 — 화면을 전환해도 keep-alive로 남은 드롭다운이 이전 화면 위에 떠 있는 문제(HDIT-2678)가 26_3_#5에서 따로 처리됐다.

## Challenge 03 : 색이 어긋난 자리를 좇지 않고 토큰 병합 순서를 고쳤다

`디자인 토큰 · 테마`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-213 (개발완료) · HDIT-1301 (개발완료) |
| 실적 | 2.0h (HDIT-213). HDIT-1301의 2.5h는 Challenge 01에 계상 |
| PR | #1905 · hd-ds#96 · #1976 |
| 산출 | DS 1.8.2 · 스토리북 브랜드 테마 전환 |

**상황**
Contrast 테마를 적용하자 Figma 디자인과 실제 렌더링 색이 어긋나고, 브랜드 테마를 전환하면 팔레트가 뒤섞였다. 증상이 Calendar, FileUpload, Select 계열 등 여러 컴포넌트에 흩어져 나타났다.

**어려웠던 지점**

1. **증상은 색이었지만 원인은 빌드 스크립트에 있었다.** `generateTokenExports.ts`가 토큰 세트를 병합하는 순서가 `$metadata.tokenSetOrder`와 무관해, 브랜드 팔레트가 전역 값에 밀렸다. 컴포넌트마다 색을 고치면 증상은 사라지지만 브랜드 전환은 계속 깨진다.
2. **하드코딩을 토큰으로 바꾸면 실제 색이 달라지는 자리가 생긴다.** Calendar의 outside 셀과 FileUpload 아이콘이 그랬다. 회귀인지 의도된 정정인지는 코드가 말해주지 않는다.
3. **Badge 이름 체계를 Figma에 맞추면 기존 사용처가 깨진다.** `purple`·`teal`이 이미 쓰이고 있었다.

**판단**
세트 병합을 `tokenSetOrder` 기준으로 정렬하고, 전역 폴백으로 해석된 참조는 빌드 후 경고로 노출하게 했다 — 조용히 그럴듯한 값이 나오는 것보다 어긋난 참조가 보이는 쪽을 택했다. Badge는 Figma 네이밍(`brand`·`accent`·reversal 계열)을 추가하되 `purple`·`teal`을 `@deprecated`로 남겨 사용처를 한 번에 고치지 않았다. 색이 달라지는 자리는 스스로 판정하지 않고 「의도한 변경인지」를 리뷰 요청에 이름으로 적어 넘겼다.

**남은 것**
스토리북 툴바에서 브랜드 테마 5종(HomeDot·Modulor·RA·RD·RTB)을 전환할 수 있게 해, 다음 토큰 변경은 브랜드별로 먼저 눈으로 본다.

## Challenge 04 : 문서 티켓이 인접 티켓 두 건을 흡수했다

`디자인 가이드 문서화`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-753 (배포완료) · HDIT-740 (배포완료) · HDIT-1093 (배포완료) |
| 실적 | 15.0h (753 11.2h · 1093 2.8h · 740 1.0h) |
| 산출 | 위키 `homedot-design-skill/SKILL.md` 3개 커밋 |
| PR | hd-cloud-wiki #161 · #169 · #175 (코드 저장소 PR 없음) |

**상황**
`homedot-design-skill`은 에이전트가 UI를 만들 때 먼저 읽는 문서다. 페이지 헤더 버튼 색·배치, 상세 화면 섹션 간격, 저장 이후 화면 이동, 이모지 입력 처리가 화면마다 제각각이었고 규칙이 적힌 자리가 없었다.

**어려웠던 지점**

1. **규칙을 새로 정할지, 이미 굳어진 관행을 승격할지가 갈렸다.** HDIT-740은 후자를 택해 `PageHeader` `rightSlot` 사용처 54개 파일과 헤더 버튼 102개를 세어 규칙을 뽑았다(`size`는 106개 중 97개가 `medium`이라 `medium`으로 통일). 근거는 커밋 메시지에만 남고 문서 본문에는 들어가지 않았다.
2. **저장 후 어디로 보낼지에 목적지가 없었다.** Hub의 상세 화면은 조회와 수정을 한 화면이 겸한다. 그래서 저장 성공 후 보내줄 「뷰 모드 상세」라는 자리가 아예 없다는 것이 문서에 적힌 판단 근거다.
3. **나흘 전에 쓴 규칙을 다시 써야 했다.** HDIT-753은 자기 범위(섹션 레이아웃·저장 CTA)를 끝낸 뒤 HDIT-740이 쓴 헤더 버튼 섹션의 「버튼이 2개 이상일 때」 게이팅을 없애 목록·상세 공통 전략으로 일반화하고, HDIT-317 가이드를 이 문서로 옮겼다. 티켓 경계와 문서 경계가 맞지 않았다.

**판단**
저장 성공 시 상세에 남지 않고 목록으로 이동하는 것을 공통 정책으로 못박고, 예외는 화면 이름이 아니라 동작으로 정의했다 — 「한 화면 안에서 대상만 바꿔가며 연속으로 입력하는 화면」만 상세에 남으며, 애매하면 기본 정책을 따른다. 순서 제약도 최소한만 남겼다. `disablePrompt()`가 `navigate()`보다 먼저라는 것 하나만 강제하고 토스트와 캐시 무효화 위치는 화면 사정에 맡겼다. 규칙을 다 정하는 대신 지키지 않으면 증상이 나는 것만 강제한 것이다. 위반 코드는 지우지 않고 이름으로 남겼다 — `EmployeeFormPage`의 삭제 핸들러가 `disablePrompt()`를 mutation 호출 전에 부른다는 사실을 「새 화면에서 따라 하지 마세요」와 함께 적었다.

**남은 것**
규칙마다 배제한 대안과 그 근거를 같은 자리에 적는 형태가 자리 잡았다. 다만 이 문서의 수명은 확인됐다 — HDIT-753이 정한 `scrollIntoView` 스크롤 방식은 9월에 상위 레이아웃까지 밀리는 버그(HDIT-2569)로 반증돼 `scrollToCenter`로 뒤집혔다.
