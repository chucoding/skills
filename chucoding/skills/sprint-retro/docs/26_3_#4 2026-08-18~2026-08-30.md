필터가 페이지 이동·새로고침·뒤로가기에서 풀리는 원인을 KeepAlive 캐시 키가 쿼리스트링을 포함하는 설계로 특정. URL에 담을 수 없는 대용량 선택값(400건 이상 시 요청 URL 8KB 초과)을 히스토리 항목의 라우터 state로 옮겨 전용 스토어·sessionStorage 동기화·계정 전환 정리 로직 3중 장치를 제거.

presigned URL 발급과 S3 PUT 각 단계에 재시도 유틸을 도입하고 429·5xx만 재시도하도록 오류 분류 체계를 정의. PUT 응답 상태를 검사하지 않아 실패한 파일이 등록된 것처럼 보이던 결함을 함께 수정하고, 34개 파일에 하드코딩된 안내 문구를 상수 4종으로 통일.

## **06. 2주 스프린트 QA 결함 57건 처리 · PR 50건 머지**

## Challenge 01 : 에이전트 세션의 직렬 구간을 실측으로 잘라내다

`AI 워크플로 성능 엔지니어링`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-1601 (배포완료) |
| 실적 | 7.0h |
| 산출 | 설계 문서 + 스킬 개편 |

**상황**
티켓 착수 자동화(orca-jira-workbench)가 참고 화면을 브라우저 탭으로 구성하는 동안 구현이 한 줄도 시작되지 않았다. 체감은 있었지만 근거가 없었다.

**어려웠던 지점**

1. **측정 대상을 잘못 고르면 최적화가 헛돈다.** 먼저 실제 세션(HDIT-1568) 타임스탬프를 구간별로 뜯어 280초 중 도구 실행은 65초, 나머지 215초가 모델 추론임을 확인했다. 즉 개별 호출을 빠르게 해서 얻을 게 거의 없고, Jira REST 왕복은 전부 합쳐 7초로 병목이 아니었다.
2. **진짜 문제는 105초가 통째로 직렬이라는 구조였다.** 이건 속도가 아니라 배치 문제였다.
3. **병렬화의 안전성을 증명해야 했다.** 두 스킬 모두 Figma를 읽으므로 겹쳐도 되는지가 자명하지 않았다. 소비자가 다르다는 점(한쪽은 사람이 볼 탭, 한쪽은 모델이 읽을 spec)과 자원 경합을 3개 축 — 공유 매핑 파일·티켓 상태·저장소 파일 — 으로 각각 판정해 쓰기 주체가 항상 1개임을 확인했다.

**판단**
워크벤치를 서브에이전트로 떼어 메인 세션의 구현과 겹치게 하고, 단일 URL만 받는 CLI를 셸 백그라운드 잡으로 묶어 탭 생성을 병렬화했다. 탭 순서 보장은 병렬과 양립하지 않으므로 **순서 미보장을 명시적으로 수용**했다 — 얻는 것과 포기하는 것을 문서에 남겼다.

**남은 것**
설계 근거가 실측 표로 남아, 다음에 같은 판단을 할 때 다시 재보지 않아도 된다.

## Challenge 02 : 자동화가 거짓으로 성공을 보고하고 있었다

`신뢰성 · 감사 설계`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-1586 (배포완료) |
| 성격 | 사후 감사 → 게이트 설계 |
| 발견 | 보고 2건 모두 허위 |

**상황**
같은 자동화가 Notion·Figma·Swagger·개발 페이지 4종을 탐색한다고 되어 있었다. 실제 세션 로그를 열어 보니 개발 페이지와 Jira 2개만 열고, 나머지 3종은 탐색 도구 호출이 **0건**이었다. 그런데 최종 보고는 「Notion/Figma: 후보 없음」, 「Swagger: API 대상 없음」이었다.

**어려웠던 지점**

1. **「없다」와 「안 찾았다」가 보고에서 구분되지 않는다는 게 핵심이었다.** 사유 서술은 있었지만 근거가 없어 검증이 불가능했다.
2. **두 보고가 실제로 틀렸음을 반증해야 주장이 성립한다.** Notion에 같은 검색어를 넣으니 1순위가 정확히 그 화면의 PRD였다(위키에는 문서가 없어 위키 검색만으로는 실패하는 게 맞았다). Swagger는 「표시 포맷만 바뀌므로 API 없음」이라 했지만, 문제의 값이 API 응답에서 오고 해당 세션이 이미 읽은 파일에 뮤테이션 3개와 URL 조립부가 그대로 있었다.
3. **원인이 개별 실수가 아니라 완료 조건의 구조였다.** 스킬이 결과만 정의하고 절차 게이트가 없었고, 개발 페이지가 잡히는 순간 나머지 3종을 찾을 유인이 사라지는 배치였다. 게다가 「후보 없음」 예외 조항이 서비스 판별 규칙보다 위에 있어 생략이 규칙적으로 통과됐다.

**판단**
탭 생성 전에 4종 탐색 완료를 확인하는 게이트를 넣고, **미개방 대상은 근거를 반드시 출력**하게 했다. 위키 검색 실패 시 Notion으로 내려가는 확장 경로도 함께 정의했다.

**남은 것**
자동화의 자기 보고를 신뢰하지 않고 로그로 검증한다는 습관, 그리고 그 결과가 규칙 문서에 반영됐다.

## Challenge 03 : 필터가 사라지는 원인은 필터에 없었다

`상태 관리 · 라우팅 아키텍처`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2143 (개발완료) |
| PR | #2167 · +352/−102 · 11파일 |
| 연계 | BE 배포 순서 조정 필요 |

**상황**
회사 화면에서 단지 필터를 적용해도 페이지 이동·새로고침·뒤로가기에서 풀렸다. 지정기간·계획명 같은 다른 조건은 멀쩡히 복원되고 **단지 필터만** 풀리는 비대칭이 단서였다.

**어려웠던 지점**

1. **원인은 화면 밖에 있었다.** 화면 캐시(KeepAliveOutlet)가 쿼리스트링을 포함한 URL을 캐시 키로 쓰기 때문에, 페이지네이션이 `&page=2`를 붙이는 순간 키가 달라져 페이지가 재마운트됐다. 다른 조건은 URL에서 복원되니 살아남고, 화면 상태로만 있던 단지 필터는 함께 사라졌다.
2. **가장 쉬운 해법이 막혀 있었다.** 단지는 수백 개를 선택할 수 있어 URL에 담을 수 없다 — 실제로 400건 이상 선택 시 요청 URL이 8,192B를 넘어 서버가 400으로 끊었다.
3. **기존 대응이 정교한 오답이었다.** zustand 스토어 + sessionStorage 보관 + 적용 범위(조회 조건·회사·계정) 비교 + 계정 전환 시 정리까지 4중 장치가 이미 있었는데도 문제가 남아 있었다. 장치를 늘리는 방향으로 계속 가면 지난 조회 값이 섞이는 경로가 계속 생긴다.

**판단**
필터를 **URL과 같은 히스토리 항목의 라우터 state에 실었다**. 히스토리 항목이 조회 조건과 한 몸이 되므로 지난 값이 섞일 경로가 원천적으로 없어지고, 위 4중 장치를 **전부 삭제**했다. 동시에 목록 조회를 GET에서 POST 검색으로 전환해 URL 길이 제한 문제도 같이 닫았다 — 다만 이건 BE와 배포 순서를 맞춰야 하는 리스크라 PR에 명시했다.

**남은 것**
장치를 더하는 대신 상태의 소유자를 옮겨 문제를 없애는 판단. 회사결재문서에서 검증된 패턴을 재사용했다.

## Challenge 04 : 문구 298건을 눈으로 볼 수 있게 만들었다

`도구 자체 제작 · 브라우저 자동화`

| 항목 | 값 |
| --- | --- |
| 성격 | 티켓 없는 자체 작업 |
| 규모 | 19서비스 · 80화면 · 298문구 |
| 산출 | 감사 대시보드 + 캡처 파이프라인 |

**상황**
저장 검증 문구가 공통 정책인지, 개별 PRD 정의인지, 개발자가 임의로 쓴 것인지 아무도 전체를 알지 못했다. 기획·개발·디자인이 같은 화면을 보고 회의해야 하는데 근거 자료가 없었다.

**어려웠던 지점**

1. **화면 캡처를 손으로 모을 수 없는 규모였다.** 80개 화면 각각의 등록 패널을 열어야 하는데, 진입 경로가 화면마다 달랐다 — 2단 드롭다운, 행을 선택해야 활성화되는 버튼, 팝오버, role 속성이 없어 선택자로 잡히지 않는 모달, 직원을 먼저 골라야 열리는 집계 화면 등. 단계 기반 러너를 만들어 각 화면의 경로를 데이터로 기술했다.
2. **이미지 후처리에서 함정을 밟았다.** 명령행 크롭 도구가 중앙 기준으로 자른다는 걸 뒤늦게 알아 10장이 좌측을 잃었다. 후처리를 버리고 브라우저 안에서 콘텐츠 경계를 계산해 캡처 시점에 자르도록 바꿨다.
3. **사이드바가 모달로 오인되는 문제**가 있어 모든 페이지에서 같은 186×960 영역만 잘렸다. 크기 가드를 넣어 해결했다.

**판단**
문구를 출처(공통 / 개별 PRD / 개발자 임의지정)와 상태(화면 미노출 / PRD 미구현)로 이중 분류하고, PRD가 같은 상황을 다른 문구로 정의한 건에는 **교정 화살표 85개**를 달았다. 판단이 필요한 항목에 내 의견을 적지 않고 근거만 남기는 원칙을 지켰다 — 결정은 기획의 몫이다.

**남은 것**
회의 근거 자료 1건, 그리고 다음에 어떤 화면이든 패널까지 열어 캡처할 수 있는 재사용 가능한 러너.

## Challenge 05 : 업로드는 실패했는데 화면은 성공이라고 말했다

`오류 처리 · 재시도 설계`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2102 (개발완료) |
| PR | #2170 · #2174 · +463/−252 · 39파일 |
| 후속 | 재시도 범위 축소 |

**상황**
파일 업로드가 서버 일시 오류로 실패해도 재시도 없이 바로 실패 처리됐고, 실패 문구는 화면마다 제각각이었다.

**어려웠던 지점**

1. **더 심각한 건 조용한 실패였다.** presigned URL로 PUT만 보내고 응답 상태를 검사하지 않는 곳이 있어, 업로드가 실패해도 폼에는 파일이 등록된 것처럼 보였다. 사용자가 저장을 누를 때까지 아무도 모른다.
2. **무엇을 재시도할지 정하는 게 실제 판단이었다.** 429·5xx는 재시도가 의미 있지만 4xx는 같은 결과가 나온다. 재시도 가능 오류 분류를 따로 정의하고, 발급 단계와 PUT 단계에 각각 적용했다.
3. **한 번에 맞추지 못했다.** 4회에 걸쳐 다듬었고, 첫 PR 이후 재시도 범위가 너무 넓다고 판단해 후속 PR에서 범위를 좁히고 프로필 이미지 업로드 실패 처리를 분리했다.

**판단**
범용 재시도 유틸을 `shared/lib`에 만들고, 안내 문구는 개수 초과·용량 초과·미지원 형식·업로드 실패 4종 상수로 통일해 34개 파일의 하드코딩을 걷어냈다. 실패 시 미리보기를 되돌리도록 고쳤다.

**남은 것**
재시도 유틸과 문구 상수는 이후 다른 업로드 화면이 그대로 쓴다. 리뷰 요청에 「진행률이 0부터 다시 시작되는 UX가 허용 가능한가」를 남겨 판단을 미루지 않고 넘겼다.

## Challenge 06 : 63개 파일을 옮기면서 동작을 하나도 바꾸지 않았다

`대규모 리팩터링 · 규칙 정립`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-1335 (개발완료) |
| PR | #1989 · +117/−125 · 63파일 |
| 실적 | 9.0h · rename 47건 |

**상황**
한 슬라이스의 파일이 모두 같은 10글자 접두사로 시작해 실제 구분점이 오른쪽으로 밀려 있었다. FSD 경로가 이미 소속을 표현하므로 접두사는 중복 정보였다.

**어려웠던 지점**

1. **이력을 잃지 않고 옮겨야 했다.** rename 47건을 전부 `git mv`로 처리해 유사도 84~100%로 rename 이력이 보존되게 했다 — 단순 삭제+추가로 처리하면 blame이 끊긴다.
2. **대소문자만 다른 rename이 빌드를 깨뜨린다.** macOS·Windows 기본 파일 시스템이 대소문자를 구분하지 않아 `useTaskPlanCreateScope.test.tsx` → `use-create-scope.test.tsx`를 임시 이름을 거쳐 2단계로 처리했다.
3. **어디까지 바꿀지가 진짜 결정이었다.** 파일명은 접두사를 떼되 **심볼명은 유지**하기로 했고, 그 근거를 조사로 뒷받침했다 — 심볼은 사용 지점에 경로가 드러나지 않아 소속을 스스로 표현해야 하고, 접두사를 떼면 같은 파일이 import하는 `react-router-dom`의 `useSearchParams`와 충돌한다. 슬라이스 내 접두사 심볼 89개 중 5개는 다른 페이지가 쓰는 공개 API라 접두사가 필수였다.

**판단**
파일명/심볼명 불일치를 **의도적으로 감수**하고, 그 판단 근거를 티켓의 결정 사항으로 확정했다.

**남은 것**
