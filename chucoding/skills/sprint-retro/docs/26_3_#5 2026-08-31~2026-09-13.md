# 1. 요약

## **01. 날짜 입력 5종을 한 스프린트에 다시 만들다**

확인 버튼 2단계 조작 VOC 하나에서 출발해 DatePicker 계열 5종의 배치·키보드·초기화·오류 문구를 전부 다시 짰다. 팝오버 배치를 손으로 짠 계산에서 floating-ui 4단계 폴백으로 넘겨 입력 5종이 같은 훅을 공유하게 만들고, 캘린더가 W3C APG Combobox 속성을 노출해 소비 앱의 Enter 내비게이션 훅에 참여하도록 계약을 정의했다. 2주 동안 디자인 시스템 릴리스가 6회(1.8.7 → 1.8.12) 나갔다.

## **02. 오류를 알리는 자리가 셋이 되면서 서로 어긋났다**

세대관리 상세에 오류 항목 바를 붙이며 검증 시점을 `onChange`에서 `onSubmit`으로 옮겼더니, 오류를 알리는 자리가 칩·툴팁·토스트 셋으로 늘고 서로 다른 오류를 가리키기 시작했다. 원인이 세 겹으로 갈렸다 — 모달 경로가 `handleSubmit`을 타지 않아 아무것도 안 뜨는 것, react-hook-form이 `errors`를 제자리 변경해 React Compiler의 메모이제이션이 안 풀리는 것, zod가 필드 `refine`을 최상위 `superRefine`보다 먼저 담아 순서가 뒤집히는 것. PR 5건으로 맞춘 뒤 검증 시점과 오류 표시 규칙을 위키 문서로 고정했다.

## **03. 고칠 수 없는 상태를 화면에 만들지 않기로 했다**

「세대주와 동일」 체크만 했는데 값이 안 바뀐 필드에 변경 표시가 뜨는 오탐을, 라디오를 해제하는 방향과 폼 값을 유지하는 방향 중에 골라야 했다. 성별은 저장으로 비울 수 없다는 사실(서버 enum, `null`은 미변경)을 확인하고 폼 값 유지를 택했다. 그 대가로 체크박스 문구가 만드는 기대와 화면이 어긋나는 것을 받아들이고, 디자인 시스템 쪽 수정은 사용처 33곳 회귀 부담 때문에 별도 티켓으로 분리했다.

# 2. 첼린지 상세

## Challenge 01 : 확인 버튼 하나를 없앴더니 5종을 다시 짜게 됐다

`디자인 시스템 · 입력 컴포넌트`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2425 (메인) + HDIT-2545 · 2546 · 2547 · 2677 |
| 실적 | 14.1h (5건 합, 업무 로그 기준 — 5절 참고) |
| PR | hd-ds 기능 8건 · 최대 #117 +1,886/−192 · 26파일 |
| 산출 | DS 1.8.7 ~ 1.8.12 (릴리스 6회) |

**상황**
날짜 하나를 고르는 데 팝오버에서 날짜를 클릭하고 확인 버튼까지 눌러야 한다는 VOC가 Slack으로 올라왔다(원본 HC-2914). 같은 컴포넌트군이 Figma CORE_2.9.0 스펙과 크기·모서리·스크롤바가 어긋나 있었고 트리거 재클릭 토글과 Esc 닫기도 동작하지 않았다.

**어려웠던 지점**

1. **티켓 문구를 그대로 따르면 시간 계열에서 값을 확정할 수단이 사라진다.** 티켓은 「확인 및 초기화 버튼 삭제」였고 첫 PR(#113)이 5종 전부에서 제거했는데, 시와 분이 별도 컬럼이라 한쪽만 골라선 값이 미완성이다. 라이브러리 5종을 조사하니 MUI X·Ant Design·Kendo·Element Plus 4종이 분리 컬럼 시간 피커에 확인 버튼을 두고 있었고, 과거 티켓 HOM-1543 원문에도 「시간 설정이 필요한 경우에만」이라는 예외가 이미 적혀 있었다. 머지 27시간 만에(#113 09-02 01:31 → #115 09-03 04:35) 시간 계열만 복구했다.
2. **초기화 버튼 제거가 과거 요청 6건을 되돌리는 변경이었다.** 팝오버 안 초기화 버튼을 기본 제공하는 라이브러리는 0곳이고 입력창 우측 X가 사실상 표준인데, 이 버튼은 HOM-621·912·1543·2065·2127·2138 여섯 티켓에서 「넣어달라」고 요청됐던 기능이다. 게다가 5종 중 TimeInput만 표시부가 입력창이 아니라 값을 비울 수단이 아예 없어졌다.
3. **자기 작업이 만든 결함이 뒤따라왔다.** 캘린더를 6주 고정 328×364로 키우면서 팝오버가 입력창을 가릴 확률이 올라갔다. 위아래 어디에도 못 들어가는 조건을 계산하니 뷰포트 높이 794px 미만이었고, 1366×768 노트북과 200% 확대 화면이 사정거리에 들어왔다.

**판단**
확인 버튼은 **날짜 단일 입력만 즉시 확정, 시간 계열은 유지**로 갈랐다. 컴포넌트마다 커밋 시점이 다른 계약이 남는 것을 감수한 선택이다. 초기화는 팝오버 복원 대신 입력창 hover X로 옮겼는데, 터치 기기에는 hover가 없어 모바일 이식 시 초기화 경로가 사라진다는 점을 알면서 택하고 디자인팀에 별도 요청으로 남겼다. 배치 계산은 손으로 짠 코드를 버리고 floating-ui 미들웨어로 넘겨 입력 5종이 같은 훅을 쓰게 했다 — 옆 배치 시 세로 위치가 손 구현과 달라지는 것은 리뷰에서 「이 옵션 한 줄만 빼면 된다」고 명시해 되돌릴 여지를 남겼다.

**남은 것**
`useDropdownPortal` 한 곳을 고치면 입력 5종에 전부 적용되는 구조, 그리고 캘린더 입력이 소비 앱의 `useEnterNavigation` 프로토콜에 참여하는 방식이 규칙으로 정해졌다. 계측 함정도 기록으로 남았다 — 배경 탭에서는 focus/blur가 발생하지 않아 포커스가 얽힌 동작이 통과한 것처럼 보인다.

## Challenge 02 : 오류를 세 군데서 알리기 시작하자 서로 다른 말을 했다

`폼 검증 · 상태 파생`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2542 · 2606(reopen 2회) · 2706 · 2705 |
| 실적 | 12.5h (4건 합) |
| PR | #2243 · #2263 · #2271 · #2276 · #2283 · #2286 |
| 산출 | 위키 `form-validation.md` (hd-cloud-wiki#239) |

**상황**
세대관리 상세는 저장 실패를 사용자에게 제대로 알리지 못하는 화면이었다. 오류가 `onChange`마다 계산돼 입력 중에도 빨간 테두리가 떴고, 어떤 필드가 잘못됐는지는 폼 전체를 스크롤해 찾아야 했다. 같은 입주민 영역의 기본정보관리에는 이미 오류 항목 바가 들어가 있어 화면마다 방식이 갈린 상태였다.

**어려웠던 지점**

1. **오류 항목 바를 붙이면서 검증 시점을 옮긴 것이 연쇄의 출발점이었다.** 알리는 자리가 칩·툴팁·토스트 셋으로 늘었고, 이어진 디자인 QA가 잡은 것은 셋이 겹치거나 서로 다른 오류를 가리킨다는 문제였다. 증상을 하나씩 고치는 대신 원인이 어디로 수렴하는지를 봐야 했다.
2. **원인이 세 겹으로 갈렸고 층마다 해법이 달랐다.** 동/호 이동 모달은 `handleSubmit`을 거치지 않아 셋 중 아무것도 뜨지 않았다 — 아웃라인은 `errors`를, 칩과 셀 강조는 `submitCount`를 보는데 둘을 함께 채우는 것은 `handleSubmit`뿐이다. 저장 후 칩만 정체된 것은 react-hook-form이 필드별 재검증에서 `errors`를 제자리 변경하고 같은 참조를 넘기기 때문인데, `useMemo`를 지워도 소용없다 — 이 저장소는 React Compiler가 켜져 있어 컴파일 결과가 같은 메모이제이션을 다시 만든다. 툴팁이 화면 아래쪽부터 뜬 것은 zod가 객체 필드 `refine`(이메일)을 최상위 `superRefine`(성명 필수)보다 먼저 담기 때문이었다.
3. **두 번 되돌아온 이유가 서로 달랐다.** 1차는 범위가 열려 있었기 때문이다 — 토스트를 지우다 애매한 자리를 발견해 금요일에 먼저 물었고, 디자이너가 「정리해서 월요일에」라고 예고한 뒤 월요일 10:53 요청이 오자 6분 뒤 티켓이 열렸다. 예상 못 한 재작업이 아니라 합의된 유예지만, 1.5h로 잡힌 티켓에 +264/−237 7파일이 붙었다. 2차는 도구가 만든 회귀다 — `motion.div` 위에 넣은 JSX 주석이 pre-commit의 `eslint --fix`를 지나며 `\{' '}` 텍스트 노드로 변형돼 화면에 역슬래시가 그대로 렌더됐다. 수정은 −1줄이었다.

**판단**
알리는 자리를 **칩과 필드 툴팁으로 좁히고**, 붙일 셀이 있는 오류의 토스트는 전부 없앴다. 붙일 곳이 없는 서버 거부만 토스트로 남겼다. 칩 갱신은 렌더 시점 파생을 버리고 `subscribe` 콜백이 준 값을 쓰는 방식으로 바꿨는데, `reValidateMode`를 `onBlur`에서 `onChange`로 옮기면서 매 입력마다 zod 스키마 전체가 도는 비용을 받아들였다 — 세대원과 차량 행이 많은 단지의 체감 지연은 리뷰 요청으로 넘겼다. 툴팁 순서는 별도 탐색 함수를 만들지 않고 **칩이 이미 정의한 화면 순서를 재사용**해 두 표시가 갈릴 여지 자체를 없앴다.

**남은 것**
`scrollToCenter`와 `parseGridErrorKey`가 `pages/employee`에서 `shared/lib`으로 올라가 두 화면이 한 정의를 공유한다. 셀 포커스 함수 두 개는 **올리지 않았다** — 섹션 조회 방식과 폴백이 화면마다 달라 합치면 주입 인자만 늘고 한쪽 동작이 바뀌기 때문이다. 가장 큰 산출은 위키 문서다. 「우리가 쓰는 검증 시점이 업계 표준과 어디서 갈라지는지 위키 어디에도 없어, 지금 동작이 의도된 선택인지 결함인지 판단할 근거가 없었다」는 이유로 쓰였고, 미결 두 항목(저장 이후 전 필드 재검증, 오류칩 바 형태)을 문서에 그대로 남겼다.

## Challenge 03 : 저장할 수 없는 상태를 화면에 만들지 않기로 했다

`폼 상태 · 디자인 시스템 경계`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2691 · HDIT-2749 |
| 실적 | 3.5h (2건 합) |
| PR | #2279 +210/−9 · #2285 +45/−4 |
| 후속 | HDIT-2757 (DS RadioGroup) |

**상황**
소유주 정보에서 「세대주와 동일」을 체크하면, 값이 바뀌지 않은 필드에도 변경 표시가 뜨고 헤더에 「변경됨」이 붙었다. 생년월일에서 먼저 발견됐고, 그 검증 중에 성별에서도 같은 것이 나왔다.

**어려웠던 지점**

1. **티켓이 기대 결과로 두 방향을 대놓고 제시했다.** 라디오를 해제할 것인가, 폼 값을 유지할 것인가. 확인해 보니 성별은 저장으로 비울 수 없다 — 서버가 `null`을 받으면 컬럼을 건드리지 않고, enum이라 빈 문자열도 못 받는다. 라디오 해제 쪽은 **저장할 수 없는 상태를 화면에 만드는 선택**이었다.
2. **디자인 시스템 쪽 원인이 버전 업으로 해결되지 않았다.** `RadioGroup`이 `value={undefined}`에서 선택을 해제하지 않는 것은 매 렌더 `value !== undefined`로 제어 여부를 판정하기 때문인데, 이 코드는 1.7.0 이후 변경이 없고 1.8.9 설치본과 1.8.11 배포본의 컴파일 결과가 동일했다. 고치려면 사용처 33곳 회귀 확인과 별도 릴리스가 따라온다.
3. **세 번째 길은 계약 변경이었다.** 서버에 enum 비우기를 요청하는 방향은 API 계약을 건드리는 일이라 이 티켓의 범위를 넘었다.

**판단**
폼 값을 유지하고, 세대주 값이 있을 때만 복사하도록 고쳤다. 그 결과 **「세대주와 동일」을 체크했는데 소유주 성별이 세대주와 달라 보이는 상태를 허용**하게 된다. 문구가 만드는 기대와 어긋나는 지점이라, 감추지 않고 리뷰 요청에 그대로 적어 판단을 넘겼다. 디자인 시스템 수정은 HDIT-2757로 분리했다 — 제어 판정을 `'value' in props`로 바꾸면 비제어와 「제어이면서 선택 없음」을 구분할 수 있다는 해법까지 적어 두었다.

**남은 것**
같은 패턴이 `HeadForm`에도 있지만 세대주 성별을 지우는 경로가 없어 현재 증상이 없다는 것까지 확인해 기록했다. 손대지 않은 자리를 「안전하다」가 아니라 「왜 지금은 안 터지는가」로 남긴 것이 다음 사람이 쓸 정보다.

# 5. 잘 안 된 지점

**가동률이 60%로 떨어졌다**
실가동 47.7h에 캐파 80h다. 지난 스프린트가 57.3h / 66h로 87%였으니 27포인트 내려갔다. 평균 동시 진행도 2.47건에서 0.89건으로 줄었다. 스프린트가 오늘 끝나 경과분이 캐파 전체와 같으므로 중간 집계 때문에 낮게 나온 값이 아니다. 개발 티켓 32건에 61.3h를 쓴 것과 나란히 놓고 볼 일이지, 한쪽만으로는 설명되지 않는다.

> 지난 스프린트 평균 동시 진행을 **2.47건**으로 적었는데, 26_3_#4 회고 본문에는 **3.9건**으로 되어 있다. 둘 다 같은 스프린트의 값이고 측정 기준이 다르다. 그 회고가 근거로 삼은 스냅샷(`26_3_#4 2026-08-18~2026-08-30.json`, 2026-09-02 생성)은 85건 중 업무 로그가 **0건**이라 전부 상태 체류로 계산된 값이고, 이 회고는 로그가 78건 붙은 뒤 다시 수집해 로그 기준으로 계산한 값이다. 티켓별 합이 257.2h 대 163.3h로 1.58배 차이난다. 실가동(57.3h)과 캐파(66h)는 두 기준에서 같으므로 **가동률 비교는 그대로 유효하다.** 평균 동시 진행만 기준을 맞춰 다시 적은 값이다.

**같은 티켓의 작업 시간이 측정 방식에 따라 두 배 차이난다**
HDIT-2836의 SP 산정 문단은 상태 이력을 09~19시로 환산해 HDIT-2545를 약 5.0h, HDIT-2547을 약 5.6h, HDIT-2677을 약 6.1h로 적었다. 같은 티켓이 이 회고의 집계에서는 각각 2.5h · 1.3h · 1.2h다. 업무 로그를 기준으로 삼고 동시 진행 구간을 티켓 수로 나눈 값이라 그렇다. 두 값이 모두 Jira 안에 있고 어느 쪽을 근거로 삼았는지는 적혀 있지 않다. **SP 산정이 이 값을 근거로 삼으므로 다음 스프린트에서 어느 기준을 쓸지 정해야 한다.**

**추정이 실적을 계속 밑돈다**
HDIT-2545는 SP 0.29(2.0h 상당)에 실제 약 5.0h, HDIT-2547은 0.36(2.5h)에 약 5.6h, HDIT-2677은 유사 실적 티켓 두 건을 근거로 잡았는데도 2.4배가 났다. 후속 HDIT-2836·2838은 이 실적을 반영해 시간당 0.06 SP 비율로 산정 방식을 바꿨다. 계획 SP 합이 캐파의 1.33배인 것은 지난 스프린트 3.7배에서 크게 내려온 값이라, 티켓 단위 추정과 스프린트 총량은 반대 방향으로 움직이고 있다.

**환경별 부분 revert를 브랜치 하나에 넣고 격리를 가정했다**
HDIT-2305는 배포 범위에서 빠져 stage에서만 되돌렸는데(#2293), 그때 계산한 것은 `qa → stage` 방향뿐이었다. 실제로는 반대 방향인 `stage → main → develop` 동기화를 타고 revert가 develop으로 역류해 필수 입력이 되살아났고, 하루 뒤 복원 PR(#2305)을 다시 올렸다. 기능 코드는 두 번 다 옳았고 틀린 것은 브랜치 간 전파 방향에 대한 가정이다. 이 티켓 하나에 4시간 23분이 들어갔다 — 티켓이 다음 스프린트(26_3_#6) 배정이라 위 4절 집계에는 들어 있지 않고, PR 3건만 이번 기간에 머지됐다. 제외 사유 자체는 세 PR과 티켓 어디에도 적혀 있지 않다.

**같은 결함 클래스를 사흘 간격으로 두 번 잡았다**
`value` 참조 비교 때문에 확인 전 선택이 날아가는 버그를 #125의 2차 리뷰 지적으로 DateRangeInput에서 잡았는데, 사흘 뒤 DateTimeInput에 같은 것이 남아 있어 #129에서 다시 잡았다. PR 본문에 「#125 2차 지적과 같은 클래스」라고 적혀 있다. 한 번 찾은 결함 클래스를 형제 컴포넌트로 넓혀 훑지 않았다.

**기록이 작업을 따라오지 못한 자리가 남았다**
HDIT-1517은 계획 SP 2.0으로 이번 스프린트 최대인데 실적이 0.0h다. 작업은 지난 스프린트에 했고(PR #2171, 08-27 머지) 티켓만 이번 스프린트에 배정돼, 두 회고 어디에서도 시간이 잡히지 않았다. **스프린트 종료 시점에 연결이 끊긴 채로 남았다**
hd-ds 1.8.12가 나왔지만 소비 앱 반영 PR(#2307)이 열린 상태이고, HDIT-2836·2838은 리뷰중이다. 리뷰봇 전환은 티켓 완료(09-04 17:40)와 실제 동작 개시(09-07) 사이 3일 동안 PR 4건이 봇 리뷰 없이 머지됐다.
