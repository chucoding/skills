# 1. 요약

## **01. 인쇄 서비스 세 갈래를 실제로 만들어 숫자로 갈랐다**

설계 단계에서 세 갈래로 갈린 인쇄 서비스 인입 방식을 POC로 직접 만들어 비교했다. 공통 조판 모듈(HDIT-3099)을 먼저 빼서 갈래 2·3이 그 위에서 갈라지게 하고, 갈래 1 대 2는 조판 위치 하나만 다른 단일 변수 실험으로 묶었다. 기존 AIReport와 같은 조건에서 재니 4,000건 기준 AIReport 5,644~7,190ms 대 POC 1,771~4,664ms로 1.5배에서 4.1배, 중앙값 약 2배 빨랐다. CPU 4배 스로틀에서는 민원일반 4,000건이 브라우저 조판 18,086ms, 서버 조판 1,509ms였다.

## **02. 그리드 단독 편집 화면을 공통 변경 추적 방식으로 옮겼다**

회사선임관리는 그리드 행 전체를 폼 배열로 들고 원본과 비교해 변경 행을 화면에서 직접 고르고 있었고, 같은 구조가 단지선임관리로 복제되려 했다. 공통 `Grid`의 `__changes`와 `SaveButton` 경로로 옮기면서 +1,230/−1,659로 코드가 줄었다. 그 과정에서 등록 API가 새 ID를 돌려주지 않아 저장 순서가 등록 → 수정이면 재저장 시 중복 등록된다는 것을 찾아 순서를 뒤집었다.

## **03. 세대관리 상세에서 화면이 말하는 것과 저장 결과를 같은 판정에 묶었다**

세대관리 상세 결함 5건을 고쳤다. 필수 별표가 상시 뜨거나 아예 없고, 비운 값이 저장되지 않고, 화면에 없는 칸이 저장을 막고, 처리 직후 수정 중이던 입력이 사라졌다. 별표 표시와 저장 차단을 같은 함수(`isMemberRowFilled`·`hasBizRegistrationInput` 등)에서 파생시키고, 티켓에 적힌 원인 대신 실제 원인을 찾아 고쳤다 — QA 결함 HOM-2463은 「휴대폰번호 11자리 미만」이 아니라 화면에 없는 사업장 전화번호의 11자리 초과 이관 값이었다.

## **04. 그리드 교체 없이 엑셀 붙여넣기를 훅 하나로 붙였다**

AUIGrid 전면 개편 검토에서 남은 미충족 요구가 붙여넣기 하나뿐이라, Enterprise 구매나 그리드 교체 대신 공통 `Grid`에 훅으로 붙일 수 있는지 POC로 확인했다. 셀 범위 선택, 복사·잘라내기·붙여넣기, 실행 취소를 `useGridClipboard` 하나로 구현했고, 1,000행 붙여넣기 뒤 이력 20단계를 채워도 이력 몫은 전체 메모리 증가분의 14%였다.

## Challenge 01 : 문서로 안 갈리던 인쇄 방식을 세 갈래로 만들어 숫자로 갈랐다

`인쇄 서비스 · 성능 측정 · 배포`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-3070 (묶음) + 3099 · 3073 · 2996 · 3368 · 2998 · 3367 · 3428 |
| 실적 | 하위 7건 합 10.7h + 묶음 HDIT-3070 8.7h (업무 로그 기준 — 5절 참고) |
| PR | hd-cloud-print 6건 · 최대 #6 +1,290/−172 · 22파일, #5 +1,157/−368 · 40파일 |
| 산출 | Notion 「부하테스트 결과」 · 위키 hd-cloud-wiki#252 · #257 · Amplify 배포본 |

**상황**
HDIT-2767 설계에서 인쇄 서비스 인입 방식이 세 갈래(브라우저 조판, 서버 조판 한 방, 서버 조판 세그먼트)로 갈렸는데 문서만으로는 우열이 갈리지 않았다. 설계가 SSR을 고른 1순위 근거가 저사양 대응인데 그 수치가 비어 있었고, 기존 리포팅 도구 AIReport와 같은 조건에서 비교한 값도 없어 개선 폭을 숫자로 말할 수 없었다.

**어려웠던 지점**

1. **두 사람이 갈래를 나눠 가지면 같은 조판기를 두 번 만들고 출력물이 갈라진다.** 그래서 공통 기반을 HDIT-3099로 먼저 빼 3073·3074를 막는(blocks) 구조로 짰다. 인쇄 CSS도 클라이언트 컴포넌트 `import`에 묶여 있어 서버가 낸 HTML은 사본을 링크할 수밖에 없었는데, 사본을 두면 한쪽만 고쳤을 때 행 높이가 갈려 같은 데이터에서 페이지 수가 달라진다. `public/print-preview.css` 한 파일로 옮기고 Tailwind preflight 기준선까지 앞머리에 넣어야 비교가 조판 차이를 재게 됐다.
2. **분할 결과가 표본마다 반대 방향으로 어긋났다.** 공통 기반 직후 5표본 중 2개는 페이지별 행 수까지 일치했지만, 인사기본정보·일별접수는 서버가 페이지당 1행 더, 민원일반은 1행 덜 넣었다. 표본별 상수로 덮으면 맞출 수는 있지만 무엇을 잰 값인지 알 수 없게 된다. 원인이 행 높이라는 전역 값이라는 것을 확인하고 세 치수를 전역 보정하자 25칸 중 일치가 10칸에서 20칸으로, 인사 4,000건의 어긋남이 71쪽(최대 20행)에서 4쪽(최대 3행)으로 줄었다.
3. **로컬 계산으로 확정했다고 적은 상한이 배포본에서 틀렸다.** 갈래 2 한 방 상한을 로컬 렌더 바이트로 계산하고 「같은 입력이면 바이트가 같으니 배포본에 쏘지 않아도 확정된다」고 적었는데, 배포본 이분 탐색 실측이 계산보다 29건에서 140건 낮았다(민원일반 5,009건 3회 200 / 5,010건 3회 500). 배포 자체도 막혀 있었다 — 조판기 의존성이 들어오며 `output: 'standalone'` 산출물이 56.1MB로 Amplify SSR 한도 50MB의 112%였다.

**판단**
인입을 갈래 1과 공유하고 데모 SSR 버튼도 측정에 쓴 `/poc/server-once`를 그대로 가리키게 해 갈리는 축을 조판 위치 하나로 지켰다. 그 대가로 데모가 POC 네임스페이스에 의존하는 것을 받아들였다. 인증과 hub-api를 빼고 결정적 표본 생성기로 데이터를 공급해 Lambda 상태 공유 없이 재현되게 했는데, DB 왕복이 없어 갈래 3을 과대평가할 수 있다는 점을 티켓에 명시했다. 인사 표본의 남은 어긋남은 치수가 아니라 모델의 한계라 고치지 않고 근거만 남겼다. `standalone`은 끄고(19.4MB, 한도의 39%) 컨테이너로 옮길 때 되살리는 쪽을 택했고, 켠 상태 빌드의 부팅과 `/health` 200은 확인해 두었다. 계산값은 지우지 않고 `calculatedRows`로 남겨 실측과의 차이가 화면에서 보이게 했다.

**남은 것**
조판 모듈(`print-layout`·`print-server`)과 측정값 모듈(`server-once.measured.ts`·`metrics-fit.measured.ts`)이 저장소에 남아 다음 측정이 같은 표에 한 줄을 더하는 구조가 됐다. 「`next dev`로 잰 값은 쓰지 않는다」, 「배포 한도는 배포본에 쏴서 확정한다」는 측정 규칙도 함께 남았다. 보정은 macOS 실측에만 맞춰져 있어 Windows Chrome 재측정이 남아 있다.

## Challenge 02 : 화면마다 따로 짠 그리드 저장을 공통 경로에 올렸다

`그리드 · 리팩토링`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-3792 (개발완료) |
| 실적 | 1.0h |
| PR | #2391 · +1,230/−1,659 · 12파일 |
| 산출 | 단지선임관리(#2375)와 같은 저장 경로 |

**상황**
회사선임관리는 그리드 행 전체를 RHF 배열(`useGridField`, `readOnlyEdit`)로 들고, 원본(`appliedGridRowsRef`)과 비교해 변경 행을 화면에서 직접 고르고 있었다. 같은 구조가 단지선임관리로 복제되려 하고 있었다.

**어려웠던 지점**

1. **저장 순서가 API 계약과 맞지 않았다.** 등록 API가 새 ID를 돌려주지 않아, 등록 → 수정 순서에서 등록 성공 뒤 수정이 실패하면 다시 저장할 때 같은 행이 또 등록된다. API 계약은 그대로 두고 순서만 수정 → 등록으로 뒤집었다.
2. **전용 셀 에디터가 공통 기본 편집과 맞지 않았다.** 전용 선택 에디터는 `onValueChange`를 알리지 않아 기본 편집으로 옮기면 고른 값이 시작 값으로 되돌아간다(e885418e1과 같은 문제). 에디터를 지우고 공통 `selectOneCellEditor`로 바꿨다.
3. **재조회가 미저장 편집을 덮었다.** 저장이나 삭제 뒤 목록을 다시 그리면 다른 행의 미저장 편집이 사라진다. 삭제는 행만 지우고, 재조회 결과는 변경이 없을 때만 그리드에 반영하며 `syncedAppointmentsRef`로 저장 직후 이전 목록으로 되돌아가지 않게 막았다. 리뷰 봇이 `onDirtyChange(true)`가 값 비교보다 먼저 호출된다고 지적했지만, AG Grid 33.3.2 `setValueUsingField`가 같은 값이면 이벤트를 내지 않는다는 근거로 오탐 반박했다.

**판단**
화면 고유의 변경 판정(`getChangedCompanyAppointmentRows`)과 전용 에디터를 버리고 세대관리와 같은 `__changes` + `SaveButton` 경로를 택했다. 저장 버튼 모양이 공통 `SaveButton`으로 바뀌는 것은 단지선임관리와 맞춘다는 이유로 받아들였다. 수정과 등록을 한 번에 저장할 때의 실제 요청 순서는 E2E로 확인하지 못하고 vitest로만 확인한 채 남겼다.

**남은 것**
그리드 단독 편집 화면 두 곳(회사·단지선임관리)이 같은 저장 경로를 쓴다. 원래 값으로 돌아온 칸은 `__changes`에서 지워 변경 없음으로 되돌린다는 규칙이 `patchRow`에 들어갔다.

## Challenge 03 : 화면이 말하는 필수와 저장이 막는 필수를 같은 함수에 묶었다

`폼 검증 · QA 결함`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-2923 · 3062 · 3076 (QA HOM-2463) · 3083 (QA HOM-2467) · 3582 |
| 실적 | 5.4h (5건 합, 그중 2923 · 3083은 0.0h — 5절 참고) |
| PR | #2308 +838/−201 · 17파일, #2320 · #2321 · #2323 · #2381 |
| 산출 | `model/use-required.ts` · `model/use-revalidate.ts` |

**상황**
세대관리 상세의 조건부 필수 항목에 별표가 없어 어떤 칸이 필수가 됐는지 알 수 없었고, 조건이 풀려도 오류 칩이 반응하지 않았다. 세대원·차량 그리드는 행을 추가하자마자 오류로 칠해지거나 헤더 별표가 상시 떠 있었다. 사업장 정보를 비우고 저장하면 재조회에서 이전 값이 돌아왔고, 특정 세대는 무엇을 고쳐도 `저장 실패` 얼럿만 떴다. 소유주 변동처리나 세대주 전출을 하면 처리와 무관한 입력까지 확인 없이 사라졌다.

**어려웠던 지점**

1. **표시와 저장 차단을 따로 판정하면 결함이 형태만 바꿔 남는다.** 별표 표시를 저장 차단과 같은 함수로 묶었는데, 그리드 헤더 별표는 AG Grid가 `refreshHeader()` 없이 `headerClass` 콜백을 다시 평가하지 않고 공용 `Grid`는 `refreshCells`만 호출해 동적으로 바뀌지 않았다. 공용 `Grid`를 건드리지 않으려고 별표만 뗀 컬럼 정의를 파생해 교체했다.
2. **필드별 의존 선언과 전체 재검증 사이에서 갈렸다.** 세대주 성명의 필수 조건이 세대주·세대원·차량에 걸쳐 있고 그리드 셀은 `Controller`가 아니라 `deps`를 빠짐없이 유지하기 어려웠다. 저장 시도 이후 값이 바뀔 때마다 폼 전체를 `trigger()`로 재검증하되, 그 과정에서 지워지는 서버 오류 두 종류는 다시 붙였다.
3. **티켓에 적힌 원인과 실제 원인이 달랐다.** HOM-2463은 「휴대폰번호 11자리 미만」으로 올라왔지만 실제로는 아파트 단지에서 화면에 그리지도 않는 세대주 사업장 전화번호에 11자리를 넘는 이관 값이 남아 서버가 400을 냈다. 사용자는 그 값을 볼 수도 고칠 수도 없었다. HDIT-2923 티켓의 예시 「상호명 입력 시 사업자 번호 필수」도 HDIT-2305 이후 반대가 된 규칙이었다.

**판단**
아파트 단지는 사업장 섹션을 그리지 않으므로 저장 요청에서도 `bizRegistration`을 빼 서버의 기존 값을 보존했다 — 이관된 초과 값을 사용자가 고칠 수단이 생긴 것은 아니라는 점을 알고 택했고, `BizRegistrationForm`의 `.slice(0, 11)`이 초과 값을 조용히 자르는 문제는 후속 후보로 남겼다. 검증 실패 안내는 토스트를 걷고 오류 항목 바 칩과 포커스로만 하도록 줄였다. 처리 후 입력 유실은 draft를 통째로 지우지 않고 처리한 영역만 서버 값으로 바꾸는 쪽을 택했는데, 처리 전 서버 값을 쿼리가 아니라 `formState.defaultValues`에서 읽어야 했다 — effect가 도는 시점에 캐시는 이미 처리 후 응답이다. 상호명 한 칸을 비우는 경로는 서버가 사업장 수정을 건너뛰는 것으로 보여 HDIT-3075로 넘겼다.

**남은 것**
필수 표시는 저장 차단 판정에서 파생한다는 규칙이 `use-required.ts`에 모였다. 세대원·차량 그리드는 「값이 하나라도 있는 행만 필수」라는 직원 등록 화면과 같은 기준을 쓴다.

## Challenge 04 : Enterprise를 사지 않고 엑셀 붙여넣기를 훅 하나로 붙였다

`그리드 · POC`

| 항목 | 값 |
| --- | --- |
| 티켓 | HDIT-3165 (개발완료) |
| 실적 | 1.4h |
| PR | #2337 · +2,921/−156 · 10파일 (#2333 대체) |
| 산출 | `useGridClipboard` · `shared/lib/grid/clipboard.ts` · 스토리북 `Grid > Clipboard` |

**상황**
AG Grid Community에는 클립보드 모듈과 셀 범위 선택이 없어 엑셀에서 복사한 값을 그리드에 바로 붙여넣을 수 없었다. AUIGrid 전면 개편 타당성 검토에서 남은 미충족 요구가 이것 하나였다.

**어려웠던 지점**

1. **실행 취소를 AG Grid에 맡기면 붙여넣기만 되돌아가지 않는다.** `undoRedoCellEditing`을 켜서 재 보니 훅이 `onRowsChange`로 새 배열을 돌려주는 붙여넣기는 AG Grid 입장에서 편집이 아니라 새 `rowData`라 기록되지 않았다. 두 이력을 섞으면 Ctrl+Z 한 번에 되는 것과 안 되는 것이 갈린다. 훅이 이력을 쥐는 대신 메모리를 실측했다 — 기준선 32.7MB → 1,000행 붙여넣기 127.4MB → 이력 20단계 142.4MB.
2. **공통 `Grid`가 끼워 넣는 행과 병합 셀이 붙여넣기 계산을 깨뜨렸다.** 표시용 소계·합계 행은 호출부 배열에 없는데 훅이 이를 「행이 모자라다」로 오해해 맨 아래에 새 행을 만들었다. 병합 셀은 구간 첫 행만 바뀌어 화면은 합쳐진 채 세대 하나에 값이 둘인 상태를 조용히 만들었다. 표시 행 순번과 값 순번을 분리하고 병합 컬럼은 편집 불가로 잠갔다.
3. **리뷰 지적을 좁게 고쳐 같은 지적이 라운드마다 돌아왔다.** 선택 범위가 방향키로만 갱신된다는 지적을 Enter·Tab에만 고치자 Home·End로 다시 돌아왔고, 이어 Tab 자동 반복에서 플래그가 먼저 소비되는 경우로 또 돌아왔다. 먼저 연 #2333은 푸시가 잦아 리뷰 봇 라운드가 10번 겹쳐 대화를 읽을 수 없게 되자 커밋 하나로 정리해 #2337로 다시 열었다.

**판단**
Enterprise 도입과 그리드 계층 교체는 요구가 붙여넣기 하나뿐이라 배제했다. 시연과 실제 화면이 어긋나지 않도록 공통 `Grid` 기본값(`rowSelection`·`singleClickEdit` 등) 덮어쓰기를 모두 걷어냈고, 그 대가로 `singleClickEdit: true`에서 Shift+방향키 범위 확장이 막히는 제약을 리뷰 요청으로 열어 두었다. 붙여넣기 상한 1,000행은 메모리가 아니라 메인 스레드가 약 1초 블록되는 지점으로 정했다. 편집 불가 컬럼은 복사에는 넣고 붙여넣기만 건너뛰어, 열 위치를 지켜 엑셀 왕복이 어긋나지 않게 했다.

**남은 것**
TSV 직렬화와 파싱(엑셀의 `\r\n`, 수식 접두 `=`·`+`·`@`·`-` 이스케이프)이 `shared/lib/grid/clipboard.ts`로 분리됐다. 두 번째 사용처를 위해 라인 설정 그리드 삭제 버튼 컬럼의 `field`를 비워 범위 선택에서 빠지게 한 HDIT-3315(#2350)가 이미 뒤따랐다.
