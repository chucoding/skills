# 회고 문서 템플릿

`<>` 안은 채울 자리다. 절 번호와 순서는 바꾸지 않는다.

## 문장부호 — 전역 문서 지침보다 이 파일이 우선

이 템플릿은 **사용자가 지정한 형식**이다. 전역 `문서 작성 지침`은 산문에서 줄표(`—`)와 가운뎃점(`·`)을 새로 쓰지 말라고 하지만, 같은 지침의 첫 줄이 `사용자가 지정한 문장부호와 형식을 가장 우선한다`이다. 아래 세 가지는 이 문서에서 그대로 쓴다.

| 기호 | 쓰는 자리 |
|------|-----------|
| `—` | 주장 뒤에 근거나 부연을 붙일 때. `자원 경합을 3개 축 — 공유 매핑 파일·티켓 상태·저장소 파일 — 으로 판정했다` |
| `·` | 나열이 짧고 같은 층위일 때. `Notion·Figma·Swagger·개발 페이지` |
| `「」` | 남의 말이나 보고 문구를 그대로 인용할 때. `「후보 없음」으로 보고했다` |

다음 세션이 이걸 `쉼표로 고쳐야 할 것`으로 오해하지 않도록, 회고 문서 안에도 이 사실을 적지 않는다. 형식 자체가 정본이다.

---

# 머리말 표

| 기간 | `<YYYY-MM-DD> ~ <YYYY-MM-DD>` |
| --- | --- |
| 산출물 | `<Jira 티켓 N건, Github PR 본문 N건, 설계 문서 N건 작성>` |

산출물의 티켓 수는 `티켓.전체`, PR 수는 `PR.저장소별` 중 본문에서 쓰기로 한 범위, 설계 문서는 `티켓.문서_티켓_후보`를 사람이 확인한 수다.

기간은 팩의 `기간` 문자열을 그대로 쓴다. 종료가 자정인 스프린트의 전날 보정이 이미 들어가 있고, **PR 집계도 같은 종료일로 했다**. `sprint.end` 를 직접 잘라 쓰면 둘이 어긋나 경계일 PR 이 두 스프린트에 겹쳐 들어간다.

# 1. 요약

챌린지 수만큼 `## 01.` ~ `## 06.` 을 만든다. 각 항목은 **제목 한 줄 + 3~4문장**이다.

- 제목은 그 작업이 **무엇을 바꿨는지**를 말한다. `AI 에이전트 워크플로 성능·신뢰성 재설계`처럼 명사구로 끝낸다.
- 본문은 숫자를 앞세운다. `280초 = 도구 65초 + 모델 추론 215초`처럼 근거가 되는 실측을 그대로 쓴다.
- 2절 상세의 요약이 아니라 **독립해서 읽히는 글**이다. 이 절만 읽고도 무엇을 했는지 알 수 있어야 한다.

# 2. 첼린지 상세

제목의 `첼린지`는 사용자가 쓰던 표기다. **고치지 않는다** — 지난 회고와 제목이 달라지면 문서끼리 대조가 끊긴다. 본문 안에서는 `챌린지`로 쓴다.

챌린지마다 아래 네 블록을 **이 순서로 고정**한다. 블록을 빼거나 이름을 바꾸지 않는다.

```
## Challenge 0N : <결과를 말하는 서술형 제목>

`<분야 태그 · 분야 태그>`

| 항목 | 값 |
| --- | --- |
| 티켓 | <HDIT-1601 (배포완료)> |
| 실적 | <7.0h> |
| PR | <#2167 · +352/−102 · 11파일> |
| 산출 | <설계 문서 + 스킬 개편> |

**상황**
<변경 전에 무엇이 문제였는지. 현재 시제로 한두 문장.>

**어려웠던 지점**

1. **<판단이 갈렸던 지점을 한 문장으로>** <그 근거와 실제로 확인한 값.>
2. **<두 번째 지점>** <근거.>
3. **<세 번째 지점>** <근거.>

**판단**
<무엇을 택했고 무엇을 포기했는지. 포기한 쪽을 반드시 적는다.>

**남은 것**
<다음에 같은 상황에서 다시 안 해도 되는 것 한 문장.>
```

표의 항목은 그 챌린지에 실제로 있는 것만 넣는다. 티켓이 없으면 `성격 | 티켓 없는 자체 작업`처럼 쓴다.

블록별 규칙:

- **제목** — `에이전트 세션의 직렬 구간을 실측으로 잘라내다`처럼 서술형으로 끝낸다. 티켓 제목을 그대로 옮기지 않는다.
- **상황** — 증상을 적는다. 원인은 여기 쓰지 않는다. 원인을 찾아가는 과정이 다음 블록이기 때문이다.
- **어려웠던 지점** — 번호 목록 2~3개. 각 항목은 **볼드 주장 한 문장 + 그 뒤에 근거**다. `어려웠다`로 끝나는 문장을 쓰지 않는다. 무엇과 무엇 사이에서 갈렸는지를 적는다.
- **판단** — 트레이드오프를 남긴다. `탭 순서 보장은 병렬과 양립하지 않으므로 순서 미보장을 명시적으로 수용했다`처럼, 얻은 것과 포기한 것이 같은 문장에 있어야 한다.
- **남은 것** — 자산이나 습관 한 줄. `잘했다`는 감상은 쓰지 않는다.

# 3. 그 외 작업

챌린지가 못 된 건을 표로 적는다. 머리에 이 묶음의 **공통점 한 줄**을 단다. 예: `공통점은 증상을 고치지 않고 판단 기준이나 소유 계층을 옮겼다는 점이다.`

| 티켓 | 내용 | PR |
| --- | --- | --- |
| `<HDIT-2364>` | **`<한 줄 요약을 볼드로>`** — `<변경 전 동작과 바꾼 축>` | `<#2211>` |

내용 칸은 두 문장 안에 끝낸다. 볼드 요약은 `A를 B로 교체`, `A를 entities로 승격`처럼 **무엇을 무엇으로 옮겼는지** 형태가 좋다.

# 4. 처리량과 남긴 자산

| 지표 | 값 |
| --- | --- |
| QA 결함 처리 | `<N건 · N.Nh>` |
| 머지된 PR | `<N건 (릴리스 N건 포함)>` |
| 실가동 / 캐파 | `<57.3h / 66h → 87%>` |
| 평균 동시 진행 티켓 | `<2.47건>` |

전부 팩에서 가져온다. 출처는 `metrics.md` 참고. 손으로 센 숫자를 넣지 않는다.

**재사용 자산**

| 자산 | 위치·효과 |
| --- | --- |
| `<범용 재시도 유틸>` | `<shared/lib · 이후 모든 업로드 경로가 공유>` |

이 절은 PR에서 실제로 추출·이동한 것만 적는다. `앞으로 쓸 수 있다`는 전망은 자산이 아니다. 두 번째 사용처가 있으면 그것을 적는다.

# 5. 잘 안 된 지점

**이 절을 비우지 않는다.** 팩이 재료를 직접 준다.

| 팩의 값 | 쓸 문장 |
|---------|---------|
| `reopen_있음` | 한 번에 맞추지 못한 건. 티켓 키와 되돌아온 횟수 |
| `기록_구멍.작업시간_0` | 상태를 거치지 않아 실적이 0으로 남은 건. 전체 대비 비율 |
| `기록_구멍.장기_열림_의심` | 방치된 체류가 작업시간으로 잡힌 건 |
| `계획.SP_환산h` vs `부하.캐파h` | 계획 추정이 실적의 몇 배였는지 |
| `PR.스프린트_티켓에_없는_PR` | 티켓 밖에서 한 일. 지표에 안 잡힌다는 사실까지 |

각 문단은 **굵은 제목 한 줄 + 사실 두세 문장**이다. 원인을 알면 적고, 모르면 `다음 스프린트에서 정해야 한다`로 남긴다. 변명과 다짐은 쓰지 않는다.

# 부록. 티켓별 실적

팩의 `부록_티켓별_실적`을 표로 그대로 옮긴다. 실적이 0으로 남은 건도 빼지 않는다. 5절의 `기록이 작업을 따라오지 못했다`와 이 표가 서로 대조되어야 한다.

| 티켓 | 제목 | 상태 | 실적 | SP | 출처 |
| --- | --- | --- | --- | --- | --- |

`출처`는 `changelog`(상태 이력으로 잰 값)인지 `worklog`(사람이 적은 값)인지다. 전역 지침의 SP 산정이 이 표를 근거로 삼으므로 생략하지 않는다.
