# 회고 문서 템플릿

`<>` 안은 채울 자리다. 절 번호와 순서는 바꾸지 않는다.

이 문서는 연말 실적 기입, 연봉협상, 이력서에 쓸 개인 기록이다. 팀에 공유하는 문서가 아니다. 그래서 정량 성과와 실적 지표를 앞에 두고, 한 일은 빠짐없이 뒤에 남긴다.

2026-10-30에 형식을 바꿨다. 그 전 회고는 `1. 요약`과 `2. 첼린지 상세`에 작업 3~6건의 어려움과 판단을 서술했고, 그 외 작업은 `3. 그 외 작업`, 지표는 4절, 잘 안 된 지점은 5절에 있다. 예전 회고를 지금 형식으로 고치지 않는다. 그때 쓴 그대로가 기록이다.

## 문장부호 — 전역 문서 지침보다 이 파일이 우선

이 템플릿은 **사용자가 지정한 형식**이다. 전역 `문서 작성 지침`은 산문에서 줄표(`—`)와 가운뎃점(`·`)을 새로 쓰지 말라고 하지만, 같은 지침의 첫 줄이 `사용자가 지정한 문장부호와 형식을 가장 우선한다`이다. 아래 세 가지는 이 문서에서 그대로 쓴다.

| 기호 | 쓰는 자리 |
|------|-----------|
| `—` | 주장 뒤에 근거나 부연을 붙일 때. `자원 경합을 3개 축 — 공유 매핑 파일·티켓 상태·저장소 파일 — 으로 판정했다` |
| `·` | 나열이 짧고 같은 층위일 때. `Notion·Figma·Swagger·개발 페이지` |
| `「」` | 남의 말이나 보고 문구를 그대로 인용할 때. `「후보 없음」으로 보고했다` |

다음 세션이 이걸 `쉼표로 고쳐야 할 것`으로 오해하지 않도록, 회고 문서 안에도 이 사실을 적지 않는다. 형식 자체가 정본이다.

---

`chucoding:job-match`의 이력서 기술 순위와 기업 추천은 이 문서에 쓰지 않는다. 그 스킬의 채용매칭 파일에만 둔다. 다만 1절 핵심 성과의 기술 태그는 job-match의 `작업_키워드`와 같은 표기로 맞춰, 이력서를 쓸 때 기술 순위와 성과 문장을 바로 이을 수 있게 한다.

---

# 머리말 표

| 기간 | `<YYYY-MM-DD> ~ <YYYY-MM-DD>` |
| --- | --- |
| 산출물 | `<Jira 티켓 N건, Github PR 본문 N건, 설계 문서 N건 작성>` |
| 완료 | `<티켓 N건 · N.NN SP · PR N건 머지>` |

산출물의 티켓 수는 `티켓.전체`, PR 수는 `PR.저장소별` 중 본문에서 쓰기로 한 범위, 설계 문서는 `티켓.문서_티켓_후보`를 사람이 확인한 수다. 완료 줄의 값은 2절 실적 지표의 이번 값과 같다.

기간은 팩의 `기간` 문자열을 그대로 쓴다. 다음 회차와 겹치지 않게 맞춘 마지막 날(`sprint.last_day`)이 이미 들어가 있고, **PR 집계도 같은 종료일로 했다**. `sprint.end` 를 직접 잘라 쓰면 둘이 어긋나 경계일 PR 이 두 스프린트에 겹쳐 들어간다.

# 1. 핵심 성과

정량 결과가 있는 작업을 **3~6건** 골라 이력서와 연봉협상에 그대로 옮길 수 있는 문장으로 쓴다. 사용자에게 고르게 하지 않는다. 근거에 정량 결과가 있는 만큼만 쓰고 수를 맞추려고 채우지 않는다.

## 0N. <결과를 말하는 한 줄 제목>

`<기술 태그 · 기술 태그>`

**<행동>해서 <정량 결과>.** <범위나 조건 한 문장.>

| 지표 | 전 | 후 | 근거 |
| --- | --- | --- | --- |
| `<그리드 초기 렌더링>` | `<1,840ms>` | `<420ms>` | `<#2487 본문 측정>` |
| `<적용 범위>` | | `<화면 12개 · 11파일>` | `<#2487, HDIT-4031>` |

- **고르는 기준**은 앞에서부터 본다.
  1. 전후 측정값이 근거에 있는 작업. 성능 수치, 오류나 결함 건수, 걸리던 시간처럼 바뀐 크기를 숫자로 보일 수 있는 것
  2. 영향 범위를 숫자로 보일 수 있는 작업. 적용한 화면이나 저장소 수, 공통 모듈을 가져다 쓰는 곳의 수, 자동화로 없앤 수작업 단계 수
  3. 위가 같으면 실적 시간이 큰 순
- **성과 문장**은 `<무엇을> <어떻게> 바꿔 <결과 수치>`의 한 문장이다. 이력서 경력 항목에 그대로 붙일 수 있게 주어는 빼고 동사로 끝낸다. 예: `그리드 행 가상화로 초기 렌더링을 1,840ms에서 420ms로 줄였다.`
- **숫자는 근거에 적힌 값만 쓴다.** PR 본문, 티켓, 커밋에 측정값이 없으면 `약`, `수 배`처럼 추정하지 않는다. 측정값이 없는 작업은 2번 기준(범위)으로만 쓰고, 범위도 숫자로 보일 수 없으면 1절에 올리지 않는다.
- 범위 숫자 중 파일 수와 증감은 PR 메타데이터(`prs[]`)에서, 화면이나 사용처 수는 PR 본문이나 코드 검색 결과에서 가져오고 근거 칸에 어디서 셌는지 적는다.
- **기술 태그**는 `chucoding:job-match`의 `작업_키워드` 표기를 따른다. 예: `React.js`가 아니라 `React`.

# 2. 실적 지표

| 지표 | 이번 | 직전 스프린트 | 최근 3회 평균 |
| --- | --- | --- | --- |
| 완료 티켓 | `<N건>` | `<N건>` | `<N.N건>` |
| 완료 SP | `<N.NN>` | `<N.NN>` | `<N.NN>` |
| 머지된 PR | `<N건 (릴리스 N건 포함)>` | | |
| QA 결함 처리 | `<N건 · N.Nh>` | | |
| 실가동 / 캐파 | `<57.3h / 66h → 87%>` | | |
| 평균 동시 진행 티켓 | `<2.47건>` | | |

- 이번 값은 전부 팩에서 가져온다. 출처는 `metrics.md` 참고. 손으로 센 숫자를 넣지 않는다.
- 직전과 최근 3회 값은 `docs/`의 이전 회고 문서 지표 표에서 그대로 옮긴다. 예전 형식 회고는 머리말 표와 4절에 있다. 그 문서에 없는 항목은 `-`로 두고 재계산하지 않는다. 재수집하면 `metrics.md`의 `언제 재는가` 함정 때문에 값이 달라진다.
- 표 아래에 직전 대비 늘거나 준 항목을 한 문장으로 적는다. 원인을 해석하지 않고 숫자만 말한다.

## 남긴 자산

| 자산 | 위치·효과 |
| --- | --- |
| `<범용 재시도 유틸>` | `<shared/lib · 이후 모든 업로드 경로가 공유>` |

재사용 자산도 연봉협상에서 쓰는 성과다. PR에서 실제로 추출·이동한 것만 적는다. `앞으로 쓸 수 있다`는 전망은 자산이 아니다. 두 번째 사용처가 있으면 그것을 적는다.

# 3. 작업 기록

스프린트 티켓 전부와 티켓 밖 PR을 묶음별 표로 적는다. 고르거나 빼지 않는다. 회의, 휴가처럼 산출물이 없는 티켓만 부록에 남기고 여기서는 뺀다.

묶음마다 `## <묶음 이름>` 제목을 달고, 머리에 이 묶음의 **공통점 한 줄**을 단다. 예: `공통점은 증상을 고치지 않고 판단 기준이나 소유 계층을 옮겼다는 점이다.`

| 티켓 | 내용 | PR | 실적 |
| --- | --- | --- | --- |
| `<HDIT-2364>` | **`<한 줄 요약을 볼드로>`** — `<변경 전 동작과 바꾼 축>` | `<#2211 · +352/−102 · 11파일>` | `<7.0h>` |

- 내용 칸은 두 문장 안에 끝낸다. 볼드 요약은 `A를 B로 교체`, `A를 entities로 승격`처럼 **무엇을 무엇으로 옮겼는지** 형태가 좋다. 1절에 오르지 않은 작업도 연말에 이 칸을 실적 문장으로 옮겨 쓴다.
- 근거를 찾지 못하면 티켓 제목만 옮기고 `근거 부족`이라고 적는다.
- 티켓이 없는 PR은 티켓 칸에 `티켓 없음`이라고 적는다.
- 실적과 PR 규모의 출처는 `metrics.md`의 `값 대응표`를 따른다.

# 4. 잘 안 된 지점

**이 절을 비우지 않는다.** 팩이 재료를 직접 준다.

| 팩의 값 | 쓸 문장 |
|---------|---------|
| `reopen_있음` | 한 번에 맞추지 못한 건. 티켓 키와 되돌아온 횟수 |
| `기록_구멍.작업시간_0` | 이번 구간 실적이 0으로 남은 건과 전체 대비 비율. 상태를 거치지 않은 경우와 업무 로그가 스프린트 구간 밖에 찍힌 경우를 `results.json` 의 `work_in_sprint_biz_seconds` 로 갈라 적는다 |
| `기록_구멍.장기_열림_의심` | 그 티켓의 `work_source` 가 `changelog` 면 방치된 체류가 작업시간으로 잡힌 건이다. `worklog` 면 표시값은 업무 로그라 체류와 무관하므로 그렇게 쓰지 않는다 |
| `계획.SP_환산h` vs `부하.캐파h` | 계획이 캐파의 몇 배였는지 |
| `PR.스프린트_티켓에_없는_PR` | 티켓 밖에서 한 일. 릴리스·동기화 PR은 걸러 내고, 지표에 안 잡힌다는 사실까지 |
| `PR.조회_실패` 와 설정 밖 저장소 | 설정(`WORKTIME_GITHUB_REPO`)에 없는 저장소의 작업은 PR 집계에 들어오지 않는다. 작업 기록 근거로 그 저장소를 따로 조회했다면 그 사실을 적는다 |

각 문단은 **굵은 제목 한 줄 + 사실 두세 문장**이다. 원인을 알면 적고, 모르면 `다음 스프린트에서 정해야 한다`로 남긴다. 변명과 다짐은 쓰지 않는다.

# 부록. 티켓별 실적

팩의 `부록_티켓별_실적`을 표로 그대로 옮긴다. 실적이 0으로 남은 건도 빼지 않는다. 4절의 `기록이 작업을 따라오지 못했다`와 이 표가 서로 대조되어야 한다.

| 티켓 | 제목 | 상태 | 실적 | SP | 출처 |
| --- | --- | --- | --- | --- | --- |

`출처`는 `changelog`(상태 이력으로 잰 값)인지 `worklog`(Jira 업무 로그를 표시값으로 쓴 값)인지다. 폴러가 실적을 자동 기입하므로 `worklog` 는 사람이 손으로 적었다는 뜻이 아니다(`metrics.md` 의 `믿으면 안 되는 값`). 서술과 숫자를 대조하는 자리라 생략하지 않는다.

표 위에 스냅샷 파일명과 `work_source` 분포를 한 줄로 밝힌다. 이 표를 SP 산정의 근거로 쓰라고 적지 않는다 — SP 산정의 정본은 Jira 업무 로그이고 산정 절차는 `chucoding:jira` 의 `SP 산정` 을 따른다.
