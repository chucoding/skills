# 1. 소개

`[N년]`차 프론트엔드 엔지니어입니다. `[회사명]`에서 React와 TypeScript로 B2B 관리 SaaS를 만들면서, 화면 개발과 함께 여러 화면과 저장소가 같이 쓰는 기반을 맡아 왔습니다. 사내 디자인 시스템 패키지, 공용 그리드, PR CI 게이트, 코딩 에이전트가 따르는 저장소 규칙이 그 기반입니다.

일하는 방식은 하나로 요약됩니다. 화면마다 따로 막던 문제를 공용 계층으로 옮기고, 옮기기 전과 후를 숫자로 잽니다. 4,997행 그리드가 첫 행을 그리기까지 걸리던 38.7초를 0.10초로 줄인 일도, 그 뒤 110개 파일의 그리드를 한 가지 스크롤 구조로 통일한 일도 이 방식에서 나왔습니다.

# 2. 경력 기술

## 공용 그리드를 행 가상화 한 갈래로 통일

- 세대 4,997행 단지에서 API 응답 후 첫 행까지 38.7초, 메인 스레드 최장 멈춤 38.6초. 원인은 autoHeight 그리드가 모든 행을 DOM에 그리는 구조
- 페이지를 유일한 스크롤러로 두고 보이는 행만 그리도록 바꿔 첫 행 0.10초, 최장 멈춤 0.21초, DOM 행 5,067개에서 16개로 감소
- 페이지 스크롤과 그리드 내부 스크롤이 입력 경로(휠, 터치, 키보드)마다 기준이 갈리던 문제를 경로별 보정 규칙으로 정리해 키보드 이동 시 포커스 셀이 가려지는 횟수 0
- 이어서 호출부가 고르던 레이아웃 옵션을 공용 컴포넌트 타입에서 지워 넘기면 타입 오류가 나게 하고, 110개 파일의 그리드를 같은 스크롤 구조로 이관
- 측정 표(첫 행 시각, 최장 멈춤, DOM 행 수)를 같은 데이터와 같은 커밋 기준으로 PR에 남겨 다음 비교의 기준으로 사용

## 디자인 시스템에 레이아웃 폭을 차지하지 않는 스크롤바 추가

- 저해상도 윈도우 PC에서 네이티브 스크롤바가 사이드 네비와 본문 폭을 깎던 문제. CSS 스크롤바 속성은 모두 폭을 차지해 라이브러리(OverlayScrollbars) 도입을 결정
- 라이브러리 기본 구조는 자식을 새 viewport로 옮겨 React 자식과 AG Grid 내부 DOM을 깨뜨리므로, 기존 스크롤 요소를 그대로 viewport로 쓰는 훅을 따로 설계
- 휠 스크롤 중 막대가 흔들리는 원인을 브라우저 컴포지터 스크롤과 JS `transform` 보정의 한 프레임 차이로 진단하고, 스크롤되지 않는 부모에 붙여 보정을 없앰
- 빌드한 CSS에서 라이브러리 기본 변수가 테마를 덮는 문제가 개발 서버에서는 로드 순서가 반대라 드러나지 않던 것을 찾아, Storybook에서 빌드 순서를 재현한 뒤 측정
- 앱 셸, 그리드, 테이블, 사이드 네비에 적용했고 표 가로 스크롤바를 페이지네이션 위에 고정하는 두 번째 사용처가 같은 컴포넌트를 재사용

## PR CI 게이트와 리뷰 요청 체계 재설계

- PR CI가 설치와 빌드만 돌려 타입 오류, 테스트 실패, 브랜치와 커밋 규칙 위반이 리뷰 단계에서야 드러나던 상태. 부문 공통 게이트(typescript, conventions)와 commitlint를 연결
- 게이트 기본값이 이 저장소에서는 0개 파일을 검사하던 것(references만 있는 루트 tsconfig)과 감시 모드 테스트 스크립트를 찾아 명령을 직접 지정
- 게이트를 켜자 UTC 러너에서 날짜 매핑 테스트 6건이 실패. 테스트마다 기대값을 고치는 대신 테스트 환경 시간대를 고정했고, 이를 위해 vitest를 2에서 4로 올림
- 리뷰 요청을 변경 경로 기준(CODEOWNERS 58줄)으로 좁혔다가 요청이 오히려 늘어난 것을 확인하고, 작성자 소속 파트 기준으로 다시 설계
- 같은 게이트 구성을 다른 저장소(관리자 앱)로 이식

## 기술 부채 정리와 대규모 이관

- 그리드 레이아웃 옵션 제거로 110개 파일 이관 (위 항목)
- deprecated Select 컴포넌트 사용처 14개 파일을 새 컴포넌트로 이관하고, 디자인 시스템의 제네릭 제약을 실제 넘어가는 타입에 맞게 정리
- 한 도메인 슬라이스의 파일명 규칙을 정리해 63개 파일, 47건 rename

## 코딩 에이전트가 기여할 수 있는 개발 환경

- 다른 파트 인원과 코딩 에이전트가 같은 저장소를 쓰게 되면서, 반복해서 어긋나는 지점만 골라 저장소 가이드라인(AGENTS.md, 109줄)을 작성
- 티켓 착수 자동화의 대기 시간을 세션 타임스탬프로 실측해 280초 중 도구 실행 65초, 모델 추론 215초로 분해. 개별 호출이 아니라 105초 직렬 구간이 문제임을 찾아 서브에이전트 분리와 병렬 실행으로 재설계
- 자동화가 참고 자료 4종 중 3종을 탐색하지 않고 「후보 없음」으로 보고하던 것을 세션 로그 감사로 발견. 「찾았는데 없음」과 「찾지 않음」을 구분하는 절차 게이트를 추가

## 측정으로 설계 방향 결정

- 인쇄 서비스 인입 방식이 설계 단계에서 세 갈래로 갈리자, 공통 조판 모듈을 먼저 분리하고 갈래별 POC를 단일 변수 실험으로 만들어 비교
- 4,000건 기준 기존 방식 5,644~7,190ms 대 POC 1,771~4,664ms. CPU 4배 스로틀에서 브라우저 조판 18,086ms 대 서버 조판 1,509ms

# 3. 공고가 묻는 질문에 대한 답

포트폴리오 첫 장이나 이력서 상단 요약에 넣을 문단이다. 필요한 것만 골라 쓴다.

## 여러 팀이 쓰는 기반을 만들고 동료의 작업이 어떻게 달라졌나

PR CI 게이트를 붙이기 전에는 타입 오류와 테스트 실패를 리뷰어가 코드를 읽다가 발견했습니다. 게이트 이후에는 리뷰 요청 전에 PR 체크로 드러나고, 커밋 시점에도 같은 커밋 규칙이 돕니다. 게이트를 켜자마자 로컬에서는 통과하던 테스트 6건이 서버 시간대 차이로 실패한 것도 이 체계가 처음 잡아낸 결함이었습니다.

리뷰 요청은 한 번 실패했습니다. 변경 경로마다 담당 파트를 나누면 요청이 줄 거라 봤는데, 공통 경로를 건드리는 PR마다 담당자가 겹쳐 요청이 오히려 늘었습니다. 작성자 소속 파트 기준으로 바꾸면서 명단에 없는 신규 입사자와 봇의 PR에는 자동 요청이 가지 않는 대가가 생겼고, 이를 PR에 적어 리뷰어 합의를 받고 넘어갔습니다.

## AI를 어디에 쓰고, 어디서 틀렸는지 어떻게 알아챘나

티켓 착수 자동화가 참고 자료를 찾아 브라우저 탭을 열어 주는데, 어느 날 「후보 없음」이라는 보고가 의심스러워 세션 로그를 열어 봤습니다. 네 종류 중 세 종류는 검색 도구 호출이 0건이었습니다. 같은 검색어를 직접 넣으니 첫 결과가 바로 그 화면의 정책서였습니다. 개별 실수가 아니라, 하나가 찾히면 나머지를 찾을 이유가 사라지는 완료 조건의 구조 문제였습니다. 그래서 탐색 완료를 확인하는 게이트를 넣고, 열지 않은 대상은 근거를 반드시 남기게 했습니다.

비슷한 일이 문서에서도 있었습니다. 에이전트에게 기존 공통 컴포넌트를 재사용하라고 준 문서에 이미 사라진 컴포넌트 7개가 남고 실존하는 8개가 빠져 있었습니다. 재사용을 유도하려던 문서가 중복 구현을 유도하고 있었던 것입니다. 이후로는 에이전트의 자기 보고와 에이전트용 문서 모두 실물과 대조해 검증합니다.

## 문제를 어떻게 발견하고 트레이드오프를 판단했나

그리드 가상화에서 가장 큰 판단은 레이아웃을 호출부의 선택으로 남기지 않은 것입니다. 옵션을 남기면 가상화된 그리드와 이중 스크롤이 남는 그리드, 두 갈래가 계속 공존합니다. 옵션을 타입에서 지우고 예외는 높이를 고정해야 하는 화면 하나에만 별도 prop으로 열었습니다. 대신 인쇄 시 화면에 그려진 행만 인쇄될 수 있다는 제한과, 모달 안 sticky 기준 변수를 전역에서 바꾸는 영향을 PR에 명시하고 받아들였습니다.

스크롤바 훅에서는 반대로 강제하지 않는 쪽을 골랐습니다. 감싸는 부모를 필수로 하면 흔들림은 원천 차단되지만 기존 화면마다 DOM을 바꿔야 합니다. 부모를 선택값으로 두고, 생략하면 흔들릴 수 있다는 점을 TSDoc에 적었습니다.

# 4. 지원 동기 (선택)

공고가 플랫폼 영역의 고객에 엔지니어뿐 아니라 PM, 디자이너, 코딩 에이전트를 포함한 점이 지원한 이유입니다. 지금 팀에서 가장 효과가 컸던 일은 화면 하나를 잘 만든 것보다, 다른 사람과 에이전트가 같은 실수를 반복하지 않도록 공용 계층과 규칙을 고친 일이었습니다. 금융 서비스처럼 안정성 요구가 높은 환경에서, 여러 팀의 개발 흐름을 받치는 기반을 같은 방식으로 만들고 싶습니다.
