# 오퍼레이터 티켓 착수

오퍼레이터 티켓(`chucoding:dev-ticket-design`의 `오퍼레이터 티켓`)에 착수하면 착수 세션이 오퍼레이터로 남고, 하위 작업 티켓은 저장소마다 Orca 감독 워커로 띄운다. `chucoding:handoff`로 넘기지 않는다. 핸드오프로 띄운 세션은 Orca가 오퍼레이터 세션을 깨워 주지 않아, 오퍼레이터가 두 세션 사이에 필요한 정보를 넘길 수 없다.

2026-11-19 HDIT-7038(하위 BE HDIT-7039, FE HDIT-7040) 착수가 근거다. 그때는 핸드오프로 띄웠고 문제가 둘 생겼다.

- BE 세션이 공유 계약에 걸리는 질문(API 권한 방식)을 자기 탭의 선택지 창으로 띄웠다. 그 창이 떠 있는 동안 오퍼레이터의 `orca terminal send`는 `agent_prompt_blocked`로 거부됐다.
- 오퍼레이터는 사용자가 말해 줄 때만 터미널 화면을 읽어 상황을 알 수 있었다.

Orca 명령의 정본은 `orca skills get orchestration`이 내려 주는 가이드다. 이 스킬은 그 가이드를 대신하지 않고, 오퍼레이터 티켓에서 무엇을 워커로 띄우고 지시문에 무엇을 넣을지만 정한다. 착수 때 가이드를 한 번 읽고, 명령 형태가 이 스킬과 다르면 가이드를 따른다.

## 1. 적용 대상

| 상황 | 처리 |
|------|------|
| 오퍼레이터 티켓의 Jira URL이나 키로 착수를 요청받았다 | 이 스킬 |
| 오퍼레이터 티켓은 없지만 하위 티켓 둘 이상을 서로 다른 저장소에서 동시에 착수하고 그 사이에 공유 계약이 있다 | 이 스킬. 계약 정본을 어디에 둘지 먼저 사용자에게 묻는다 |
| 다른 저장소 작업을 넘기고 결과를 기다리지 않는다(위키, TIL, 스킬, 전역 AGENTS.md) | `chucoding:handoff` |
| 저장소가 하나뿐인 개발 티켓 | 평소 Jira 착수 |

- 사용자가 감독이나 대기를 따로 요구하지 않아도 위 두 행에 해당하면 감독 워커로 띄운다.
- 둘째 행처럼 오퍼레이터 티켓이 없으면 계약 정본을 둘 곳(하위 티켓 중 하나의 설명, 새로 만드는 오퍼레이터 티켓 등)을 사용자에게 물어 정한 뒤에 진행한다. 정한 위치에는 하위 작업 키와 저장소의 짝, 공유 계약을 적어 두고, 이 스킬에서 `오퍼레이터 티켓 설명`과 `오퍼레이터 키`라고 쓴 곳은 모두 그 위치와 그 티켓 키로 읽는다. 이 경로에는 `진행 방식`과 완료 조건이 없으므로 산출물을 모아 둘 곳, 통합 확인을 할지, 무엇을 끝으로 볼지도 띄우기 전에 사용자와 정한다. 정본을 정하지 못하면 워커를 띄우지 않는다.
- 오퍼레이터 티켓 자체의 착수 전환과 참고 탭은 평소처럼 `chucoding:jira`와 `chucoding:orca-jira-workbench`를 따른다. 이 스킬은 그 뒤 하위 작업을 띄우는 부분을 맡는다.
- 오퍼레이터 세션은 착수한 워크스페이스에서 그대로 돈다. 오퍼레이터 티켓은 코드 변경이 없으므로 저장소를 고르려고 워크스페이스를 새로 만들지 않는다.

## 2. 띄우기 전 준비

1. 오퍼레이터 티켓 설명의 `하위 작업`, `공유 계약`, `진행 방식`을 읽는다. 하위 작업 키와 저장소의 짝은 설명이 정본이다.
2. `공유 계약`에 모양이 정해지지 않은 지점이 있으면 워커를 띄우기 전에 사용자와 확정하고 설명을 먼저 고친다(`chucoding:dev-ticket-design`의 설명 4번).
3. 저장소마다 `orca repo list --json`에서 `id`를 찾는다. 선택자는 `name:`이 아니라 `id:<repoId>`를 쓴다(`chucoding:handoff`의 `2. 대상 저장소 판별`과 같은 이유). 저장소가 등록돼 있지 않으면 `orca repo add --path <절대경로> --json`으로 먼저 등록한다.
4. 워크스페이스 이름은 `<하위 티켓 키 소문자>-<영문 슬러그>`로 정한다(예: `hdit-7039-vote-sms-sender`). 브랜치 이름을 런북 형식으로 맞추는 것은 워커가 착수하면서 `chucoding:jira`의 `착수 브랜치 이름`대로 한다.
5. 저장소마다 PR을 올릴 배포 브랜치(base)를 확인한다. 기능 전용 배포 브랜치가 있는지 사용자에게 묻고, 정한 base를 지시문에 적는다. HDIT-7207(2026-11-23)에서는 허브(hd-cloud-client)에 신규 인쇄 전용 배포 브랜치 `print`가 있었는데 워커가 PR을 `main`으로 올려, 사용자가 "베이스 브랜치 주의하도록해. 신규 프린트 전용 배포용 브랜치 따로 있는걸로 알고 있어"라고 지적했다. 같은 작업에서 인쇄 서버(hd-cloud-print)는 `main` 하나였고 ERP에는 인쇄 전용 브랜치가 없었다. 저장소마다 다르므로 짐작하지 않는다. 5절의 `worker-start`에 `--base-branch <base>`를 넘겨 워크스페이스를 그 base에서 만들고(`worker-start --help`에 있는 옵션이며 이 조합으로 띄워 본 적은 아직 없다), 지시문에는 그 base가 `chucoding:commit-pr`의 통합 브랜치 판정보다 우선한다고 적는다.
6. 워커마다 지시문 파일을 `~/.claude/handoffs/<YYYYMMDD-HHMM>-<티켓키 소문자>-<슬러그>.md`에 쓴다. 대상 저장소 안에 두지 않는다.

## 3. 워커 지시문

지시문은 그 파일만 읽고 착수할 수 있게 쓴다. 워커는 이 대화를 읽지 못한다.

```markdown
# <하위 티켓 키> <제목> 착수

## 할 일
Jira 티켓 <하위 티켓 키>를 이 워크스페이스에서 착수해 개발완료까지 진행한다.
PR base는 `<2절 5번에서 정한 base 브랜치>`다. `chucoding:commit-pr`의 통합 브랜치 판정 결과가 달라도 이 base를 쓰고, 다른 브랜치로 올리지 않는다. 푸시 전 자기 리뷰의 base, AS-IS 녹화의 base 커밋(이 base와의 merge-base)처럼 통합 브랜치 판정을 쓰는 다른 자리도 이 base를 쓴다.

## 계약 정본
- 오퍼레이터 티켓 <오퍼레이터 키> 설명의 `공유 계약`. 구현 전에 다시 읽는다.
- 형제 티켓: <키>(<저장소>). 같은 시각에 다른 워크스페이스에서 진행 중이다.

## 배경과 판단 근거
<이번 대화에서 확인한 사실, 정한 결정과 버린 대안>

## 조율 규칙
<아래 네 규칙 전문>

## 끝나는 조건
1. PR을 올리고 `status`로 알린 뒤, 오퍼레이터에게 `ask`로 머지해도 되는지 묻고 턴을 끝낸다.
2. 고칠 내용을 답으로 받으면 고쳐서 푸시하고 1번을 다시 한다.
3. 머지해도 된다는 답을 받으면 이 저장소의 평소 PR 리뷰 절차를 거쳐 머지한다. 리뷰 반영이 공유 계약 항목을 건드리면 조율 규칙 1번대로 먼저 묻는다. 저장소 규칙이 사람 승인을 요구하면 리뷰어를 임의로 지정하거나 다른 계정으로 승인하지 않고, 사용자가 직접 승인을 받는다. 승인 상태는 `gh pr view <PR URL> --json reviewDecision`으로 본다. `APPROVED`나 빈 값이면 머지하고, `REVIEW_REQUIRED`면 턴을 끝내고 기다리며, `CHANGES_REQUESTED`면 요청 내용을 사용자에게 알리고 고칠지 묻는다. 기다리기 전에 오퍼레이터에게 `status`로 승인 대기 중인 PR을 알린다. 승인이 나면 사용자가 이 탭에서 이어 가라고 하거나 오퍼레이터가 `send`로 알리고, 그때 다시 조회해 아직 `APPROVED`가 아니면 같은 `status`를 보내고 다시 기다린다.
4. 머지를 확인하고 티켓을 개발완료로 옮긴 뒤 `worker_done`을 보낸다. 개발 서버 반영을 확인했으면 그 전에 `status`로 알리고, 확인하지 못했으면 `worker_done` 본문에 반영 미확인이라고 적는다.

## 하지 말 것
- 형제 티켓의 저장소를 고치지 않는다.
- 공유 계약을 오퍼레이터 답 없이 바꾸지 않는다.
- 오퍼레이터가 알리기 전에 머지하지 않는다.
<이 티켓에만 해당하는 금지 사항. 없으면 위 세 줄만 둔다>
```

`조율 규칙`에는 아래 네 가지를 빠짐없이 넣는다. 명령은 Orca가 워커 프롬프트 앞에 붙이는 안내(Task와 Dispatch ID가 든 preamble)의 형태를 따르라고 함께 적는다.

1. 공유 계약(API 경로, 파라미터, 응답, 오류 응답, 권한, 판정 기준)에 걸리는 질문이나 변경은 사용자 선택지 창(AskUserQuestion)으로 띄우지 않는다. 오퍼레이터에게 `orca orchestration ask --question "<질문>"`으로 묻고 턴을 끝낸다. Orca가 답과 함께 깨운다. 계약을 바꾸려면 바꾸기 전에 묻고, 답을 받은 뒤에 구현에 반영한다. 계약에 걸리는지 애매한 질문도 오퍼레이터에게 묻는다.
2. 계약과 무관한 결정은 그 세션에서 사용자에게 직접 묻는다.
3. 동기화 지점마다 오퍼레이터에게 `orca orchestration send --type status --subject "<요약>" --body "<내용>"`을 보낸다. 동기화 지점은 API 형태를 확정했을 때(계약대로 구현을 마쳤거나, 1번으로 답을 받아 바꾼 내용을 반영했을 때), PR을 만들었을 때, 개발 서버에 배포했을 때, 상대 저장소의 응답이나 동작을 가정하고 구현했을 때다. 본문에는 상대가 그대로 쓸 수 있는 산출물(응답 예시, payload 예시, PR 링크, 가정한 내용)을 넣는다.
4. PR은 올리되 오퍼레이터가 머지해도 된다고 알리기 전에는 머지하지 않는다. 오퍼레이터는 맞물리는 하위 작업의 산출물을 모두 계약과 대조한 뒤에 알린다. PR `status`를 보낸 뒤에는 `ask`로 머지해도 되는지 묻고 턴을 끝낸다. 허가를 `ask`의 답으로 받게 하는 이유는 무엇을 기다리는지가 오퍼레이터에 질문으로 남고, `ask`로 끝낸 턴은 오퍼레이터에 `escalation`을 일으키지 않기 때문이다.

- 2번을 빼고 모든 질문을 오퍼레이터로 보내게 하지 않는다. 1번의 애매한 질문만 예외로 오퍼레이터를 거친다. 계약과 무관한 결정까지 오퍼레이터를 거치면 사용자가 그 탭에서 바로 답할 수 있는 것이 한 단계 늦어진다.
- 4번의 기준은 통합 E2E가 아니라 오퍼레이터의 산출물 대조다(사용자 결정, 2026-11-19). 통합 E2E는 하위 작업이 모두 개발완료되어 개발 서버에 반영된 뒤에 오퍼레이터 티켓에서 하므로(`chucoding:dev-ticket-design`의 `진행 방식`), 머지를 E2E 뒤로 미루면 서로를 기다리게 된다.
- `끝나는 조건` 3번의 승인 문구는 기본으로 넣는다. HDIT-7207(2026-11-23)에서는 세 저장소 모두 브랜치 규칙상 다른 사람의 승인 1건이 필요해, 오퍼레이터가 머지를 허가한 뒤에도 워커가 막혔다. 매번 사용자가 직접 승인 요청을 골랐다(ERP #320, print #114, 허브 #3081).
- 받는 쪽이 주는 쪽 배포보다 먼저 개발하면 계약대로 만든 mock으로 개발한다는 것과 mock을 언제 지우는지를 `배경과 판단 근거`에 적는다.

## 4. 확인 받기

워커를 띄우기 전에 `chucoding:handoff`의 `4. 확인 받기`와 같은 방식으로 승인받는다. 승인 없이 띄우지 않는다.

- 워커마다 대상 저장소, 워크스페이스 이름, 지시문 파일의 절대경로와 내용 전문을 선택지 질문 밖의 본문으로 출력한 뒤 승인 질문을 띄운다.
- 워커 전부를 한 번에 출력하고 승인도 한 번에 받는다.
- 사용자가 고치게 하면 고친 전문을 다시 출력하고 다시 승인받는다.

## 5. 워커 띄우기

```bash
orca orchestration worker-start --spec-file <지시문 절대경로> --task-title "<하위 티켓 키> <저장소>" \
  --worktree new-top-level --repo id:<repoId> --name <워크스페이스 이름> --base-branch <2절 5번의 base> --agent claude --json
# 둘째 워커부터는 첫 결과의 runId를 --run <run_id>로 넘겨 같은 Run에 묶는다
```

- 이 `new-top-level` 형태는 2026-11-19 skills 저장소에 일회용 워커 하나를 띄워 확인했다. 결과는 `state: ready`, `keptOpen: true`였고 `dispatchId`, `taskId`, `runId`, 워커 터미널 handle이 함께 왔다. 저장소 둘에 동시에 띄우는 것과 Jira 착수를 맡긴 워커는 아직 돌려 보지 않았다. 결과가 이 설명과 다르면 가이드와 결과의 `next`를 따르고, 달랐던 점을 보고에 남긴다.
- 워크스페이스는 저장소마다 `new-top-level`로 만든다. 오퍼레이터 워크스페이스 아래에 두는 `new-child`나 `current`를 쓰지 않는다. 하위 작업은 저장소가 다르다.
- 새 워크스페이스로 띄운 워커는 끝나도 열린 채 남는다(`--help`의 Notes). 사용자가 그 탭에서 리뷰 대응과 QA 재작업을 이어 갈 수 있다.
- `worker-start`가 실패하면 같은 명령을 다시 돌리지 않는다. 결과의 `failedStage`를 읽고 가이드의 `references/recovery-and-cleanup.md`를 따른다.
- 워커를 모두 띄웠으면 Run id와 워커별 dispatch id, 워크스페이스, 지시문 경로를 보고하고 턴을 끝낸다. 터미널을 주기적으로 읽거나 `check`를 도는 감시 스크립트를 만들지 않는다. Orca 가이드가 금지하고, Orca가 메시지가 올 때 오퍼레이터를 깨운다.
- 워커에게 말할 때는 터미널 입력(`orca terminal send`)이 아니라 `orca orchestration send --to dispatch:<dispatch_id>`를 쓴다. 가이드는 일하는 중인 워커가 이 메시지를 현재 턴이 끝날 때 받는다고 적는다. 턴을 끝내고 쉬는 워커는 `send`와 `ask`의 `reply` 모두로 깨어난다(2026-11-19 일회용 워커로 확인. `reply`를 받은 워커가 답을 읽고 턴을 끝냈고, 뒤이은 `send`로 다시 깨어나 `worker_done`을 보냈다). 선택지 창이 떠 있는 워커에 언제 들어가는지는 확인하지 못했다. 오퍼레이터는 워커를 감시하지 않아 창이 떠 있는지 알 수 없으므로, `send`나 `reply`를 보낸 턴의 끝 보고에 무엇을 어느 워커에 보냈는지 항상 적는다. 6절에서 보내는 메시지도 같다. 워커가 멈춰 있으면 사용자가 그 탭의 질문에 답한다. 머지 허가를 `send`가 아니라 `ask`와 `reply`로 주고받는 이유는 3절 조율 규칙 4번에 적었다.

## 6. 깨어났을 때

Orca가 깨우면서 `check` 명령을 알려 주면 그 명령을 돌린다(HDIT-7038에서는 `orca orchestration check --run <run_id> --terminal <오퍼레이터 handle>`). 받은 메시지는 종류별로 아래처럼 처리한다.

| 받은 것 | 처리 |
|------|------|
| `status` | 내용에서 상대 워커가 알아야 할 것만 골라 `orca orchestration send --to dispatch:<상대 dispatch_id> --subject "<요약>" --body "<내용>"`으로 넘긴다. 상대와 무관하면 넘기지 않는다. 산출물은 오퍼레이터 티켓 `진행 방식`대로 모아 둔다 |
| `question`(워커의 `ask`) | 답이 계약 정본이나 사용자가 이미 정한 것에서 나오면 `orca orchestration reply --id <message_id> --body "<답>"`으로 답한다. 계약을 바꾸거나 새로 정해야 하면 아래 `계약 변경`을 거친 뒤 답한다. 계약과 무관한 질문이면 그 세션에서 사용자에게 직접 물으라고 답한다. 머지해도 되는지 묻는 질문은 아래 대조 항목대로 답한다 |
| `worker_done` | 그 하위 작업의 결과를 사용자에게 보고한다. 실패로 온 보고를 완료로 적지 않는다 |
| `escalation` | 워커가 `worker_done` 없이 턴을 끝냈다는 뜻이고 실패가 아니다. 2026-11-19 확인에서 `ask`를 보내고 끝낸 턴에는 오지 않았고, `ask` 없이 끝낸 턴에는 `stopReason: finished`로 왔다. 본문의 `Last output`으로 워커가 왜 멈췄는지 읽는다. 워커가 오퍼레이터에게서 받을 것(답, 상대 산출물)을 기다리며 멈췄으면 줄 수 있는 것은 `send`로 보내고, 아직 줄 수 없으면 무엇을 기다리는지 사용자에게 알린다. 머지 허가를 기다리는데 `ask`가 없으면 허가를 `send`로 보내지 않고, 머지해도 되는지 `ask`로 다시 물으라고 `send`로 알린 뒤 그 `ask`를 아래 대조 항목대로 처리한다. 사용자 답이 필요해 멈춘 것이면 어느 워커인지 사용자에게 알린다. 머지 허가 뒤 PR 승인을 기다리며 멈춘 것(`끝나는 조건` 3번)이면 어느 PR이 승인을 기다리는지 사용자에게 알린다. 사용자가 승인이 났다고 알리면 그 워커에 `send`로 이어 가라고 보낸다. 이유를 읽어 낼 수 없으면 워커에 `send`로 무엇을 기다리는지 `status`로 답하라고 묻고 사용자에게도 알린다. 그 답은 위 `status` 행대로 처리한다. 그 워커의 이후 쉬는 턴은 오퍼레이터가 다시 쓰기 전까지 보고되지 않는다(2026-11-19에 받은 `escalation` 본문의 안내). 사용자 선택지 창을 띄운 채인 워커가 이 메시지를 일으키는지는 확인하지 못했다 |

- HDIT-7038에서는 FE 워커의 `status`에서 BE가 알아야 할 것(FE가 가정한 응답)만 골라 BE 워커에게 넘겼다.
- PR `status`가 오면 그 워커의 산출물을 계약과 대조한다. 대조 대상은 `status` 본문의 응답 예시와 payload 예시, 그리고 PR diff(`gh pr diff <PR URL>`)에서 계약 항목(경로, 파라미터, 응답 필드, 오류 응답, 권한)에 해당하는 부분이다. 계약과 무관한 구현은 보지 않는다.
- 머지해도 되는지 묻는 `ask`에는 그 계약 지점으로 맞물리는 하위 작업의 PR이 모두 올라와 계약과 맞을 때 `reply`로 허가한다. 하위 작업이 셋 이상이면 전체가 아니라 같은 계약 지점을 주고받는 작업끼리 묶어 본다. 상대 PR이 아직 없으면 답을 미루고 그 사실을 사용자에게 알린다.
- 구현이 계약과 다르면 그 워커의 `ask`에 고칠 내용을 답하고 사용자에게 보고한다. 워커는 고친 뒤 다시 `status`와 `ask`를 보낸다. 계약 쪽을 바꿔야 맞는 경우면 아래 `계약 변경`을 거친다.
- 처리할 것이 없으면 턴을 끝낸다. 하위 작업이 모두 `worker_done`으로 끝나면 오퍼레이터 티켓 `진행 방식`의 통합 E2E로 넘어가고, 완료 처리는 `chucoding:jira`의 `상태 전환`에 있는 오퍼레이터 티켓 항목을 따른다. 통합 E2E의 캡처와 녹화는 처음부터 `chucoding:screen-evidence`의 보관 폴더에 두고(그 스킬의 `오퍼레이터 통합 E2E 증빙`), 완료 처리에서 증빙 댓글로 남긴다.

### 계약 변경

1. 계약을 바꾸거나 새로 정하는 결정은 오퍼레이터가 정하지 않고 사용자에게 선택지로 묻는다.
2. 결정되면 오퍼레이터 티켓 설명의 `공유 계약`을 먼저 고친다. 설명이 계약 정본이다. 수정은 `chucoding:jira`의 설명 수정 규칙을 따른다.
3. 그 뒤 질문한 워커에는 `reply`로, 영향받는 다른 워커에는 `send --to dispatch:<id>`로 바뀐 내용을 알린다. 질문한 워커 없이 오퍼레이터의 대조에서 시작된 변경이면 모두 `send`로 알린다.
4. 하위 작업 티켓 설명에 반영할 것이 있으면 함께 고친다. 오퍼레이터 티켓의 완료 조건이다.

## 7. 핸드오프로 띄운 세션 전환

이미 `chucoding:handoff`나 `orca worktree create`로 띄운 세션은 그 터미널을 감독 워커로 전환할 수 있다. 2026-11-19 HDIT-7038에서 돌고 있던 BE와 FE 세션을 이렇게 전환했다(실측).

```bash
orca orchestration worker-start --spec-file <지시문 절대경로> --task-title "<제목>" --terminal <기존 handle> --keep-open --json
# 둘째 워커부터는 첫 결과의 runId를 --run <run_id>로 넘겨 같은 Run에 묶는다
```

- 지시문에는 3절의 `조율 규칙`, `끝나는 조건`, `하지 말 것`을 그대로 넣고 지금까지 진행한 작업을 이어서 한다는 것을 적는다. 3절 `할 일`의 PR base 문구도 2절 5번의 base로 넣는다. `--terminal`로는 워크스페이스 base를 바꿀 수 없으므로, 그 세션의 브랜치가 다른 base에서 갈라졌으면(`git merge-base --is-ancestor <base> HEAD`가 실패) 사용자에게 알리고 어떻게 할지 묻는다. 4절의 승인도 똑같이 받는다.
- `--terminal`을 쓸 때는 `--worktree`와 `--agent`를 붙이지 않는다. 그 터미널의 워크스페이스에서 시작한다.
- 세션이 턴을 도는 중이면 결과가 `state: outcome_unknown`, 경고 `turn_start_unobserved`로 온다. 지시문이 입력만 된 상태이며 실패가 아니다. 다시 보내지 않고 기다린다. HDIT-7038에서는 FE 워커가 약 2분 뒤 `status`를 보냈고 Orca가 오퍼레이터를 깨웠다.
- 워커의 선택지 창이 떠 있을 때의 처리는 `5. 워커 띄우기`의 `send` 항목과 같다.

## 8. 하지 않는 것

- 하위 작업을 `chucoding:handoff`로 띄우지 않는다.
- 승인 없이 워커를 띄우지 않는다.
- 터미널을 폴링하거나 감시 스크립트를 만들지 않는다.
- 계약을 바꾸는 결정을 사용자 확인 없이 워커에게 답하지 않는다.
- 워커의 커밋, 테스트, PR을 오퍼레이터 세션에서 대신 하지 않는다. `chucoding:commit-pr`은 각 워커의 몫이다.
- 만든 워크스페이스와 워커를 사용자 확인 없이 지우거나 멈추지 않는다.
- Orca의 `orchestration` 가이드 파일을 고치지 않는다. Orca가 버전에 맞춰 내려 주는 파일이다.
